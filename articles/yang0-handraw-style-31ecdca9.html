偵察提案：yang0/handraw-style

專案是什麼

一個「手繪風格編號畫廊＋雙語提示詞」的 Skill：以編號條列多種手繪視覺風格，每則搭配中英雙語提示詞片段，供呼叫端以編號選取風格而非重新描述需求。定位是提示詞複用工具，成熟度屬單一 Skill 級別（非框架），核心機制細節（如是否用 JSON/YAML 清單而非純 Markdown 條列）未見原始碼，待查證。

對本系統的借鑑點

已實際讀取 examples/plugins/skill-prompt/skills/ 下三支模板核對：team-podcast-script.md、team-podcast-buddhist-script.md、team-podcast-news-script.md——三者主持人設定（曉晨/host_a 等）高度雷同，差異僅在素材網域（一般筆記／佛學機構／時事）與 truncate 數值，卻各自獨立成檔、各自維護一份 description／when／triggers frontmatter，被 resource.catalog 索引為三條互相競爭比對分數的獨立條目。

對照之下，team-insight-lenses.md 已示範另一種做法：主透鏡／對抗透鏡是呼叫端傳入的參數，而非寫死在檔案裡的變體——同一支模板承載多種視角，不靠複製檔案。

handraw-style 的「編號畫廊」補的是介於兩者之間的第三種模式：當變體集合是有限、已知、可預先列舉（如三種主持人設定）時，不必像 lens 模板那樣完全開放參數化（呼叫端可能給出未預期的透鏡名），而是把變體收斂成模板內建的編號清單，呼叫端只傳編號，模板內部展開對應的人設與素材規則。這剛好填補 podcast 三支模板目前「既非完全參數化、也非開放輸入」的中間狀態所造成的檔案重複。

具體對應：可將 team-podcast-script／-buddhist-script／-news-script 的人設與素材規則收斂為一支模板內的編號清單（例：1=一般筆記 2=佛學時事 3=一般時事），frontmatter 只需維護一份，triggers 詞彙不再三處分散比對。

建議行動

低風險（可先做）：

  1. 對現有 3 支 podcast 模板做重複率量測——逐行比對 frontmatter 的 triggers 詞彙重疊比例、body 中主持人設定段落的字元相似度（可用簡單 diff 或 Levenshtein），並查 resources match 對同一意圖查詢（如「podcast 逐字稿」）時這 3 支是否互相擠壓排名，取樣本數＝3 支模板 × 5 組意圖查詢，記錄各自命中排名與分數。
  2. 若重複率量測確認高相似（如主持人設定段落相似度 >70%），先寫一份合併後的草案模板（不上線），驗證編號選取邏輯能否用純 frontmatter＋body 條列達成，不需改動 resource-catalog 或 skill.invoke 的呼叫介面 schema。

需人工決策：

是否要真的合併這 3 支模板並汰除舊檔——這會改變既有排程任務（若 todoist-team 或插件呼叫端已硬編碼舊 skill id）的呼叫參數，需要人工確認目前有哪些呼叫方依賴舊 id 後才能執行，避免破壞現有排程。
