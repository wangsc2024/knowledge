偵察提案：okf-agent-memory（okf-memory/okf-agent-memory）

專案是什麼

純 Go 實作的「Git-native」代理記憶系統，實作 Google OKF v0.2 標準：知識以帶 YAML frontmatter 的 Markdown 儲存於 knowledge/{project,architecture,convention,roadmap}/，靠純本機 BM25（<300µs）索引與 index.md 階層＋link graph 做漸進式揭露，零外部資料庫。CLI 提供 init/create/update/validate/search/show/bootstrap/mcp，並以 mcp knowledge 內嵌 MCP server 供 Claude Code／Cursor／Codex 直接掛載。frontmatter 明確含 sources（來源）、generated vs verified（信任層級）、status／stale_after（生命週期／過期時間）。成熟度中等：README 完整但 SPEC/CLI 細節分散在獨立文件，多數欄位語法未在首頁公開（已查證確認，非猜測）。

對本系統的借鑑點

  1. Skill frontmatter 缺生命週期欄位——已查證屬實：test/skill-frontmatter-quality.test.mjs 只對 description／triggers／when 三個欄位評分（docs/SKILL-INDEX.md §7），完全沒有「這份 skill 內容是否過期」「是人工核實還是自動 backfill 佔位」的標記。OKF 的 status／stale_after／generated vs verified 三元組可直接補上：backfill 產生的樣板值標 generated+短 stale_after，人工定稿後改 verified，讓每日輪替評估（quality_daily）優先挑到「快過期」而非隨機輪替。
  2. 知識庫筆記缺信任分級：個人知識庫（localhost:3000）目前筆記無來源可信度區分，OKF 的 sources＋trust tier 可作為 knowledge-query 回答時的權重依據（例如自動生成摘要 vs 人工驗證筆記，回答時優先引用 verified）。
  3. resources match 已有語意匹配，OKF 的 BM25＋index.md 非取代而是互補：Cordis 的 catalog 走「決定論比對＋LLM 意圖」，OKF 走純本機 BM25 全文檢索。若知識庫筆記量成長導致查詢延遲，BM25 索引可作為 knowledge-query 的輕量本機備援層，但這點效益待實測驗證，非立即需求。

建議行動

  • 低風險、可先做：在 examples/plugins/skill-prompt/skills/*.md frontmatter schema 追加 status（generated/verified）與 stale_after 兩欄位，並擴充 parseSkillFrontmatter／skill-frontmatter-quality.test.mjs 納入檢查——這是對既有機制的欄位擴充，不引入新依賴。
  • 需人工決策：是否要引入完整 OKF CLI／Go binary 作為外部工具鏈（增加一種非 Node.js 執行環境），或只借用其 schema 概念、自行在既有 JS 生態內實作，避免多語言維運負擔。
  • 待查證後再議：knowledge-query 是否需要本機 BM25 備援，需先實測目前語意搜尋在筆記量成長後的延遲，再決定要不要引入。
