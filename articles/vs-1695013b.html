引言

企業導入多代理 LLM 系統時，選型討論多半停留在框架流行度的表層比較——該用 LangGraph 還是 AutoGen？CrewAI 夠不夠用？這類問題掩蓋了更根本的架構問題：這些框架背後其實分屬兩種源自控制理論與分散式系統實務、已存在數十年的控制範式——「宣告式協調迴圈」（declarative reconciliation loop）與「命令式逐步排程」（imperative step-scheduled orchestration）。前者要求使用者僅宣告期望狀態，交由持續運作的調和迴圈自動收斂；後者則以逐步指令或對話式互動，由執行環境即時決定下一步行動。

既有文獻對此二分法的系統性整理付之闕如：多代理 LLM 編排研究多聚焦個別框架效能評測（如 Gradientsys 於 GAIA 基準的表現），基礎設施研究則多停留在容器編排領域（如 Kubernetes 控制器模式），兩條文獻脈絡至今罕見交會。與此同時，MCP 與 A2A 兩大新興協定的興起，進一步模糊了協定層與編排引擎層的範式邊界，業界論述常見「協定大戰」敘事（MCP vs. A2A），卻少有研究釐清兩者實際控制邏輯的異同。

本文的知識缺口與貢獻在於：(1) 系統性梳理宣告式與命令式範式在 AI Agent 編排各層級（基礎設施、協定、編排引擎）的具體實作譜系；(2) 以三角佐證法驗證兩範式並非互斥對立，而是依抽象層級分工並存的分層混合設計；(3) 提出企業架構決策應以「所需控制力與確定性程度」而非框架流行度作為核心判準的分類框架，並納入社群對宣告式抽象層必要性的批判聲音，避免單向度的技術樂觀主義。

[李飛飛主筆]

命令式／逐步排程源流。這條文獻脈絡的奠基之作是 Yao 等人（2023）提出的 ReAct 範式：讓語言模型以交錯方式產生推理軌跡與行動，推理協助模型建立、追蹤、更新行動計畫，行動則讓模型與外部環境互動取得新資訊。這篇 ICLR 2023 論文之所以重要，不只是因為其在 HotpotQA、ALFWorld 等任務上優於純思維鏈基線，更因為它確立了後續絕大多數命令式多代理框架共享的理論基礎：逐步、交錯、由模型即時決定下一步的控制邏輯。同年，Schick 等人（2023）的 Toolformer 補上了「每一步驟如何觸發外部呼叫」的細節——模型以自監督方式自我學習何時呼叫哪個 API、傳入何種參數，僅需少量示範即可習得工具使用能力。

這套交錯推理—行動迴圈很快被搬進企業級多代理系統。Wu 等人（2024）的 AutoGen 讓可自訂、可對話的代理彼此交談完成任務，編排邏輯以自然語言與程式碼共同定義，命令式地嵌入 Python 程式並與執行環境緊密耦合——這正是我認為值得警惕之處：對話驅動的彈性固然吸引原型開發者，但也讓系統行為難以在治理層面被完整預測，我稱之為「彈性與可觀測性的技術根本取捨」，而非單純的框架好壞之爭。Hong 等人（2024）的 MetaGPT 則走向另一個極端：將人類標準作業程序編碼為提示序列，以「組裝線」典範拆解任務給具人類職能角色的代理依序執行，屬結構化命令式流程的代表——SOP 序列本質上是預先設計好的逐步腳本，而非持續調和的期望狀態宣告。Song 等人（2025）的 Gradientsys 進一步將 ReAct 式動態規劃迴圈與具型別 MCP 結合，支援同步/非同步混合執行與失敗重試重規劃，是命令式範式在企業多代理排程的當代代表。

宣告式／協調迴圈源流。此脈絡的學術根源遠早於 AI Agent 熱潮。Kephart 與 Chess（2003）提出的「自主運算」願景與 MAPE-K 迴圈——監控、分析、規劃、執行於共享知識庫上運作——是控制理論式回饋迴圈應用於軟體自我調適最早、引用量最高的經典文獻之一。Brun 等人（2009）進一步主張回饋迴圈本身必須被當作一等公民明確設計、建模與驗證，而非隱藏於應用邏輯內部，為「宣告式協調迴圈」提供跨領域控制理論支撐。這套思想在工業界最具權威性的落地案例，是 Google 十餘年容器管理系統演化：Verma 等人（2015）描述的 Borg 依使用者宣告的工作規格搭配准入控制達成高利用率，Burns 等人（2016）回顧 Borg→Omega→Kubernetes 三代系統演化，核心論點是 Kubernetes 採宣告式 API 搭配持續調和的控制迴圈取代命令式指令稿。Kubernetes 官方文件將「控制器」明確定義為「永不終止的控制迴圈」，並以 Operator 模式將此思想延伸到應用層自動化維運——這是本論文分類學中「宣告式」一端最權威的術語錨點。

2026 年，Mouzouni 提出的 Context Kubernetes 將這套思想直接移植進 AI Agent 治理層：以 YAML 宣告式 manifest 定義知識架構、以調和迴圈持續使實際知識存取狀態收斂至期望的權限/新鮮度狀態，並以三層代理權限模型確保代理權限恆為人類權限子集，經 TLA+ 模型檢查驗證 460 萬可達狀態零違規。這是我認為本文獻回顧中最關鍵的證據：它證明「宣告期望狀態、由系統持續調和」不再只是基礎設施層的工程慣例，而是正被有意識地類比、移植進 AI 治理這個更高風險的領域。同一脈絡下，Daunis（2025）提出的宣告式 Agent 工作流 DSL 在 PayPal 真實電商場景驗證，開發時間減少 60%、程式碼複雜度由 500+ 行命令式程式碼降至 50 行以下，是「宣告式優於命令式」最直接的量化企業實證。

協定層的分層混合。MCP 與 A2A 常被業界簡化為「協定大戰」的兩個對立陣營，但仔細檢視規格文件會發現更細緻的圖像：MCP 官方規格明確定義伺服器向客戶端「提供」（offer）Resources／Prompts／Tools 三類能力，客戶端查詢協商後動態使用，但底層執行仍以 JSON-RPC 方法呼叫完成；A2A 的 Agent Card 則讓代理以 JSON 中繼資料宣告身份與能力，供客戶端在互動前讀取以決定可用互動模式，避免試錯呼叫。中文技術部落格優程式的觀察與此一致：MCP「內建自我描述能力，允許伺服器宣告其可提供的資源與操作」，同時底層仍以 JSON-RPC 標準訊息格式執行。WorkOS 的獨立技術評論則提供了本文獻回顧中最精煉的定位：MCP 是「垂直」的 agent↔tool 協定，A2A 是「水平」的 agent↔agent 協定，兩者「無法處理點對點協商」（MCP 的侷限）與「缺乏標準化的資料連接能力」（A2A 的侷限）互為表裡，需疊加而非互斥用於企業級編排。

企業框架選型實務。LangGraph 官方文件將框架建模為 State、Nodes、Edges 三元件，「先宣告拓撲、後編譯執行」，是宣告式狀態機陣營的主要代表；Temporal 官方部落格則主張其 Durable Execution 模型讓開發者以一般程式語言、命令式 for/while/if 控制流表達 agent loop，由 runtime 保證容錯與跨崩潰恢復；AWS Step Functions 延續 Amazon States Language 宣告式狀態機傳統，將 agent 推理嵌入既有宣告式工作流。獨立比較文章 Pathak（2026）附上具體成本數據：每日千次 GPT-4o-mini 呼叫下 LangGraph 約 63 美元、CrewAI 約 78 美元、AutoGen 無終止上限時約 171 美元——這正是我所強調的「數據即科學儀器」：成本與可靠性的量化比較，遠比框架熱度更能指引企業決策。中文業界論述 we0.ai 與 CrewAI 官方文件呼應相同結論：CrewAI 角色制、速度優先，適合原型驗證；LangGraph 圖狀態機、控制優先，適合正式上線。

研究方法

本研究採三階段檢索策略。Phase 0 以 arXiv、OpenAlex、Semantic Scholar 進行機械化論文採集，取得 24 篇基礎候選（含 title、abstract、year），確立「宣告式協調迴圈 vs. 命令式逐步排程」此一候選主題方向後，再以目標式關鍵詞——declarative orchestration、reconciliation loop、autonomic computing、MAPE-K、ReAct、Model Context Protocol、Agent2Agent Protocol、LangGraph vs AutoGen vs CrewAI 等——追加檢索，最終候選池篩選達 56 筆，納入 32 篇獨立來源，達成 Tier S 門檻（候選池 ≥40、納入來源 ≥20）。

納入排除準則採三層優先序：Tier A（同行評審論文、官方規格書之原始出處，如 arXiv、ACM Queue、IEEE、NeurIPS/ICLR/COLM 會議論文，共 11 篇）優先於 Tier B（官方文件與規格、企業部落格首發公告，共 9 篇），Tier B 再優先於 Tier C（獨立比較評測、企業技術部落格、社群討論，共 12 篇，含 Hacker News 與 V2EX 討論串）。Tier C 來源不作為核心主張的唯一佐證，僅用於三角驗證與呈現實務／社群分歧觀點，且刻意納入批判性反例以避免報告淪為單向度技術樂觀主義。中文來源刻意納入以驗證分類學在中文技術社群論述中同樣成立。全程排除知識庫既有筆記作為選題或引用來源，以避免自我引用循環。

三角佐證法要求每條核心主張至少 3 個獨立來源交叉確認：≥3 獨立來源同意標記「已驗證✅」，僅單一來源或分歧未達共識則標記「部分驗證⚠️」並如實呈現分歧觀點。本研究對 5 條核心主張完成三角驗證，4 條達成「已驗證✅」（各由 4-5 個獨立來源支持），1 條標記為「部分驗證⚠️」（社群對宣告式框架必要性存在分歧，構成本文風險與限制章節素材，而非被忽略或掩蓋）。

結果與討論

[李飛飛主筆：核心論證]

三角佐證後的核心發現有三。第一，宣告式協調迴圈已從基礎設施層系統性遷移進 AI Agent 治理層。這不是類比修辭，而是可驗證的工程事實：Context Kubernetes〔來源：Context Kubernetes: Declarative Orchestration of Enterprise Knowledge for Agentic AI Systems, 2026〕形式化了六個核心抽象、一套 YAML 宣告式 manifest 與調和迴圈，並以 TLA+ 模型檢查驗證 460 萬個可達狀態零違規——這種可驗證性正是我認為宣告式範式在治理場域被優先採用的根本原因：當「誰能存取什麼」必須對稽核與監理負責時，宣告式的期望狀態比命令式的執行軌跡更容易被形式化驗證。Kubernetes 官方對「控制器」的定義〔來源：Controllers, Kubernetes Documentation〕——「永不終止的控制迴圈，持續觀察叢集現狀並試圖使其逼近期望狀態」——恰好點出這種治理優勢的技術根源：控制邏輯與期望狀態解耦，使兩者可被獨立稽核。

第二，命令式逐步排程並未因此式微，而是在推理與工具呼叫層持續擴張。ReAct〔來源：ReAct: Synergizing Reasoning and Acting in Language Models, 2023〕確立的交錯推理—行動迴圈，經 AutoGen〔來源：AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversation, 2024〕、MetaGPT〔來源：MetaGPT: Meta Programming for A Multi-Agent Collaborative Framework, 2024〕與 Gradientsys〔來源：Gradientsys: A Multi-Agent LLM Scheduler with ReAct Orchestration, 2025〕不斷擴充，證明「由模型即時決定下一步」在需要開放式探索、無法窮舉狀態空間的任務類型上，仍具有宣告式狀態機難以取代的靈活性。

第三，也是三角佐證中證據密度最高的發現：協定層的宣告式與命令式並非互斥，而是分層混合。MCP〔來源：Specification (2025-06-18), Model Context Protocol〕與 A2A〔來源：A2A Protocol Specification, 2026〕都採「先宣告可用能力、後協商互動」的宣告式能力發現層，但底層執行仍以命令式方法呼叫（如 MCP 的 tools/call）完成。WorkOS 的獨立分析〔來源：MCP vs. A2A: Which AI agent protocol should you use?, 2025〕與中文部落格優程式〔來源：MCP（模型上下文協定）是什麼？技術原理解析, 2025〕從不同語言脈絡得出一致結論，強化了此發現的跨語境穩健性。

[Yann LeCun 主筆：實踐建議]

基於以上發現，我認為企業架構決策不該問「LangGraph 還是 AutoGen」，而該先回答一個更根本的問題：這個任務需要多少確定性？三個具體建議。第一，若任務涉及合規稽核、權限治理或需要人工核准閘門——例如金融交易審核、醫療資料存取——優先選擇宣告式狀態機陣營：LangGraph〔來源：Graph API overview, LangGraph Docs, 2026〕的顯式節點/邊拓撲、AWS Step Functions〔來源：AWS Step Functions adds AgentCore-powered agentic reasoning step, 2026〕的 Amazon States Language，兩者共同特徵是執行路徑可在部署前被靜態稽核。第二，若任務屬開放式探索、原型驗證或需要快速迭代——例如客服對話輔助、內容生成草稿——命令式/對話式框架的低門檻價值更高：獨立比較文章〔來源：LangGraph vs CrewAI vs AutoGen: Which AI Agent Framework Should You Use in 2026?, 2026〕實測顯示 LangGraph 學習曲線長達 10 至 14 天，CrewAI〔來源：CrewAI Documentation, 2026〕原型速度快但長時間無人值守任務中委派鏈脆弱；這是典型的「架構是否可擴展」與「是否只是 prompt 工程」的權衡，不必為了顯得工程嚴謹而過早引入宣告式抽象層。第三，Temporal〔來源：Build Resilient Agentic AI with Temporal, 2025〕證明命令式風格本身也能達到高確定性——重點從來不是「宣告式 vs 命令式」的意識形態選邊站，而是這個框架是否把回饋迴圈（我稱之為系統的「世界模型」——它如何感知並修正自身狀態）當作一等公民來設計，這才是我判斷任一框架成熟度的核心啟發式。

[Yann LeCun 主筆：風險與限制]

我必須誠實指出這篇分類學本身的限制。首先，證據時間窗口嚴重偏向 2025-2026 年新興論文與企業部落格，長期生產環境的量化實證（例如三年以上運行的宣告式 AI 治理系統故障率）仍付之闕如，Context Kubernetes 的 460 萬狀態驗證是模型檢查（model checking），不是生產環境的實際運行數據，這個差異不該被模糊。其次，Hacker News 上關於 LangGraph 的討論串〔來源：I don't really understand why an engineer would use langgraph..., 2024〕提出了我認為必須被正視、而非消音的質疑：若圖形化/宣告式介面對程式設計真的普遍有用，為何一般程式設計不早已大規模採用？LangGraph 作者本人的澄清——核心價值在於處理循環（cyclic）控制流而非「視覺化無程式碼」——某種程度上迴避了更根本的問題：這種循環控制流的複雜度，究竟是任務本質需要的，還是框架自身製造出來、再由框架自己解決的。另一則關於 MCP 的討論串〔來源：Reflections on building with Model Context Protocol, 2024〕更直接：「教會 LLM 存取資源不該超過一個單檔 shell/python 腳本」。我不完全同意這個極端立場，但它指出了一個真實張力——宣告式協定層的治理價值，是用組織規模換來的；對單一開發者或小團隊而言，這層抽象的邊際成本可能大於邊際效益。最後，V2EX 上對 A2A 協定的討論〔來源：谷歌發布 A2A 協定——谷歌版本的 MCP, 2025〕反映協定標準化本身也存在收斂不確定性，「表面互補、實則競爭」的產業現實意味著本文的協定層分類學可能在未來 12-24 個月內因協定合併或棄用而需要修正。

原創論點

[李飛飛主筆]

基於前述證據，我提出四個獨立論斷，這些論斷不是文獻回顧的重述，而是我對證據模式的判斷。

第一，我主張當前業界「協定大戰」敘事（MCP vs. A2A）本身就是一個被過度簡化的假問題。仔細比對兩份規格書會發現，MCP 與 A2A 共享同一種「宣告式能力發現＋命令式執行」的分層設計哲學——差別只在於協商的對象是工具（MCP）還是代理（A2A）。真正值得業界關注、卻鮮少被討論的分歧，其實發生在更高層的編排引擎（LangGraph vs. Temporal vs. AutoGen）：這才是決定一個企業系統究竟是「宣告式治理優先」還是「命令式靈活優先」的關鍵層級，協定層的選擇反而相對次要，甚至如 WorkOS 分析所示，兩者常被建議疊加而非二選一。這個論斷把業界注意力錯置的問題點了出來——資源被投入在協定層的路線之爭，而非真正決定架構命運的編排引擎層決策。

第二，我認為宣告式與命令式的選型爭論，本質上是組織治理成熟度的訊號，而非純粹的技術優劣判斷。Context Kubernetes 的三層代理權限模型之所以重要，不是因為它技術上多精妙，而是因為它把「代理權限恆為人類權限子集」這個治理承諾，用可形式驗證的方式寫進了架構本身。一個組織若還沒有能力說清楚「代理可以做什麼、不能做什麼」，引入宣告式框架不會自動解決治理問題，反而可能製造一種「已治理」的錯覺——這是我認為業界在鼓吹宣告式框架時，最常被忽略的風險。

第三，我判斷 Kubernetes 式調和迴圈能被移植進 AI Agent 治理層，關鍵前提是「狀態可被完整枚舉與比對」。容器編排的期望狀態（副本數、資源配額）本質上是有限、離散、易於形式化的；但 AI Agent 的「期望行為」往往涉及語意層面的判斷（例如「回應應合乎品牌語氣」），這類期望難以化約成 Context Kubernetes 式的 YAML manifest。這意味著宣告式協調迴圈在 AI Agent 領域的適用邊界，很可能就停留在「資源與權限治理」這類結構化子問題，而不會像在容器編排領域那樣，擴張成通用的執行控制範式——這是我對宣告式 DSL 倡議者過度樂觀敘事的一個限定性修正。

第四，我主張 HN 與 V2EX 社群對宣告式抽象層必要性的質疑，不該被當成雜訊過濾掉，而應被納入企業選型的正式決策矩陣——換句話說，「這個宣告式抽象層是否只是把命令式的複雜度移到了另一個地方、而非真正消除複雜度」，應該成為架構評審會議的標準提問，而不是留給社群論壇的情緒發洩。

結論

本文以三角佐證法系統性驗證，企業級多代理 LLM 編排系統的架構抉擇，應回歸「宣告式協調迴圈」與「命令式逐步排程」這兩種源自控制理論與分散式系統實務的控制範式之爭，而非停留在框架流行度的表層比較。研究問題「企業多代理編排的控制範式如何分類、如何指導架構決策」的答案是：兩種範式並非互斥對立，而是依抽象層級——基礎設施/知識治理層傾向宣告式、推理/工具呼叫層傾向命令式、協定層則呈現宣告式能力發現與命令式方法呼叫並存的分層混合設計——分工並存；企業應以所需控制力與確定性程度，而非單一框架的流行度或供應商生態，作為核心選型判準。

本研究的限制主要有二：一是證據時間窗口集中於 2025-2026 年新興論文與企業部落格，長期生產環境實證數據仍待累積；二是本文分類學聚焦於架構控制範式本身，未涵蓋成本、延遲、安全漏洞等其他選型維度的系統性比較（僅在實踐建議中援引部分成本數據作為佐證）。後續研究可朝兩個方向推進：其一，持續追蹤 Context Kubernetes 式治理模式與 MCP/A2A 協定融合的長期演化，特別是協定層是否真如 V2EX 討論所預示走向合併或淘汰；其二，針對「宣告式抽象層的組織治理成熟度前提」（本文原創論點二）進行實證研究，量化不同治理成熟度組織導入宣告式框架後的實際治理效果差異，而非僅停留在架構設計層面的理論推演。
