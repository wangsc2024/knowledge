偵察提案：XiaoDuoYa/codex-with-chatgpt

專案是什麼

專案讓 ChatGPT 網頁版（既有訂閱額度）負責規劃，Codex CLI 只負責執行，藉此把「規劃/審閱」耗用的 token 從付費 API 移到閒置的網頁配額。核心是一個唯讀 MCP bridge：loopback-only HTTP、OAuth 2.1+PKCE、5 分鐘 TTL 的一次性配對碼，只暴露 8 個唯讀工具（inspect/list/read/search/git status·diff/test status/exec summary）；控制面則用 [C2C] 結構化狀態訊息走 INIT→PLAN→EXECUTED→REVIEW→DONE，不夾帶檔案內容本體，細節靠 MCP 拉取。Skill 安裝到 ~/.codex/skills/，屬個人剛發布專案，實際採用規模待查證。

對本系統的借鑑點

  1. 讀寫分權子集缺口：實讀 examples/plugins/workflow-composer/allowlist.mjs 確認，目前 buildWorkflowAllowlist() 只做 authority 黑名單（denies commander.／resource.lifecycle.），其餘能力全數放行給 llm-codex/agent-server.mjs 的 codex.agent_loop。對照該專案把外部規劃者限定在唯讀工具集的做法，可為「規劃階段」新增一個只放行 .list／.read／*.status 後綴的子集，執行階段才解鎖寫入，降低低信任規劃者誤觸寫入的風險面。
  2. 摘要式狀態協定：實讀 examples/plugins/llm-router/index.mjs 確認其 attempts[] 已是「只記 provider/status/duration 摘要、不夾帶 payload」的思路。C2C 的 PLAN/REVIEW 狀態語彙可搬到 allowlist.mjs 註解提及的「commander. 人工核准閘」上，讓 todoist-team 自動任務等待核准時有標準狀態可查，而非現有單純 pending/skipped/failed。

建議行動

低風險：在 allowlist.mjs 旁新增 buildReadOnlyAllowlist()（僅過濾 capability id 符合唯讀後綴），不動既有函式，先寫測試驗證過濾邏輯，不涉及 CLI/OAuth。

需人工決策：是否真的引入外部 ChatGPT 網頁規劃者——這牽涉 OAuth 2.1＋Cloudflare Tunnel 的對外曝露面，會改變 Cordis 目前「全走 CLI/API provider」的信任模型，需權衡省 token 與新增攻擊面的取捨。
