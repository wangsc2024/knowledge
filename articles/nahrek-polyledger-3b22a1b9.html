偵察提案：nahrek/polyledger

專案是什麼

一個可續傳（resumable）的 Polymarket 索引器：整合 CLOB API（市場元資料）、Envio HyperSync（Polygon 鏈上事件）與 Gamma API（缺漏代幣回填），落地成單檔案 DuckDB。核心機制是「資料列與 checkpoint 游標同一交易提交」＋以 (transaction_hash, log_index) 為唯一鍵搭配 ON CONFLICT DO NOTHING，使重複執行同區間天然冪等；並用共享 token-bucket 限流（8 RPS、逾時 30s、含 jitter 的指數退避）統一管理多來源 REST 請求。成熟度：具備 V1/V2 雙版本事件解碼與鏈重組防護，屬生產級設計而非原型。

對本系統的借鑑點

  1. 去重機制：本檔（team-scout/index.mjs:72）目前用 prior.find(repoToken 比對 || includes 子字串) 對 proposal.list 拉回的整份陣列線性掃描比對，屬應用層手刻的字串比對，這正是先前 podcast 120 天固定候選集永久鎖死（memory: cordis-podcast-fixed-universe-history-trap）同一類根因——去重規則寫死、無資料層保證。polyledger 的「唯一鍵 + ON CONFLICT DO NOTHING」把去重下沉到儲存層，值得作為 state/team/proposals.json 類歷史檔未來的參考模式。
  2. 整檔讀寫：proposal-staging/index.mjs:27 用 readJsonOrNull(stateFile()) 整檔讀入、記憶體改、經 state-file.mjs 的 withStateFile 原子改寫回。隨歷史累積會趨向 O(n)；polyledger 每 50,000 筆做批次 checkpoint flush 的策略可作為檔案增長後的寫入節流參考。

建議行動

  • 低風險：先把 team-scout/index.mjs 現有的線性掃描去重抽成獨立、可單元測試的函式，補上迴歸測試，不動儲存引擎，為後續替換鋪路。
  • 需人工決策：是否引入嵌入式 DB（如 duckdb/better-sqlite3 的 Node 綁定）取代 state/team/*.json。polyledger 本身是 Python 專案，借鑑的是架構模式而非可直接搬移的程式碼；且 Node 原生模組在本機 Windows 環境的預編譯相容性待查證（此機器已知有原生工具鏈不穩定的前例），加上須重新檢視 state-file.mjs 既有的跨行程鎖語意是否要一併調整，影響範圍較大，不建議直接執行，僅列為選項。
