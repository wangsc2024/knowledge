偵察提案：nateherkai/scroll-craft

專案是什麼

Claude Code Skill（隸屬 nateherk-design plugin），產出「捲動驅動」網頁設計。內建 interview→grammar→score→build→verify 五階段流程，SKILL.md 僅留骨架，8 份 references/*.md（文法、情感曲線、裝置、驗證規範等）按需載入。已達 1000+ stars、164 forks，MIT 授權，8 次提交穩定迭代，文件齊全。

對本系統的借鑑點

  • verify.md 機器自動走查：build 後用 headless browser 逐格檢查死滾動、對比度、編碼失敗，非僅人工判讀。對應 kb-site-publish 發布流程——目前靠 [[port-3000-dual-listener-trap]] 教訓手動繞行驗證，可加一道自動化 sanity walk 抓連線/編碼異常。
  • references/ 模組化拆分：SKILL.md 只留骨架，細節分散到按需載入子文件。對應目前偏長的 pingtung-policy-expert（15 大施政領域）、knowledge-query 等 skill，可仿此拆分降低單次載入負擔。
  • score 關卡前移至 build 之前：先評分才決定做不做，而非做完才評。對應 team-review 剛加上的「通知評分行」（commit b01d386）——現行是評分伴隨輸出，可借鏡把評分前移為門檻，未達分不進入通知產出。
  • 固定「文法」選單＋強制唯一簽名效果：以有限分類取代自由生成，並強制每次輸出至少一項獨特元素。對應 team-rss-news 剛提高的摘要品質門檻（commit 02ff4ad）——可借鏡固定格式選單降低摘要品質隨機落差。

建議行動

低風險可先做：把過長 SKILL.md（如 pingtung-policy-expert）拆成 references/ 子文件；為 kb-site-publish 發布流程加一道自動化走查腳本。

需人工決策：是否把 score 門檻前移到 team-review 的 build 之前、是否為 team-rss-news 摘要導入固定格式分類——兩者牽動既有 prompt 與品質門檻設計，需評估後再改。
