偵察提案：ashemag/human-atlas

專案是什麼

開源 3D 人體解剖瀏覽器，載入 2,234 個可選取的 BodyParts3D 網格，依「系統分層」（如骨骼、肌肉等解剖系統）分組顯示，並提供搜尋定位部位。內部索引與渲染機制素材未揭露，待查證；就描述看屬功能完整但單一用途的瀏覽器，非通用框架。

對本系統的借鑑點

  • 已讀取 examples/plugins/resource-catalog/lib.mjs：filterResources()（第260–276行）目前只有 kinds（plugin/capability/skill/lens）與純子字串 query 兩個篩選維度，並未把每筆資源都具備的 sideEffects（none/network/filesystem/process/llm/external，AGENTS.md 訂義六級，第30/67/176/206/229/249行皆有此欄位）當成可篩選分層。human-atlas 用「系統分層」在龐大目錄中切換可見範圍，這正是「拿既有分類欄位做二次分層瀏覽」——本系統資料已具備，只是 resource.catalog.list/match 未暴露成 facet。
  • filterResources 的 query 是純 .includes()（無排序），真正的排序/降權邏輯在 matchCatalog（第284–307行）用 matchResources+compareMatches 實現，兩者目前分屬 list 與 match 兩支能力。human-atlas 把「選取瀏覽」與「搜尋」整合於同一介面，提示 list 若供人工瀏覽，值得比照補上簡單排序而非維持插入序。

建議行動

  • 低風險可先做：在 filterResources 新增可選 sideEffects 陣列參數（比照既有 kinds 寫法），未帶入時行為不變、向後相容；同步補上 resource.catalog.list input schema。
  • 需人工決策：是否要為 catalog 建立類似 human-atlas 的視覺化瀏覽介面（目前僅 CLI JSON 輸出）——牽涉新增前端面向，超出目前 manifest-only runtime 的既定範圍，需先確認產品方向。
