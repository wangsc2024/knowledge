Skill 審查：forge_v2 生成 Skill 的兩種缺陷模式（2026-08-09）

Skill審查品質優化Forge-建議-ci-auto-triggers-disabled-days-forge_v2skill_audit

審查對象

  • Forge-建議-ci-auto-triggers-disabled-days-（P1：工具已存在但未接線）
  • Forge-建議-daily-success-rate-觸發-critical-（P1：功能已被既有 Skill 完整覆蓋）

選定依據：state/auto-task-skill_audit-precomputed.json 選出的 2 個「從未審查」候選，皆屬 has_use_when=false / tools_count=0 / cache_ttl_null 的 forge_v2 自動生成空殼（無 YAML frontmatter，僅有敘述性 Markdown）。

發現：forge_v2 生成物有兩種截然不同的缺陷模式

模式 A（工具已存在但無人呼叫）— ci-auto-triggers-disabled-days

tools/ci_trigger_guard.py 是完整、有測試（TOOL_INDEX ✓）的實作：解析 .github/workflows/ci.yml 的 on: 區塊，計算 push/PR 自動觸發被禁用的天數，含 kill switch DDP_CI_TRIGGER_GUARD=off。但從未被任何 Skill / PS1 / 排程呼叫。2026-08-09 實測：alert=true, days_disabled=29（自 2026-07-11 停用），是一筆真實、未消費的告警。

同批生成的 tools/forge_ci_auto_triggers_disabled_days.py 只回傳 {"status": "ok"}（空 TODO stub），與 ci_trigger_guard.py 重複，是干擾項而非實作。

修復：不重新實作邏輯，改寫 SKILL.md 為薄封裝——呼叫 uv run python -m tools.ci_trigger_guard --write → 判讀 alert → alert=true 時走 ntfy-notify + backlog。補齊 frontmatter（name/description含Use when/allowed-tools/cache-ttl/triggers）後 validate_config.py --check-skills 從 0/100 → 100/100，並已同步 skills/SKILL_INDEX.md（# 113d）。

模式 B（功能已被既有 Skill 完整覆蓋，屬純重複）— daily-success-rate-觸發-critical

skills/system-success-rate-improvement/SKILL.md 早已存在，triggers 含 daily_success_rate、success_rate_improvement，處理邏輯已涵蓋 critical/warning 兩種嚴重度（讀 context/system-insight.json 的 alert_id/description，非按嚴重度分裂成不同 Skill）。forge_v2 又生成了 Forge-建議-daily-success-rate-觸發-critical- 與 -warning-強 兩個空殼，是 100% 功能重複，不是覆蓋度缺口。

修復：判定為 YAGNI，未補全 frontmatter（避免製造與既有 Skill 觸發詞衝突的重複路由入口），改寫 backlog P1 建議人工依 skills/CLAUDE.md「Skill 退役檢查清單」流程退役（本身未被 SKILL_INDEX 收錄，無需移除索引項）。

通用結論

Skill 審查遇到 forge_v2 生成的空殼 SKILL.md 時，不能只套用「補 frontmatter 讓它變合法」的機械修法——必須先查四索引（tools/TOOL_INDEX.md、skills/SKILL_INDEX.md）確認是否已有等價實作：

  • 若底層工具存在但未接線 → 補 Skill 作為薄封裝（不重複實作邏輯）
  • 若功能已被其他 Skill 完整覆蓋 → 判定重複，寫 backlog 建議退役，不強行完成，避免製造觸發詞衝突

此為既有「外部市集技能命名衝突觀測」教訓的內部版本：同名/近義觸發詞的重複 Skill 會造成路由歧義。
