日期：2026-08-02

任務：insight_briefing

狀態：計畫已輸出（plan_ready），待人工執行

---

摘要

本簡報聚焦 DDP 在 OTel export 試辦（config/otel-config.yaml enabled: false）轉正前的屬性層敏感值防線缺口。對照 pydantic/logfire 官方 scrubbing 機制（預設 17 組 regex + ScrubbingOptions 擴充 + OTel Collector 三 processor 鏈），現行 tools/openllmetry_bootstrap.py 的 _FileSpanExporter 仍以 dict(span.attributes or {}) 明文寫入 JSONL，與既有 instrumentation.trace_content: false 內容層防線形成單層防護。docs/plans/github-scout-20260727-otel-attribute-scrubbing.md 已輸出六步驟實作契約（風險 low、零生產影響），本輪萃取 6 項洞察、套用 3 組思考透鏡，建議優先人工合入 scrubbing 後再審核 OTel 試辦轉正。

---

關鍵洞見

1. 雙層防線模型：內容層 ≠ 屬性層

DDP 現以 instrumentation.trace_content: false 阻擋完整 prompt/completion 內容落地（見 config/otel-config.yaml L21-23），但 instrumentor 仍可能把 api_key、authorization 等寫入 span attributes。logfire 預設對 password、secret、api_key、jwt 等 17 組 pattern 做值層 redaction（官方 scrubbing 文件）。證據：openllmetry_bootstrap.py L63 無任何遮罩邏輯。

2. logfire 刻意對 LLM message 屬性停用 scrubbing

gen_ai.input.messages、gen_ai.output.messages、pydantic_ai.all_messages 等屬性不經 regex scrubbing，因假陽性（對話中出現 "password" 字樣）與偵測失效（敏感資料無關鍵字）。官方建議 instrument_pydantic_ai(include_content=False) 排除內容而非依賴 scrubbing。對 DDP 意味：即使實作屬性鍵 scrubbing，仍須維持 trace_content: false 作為 LLM 內容防線。

3. OTel Collector 提供語言無關的進階 scrubbing 鏈

logfire PR #1195（2025-06-27 merged）新增 Collector 指南：processor 順序為 attributes（鍵更新）→ redaction（regex 遮罩值）→ transform（OTTL 條件邏輯，如僅 5xx 時遮罩信用卡號）。應用端設 send_to_logfire=False 經本地 Collector 再匯出。DDP 若以 file exporter 為主，等價邏輯應落在 _FileSpanExporter.export() 前。

4. 計畫檔已具體化且風險極低

docs/plans/github-scout-20260727-otel-attribute-scrubbing.md 定義：DEFAULT_SCRUB_KEY_PATTERNS = [key, token, secret, password, authorization]、config/otel-config.yaml 新增 attribute_scrubbing.key_patterns、TestFileSpanExporterScrubbing 測試類。enabled: false 下合入零生產行為影響。未自動落實原因：github_scout step9 允許範圍不含 tools/*.py。

5. 與 post_tool_logger / eval 路徑的交叉風險

improvement-backlog 多筆條目指向 post_tool_logger 補 input_keys 解鎖 ToolParameterAccuracyEvaluator；另有參數值記錄需脫敏規則（2026-07-18）。屬性層 scrubbing 硬化應與 jsonl_to_otel_span 轉發路徑對齊，避免 JSONL→OTel 雙寫時一條有 scrub、一條無 scrub 的不一致信任邊界。

6. 訊息模板 vs f-string 的 scrubbing 盲區

logfire 文件強調：僅 scrub 欄位值，不 scrub 完整 message 字串；logfire.info('User: ' + str(user)) 會洩漏 password，而模板參數化則安全。DDP structured logging 若未來在 span event/message 層記錄自由格式字串，屬性 scrubbing 不足以覆蓋。

透鏡選擇

| 透鏡 | 角色 | 選擇理由 |

框架化建議

Altman 視角：計畫檔已是可 ship 的最小增量——預設 pattern 列表 + 單元測試，不等待完美 OTTL 條件邏輯。先合入 enabled=false 路徑的防線，試辦轉正時自動生效；反饋閉環靠 pytest 而非生產事故。

Jensen 視角：scrubbing 不是單點修補，是 exporter 層的「加速計算護城河」——在寫入 JSONL 前 offload 遮罩邏輯，保持應用 lean。三層對齊：SDK 內容開關 → exporter 屬性 scrub → 未來 Collector 進階規則。

Taleb 反模式檢查（adversarial）：

  • ❌ 「enabled=false 所以不急」= 火雞問題，轉正日即暴露
  • ❌ 只靠 trace_content=false = 中間地帶，屬性鍵洩密無後果
  • ✅ 槓鈴：低成本預先硬化（low risk patch）+ 維持試辦關閉直到人工審核

透鏡盲區自陳

  • Altman 視角可能低估合規審計對「已部署未啟用程式碼」的審查要求
  • Jensen 全棧敘事未量化 scrub regex 對 export 延遲的影響（logfire 原始碼註記 BoundedAttributes 有效能顧慮）
  • Taleb 視角對「人工審核」過度悲觀——DDP 治理鏈（plan_ready + human_review_required）本身即 skin in the game 設計
