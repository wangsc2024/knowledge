偵察提案：chrisgreg/boop

專案是什麼

Boop 是一個極簡的自架開發者通知收件匣：單一 Go binary + 一個 SQLite 檔 + 一個 Docker container，MIT 授權。應用程式用 API key 把事件 POST 進去，伺服器做遮罩（redact）後存入 SQLite，並用「fingerprint」把同類事件歸併成一列，記錄發生次數與首次／最後一次出現時間，再直接推到 Apple APNs（無 hosted relay、無帳號系統、無遙測）。事件也能一鍵匯出成含 exception／environment／stack trace／context 的 Markdown，方便貼進 Claude/ChatGPT 除錯。成熟度：功能單一、部署極輕，屬「小而完整」的工具，非框架。

對本系統的借鑑點

已核實現有系統缺口（讀取 examples/plugins/digest-history/index.mjs、notify-ntfy/plugin.json、notify-agentflow/plugin.json 及 state/ 下各記錄檔確認）：

  1. Fingerprint 歸併＋計數／首末時間 — 目前 digest-history 只做「3 天內同 key 標題去重」的快取，防止重複推播，但不記錄發生次數、也不是可查詢的事件庫。可比照 boop 的 schema，把 digest-history 升級為存 fingerprint / count / first_seen / last_seen 的輕量事件記錄，讓「同一告警重複觸發了幾次」變成可查資訊，而非只是被吃掉。
  2. 收件匣作為推播前置層 — notify.send（notify-ntfy）與 notify.agentflow 目前都是即發即忘：送出就結束，沒有持久化狀態，也沒有已讀/未讀。像 team-health-watch 或 quality-gate 每日輪替失敗這類會重複觸發的告警，容易對外洗版式重複推播。可在這兩個 capability 前插一層「先寫本地事件記錄、依 fingerprint 決定是否真的要外推」的判斷，降低雜訊。
  3. 結構化 Markdown 匯出格式 — boop 把每則事件固定拆成 exception/environment/stack trace/context 四段，方便直接貼給 LLM 除錯。目前 notify.agentflow 的訊息內容是自由格式文字，可借用這個固定欄位骨架，讓告警訊息更適合被下一輪 agent 直接消化。

建議行動

  • 低風險可先做：擴充 digest-history 的資料結構（純 filesystem sideEffect，不涉及 external，不改動現有 invoke 介面），加入 fingerprint／count／first_seen／last_seen 欄位，把它從「防重複快取」升級為「可查詢的輕量事件記錄」。
  • 需人工決策：是否要仿 boop 新增一個獨立的「收件匣」plugin（SQLite 持久化 + 查詢 capability + 已讀狀態），這屬於新增持久服務的架構決策；若進一步要做行動裝置推播（類比 APNs），會落在 sideEffects=external 範疇，依 AGENTS.md 規則須先人工確認才能執行，不可由模型自行決定導入。
