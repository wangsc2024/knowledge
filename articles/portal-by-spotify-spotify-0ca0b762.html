偵察提案：Portal by Spotify（spotify/portal-ai-plugins・shunt 插件）

專案是什麼

Spotify 開源的 Claude Code 插件庫（Apache-2.0，v0.2.0）。核心是 shunt 插件：用 PreToolUse hooks（plugins/shunt/hooks/hooks.json）攔截 Read／Bash 呼叫，check-file-size 對超過 350 行的讀取轉發給 bulk-reader skill，改由更便宜的模型（Gemini 2.5 Flash）讀完整檔、只回答案，原文從不進主 agent 的 context。Spotify 工程部落格報告平均節省 90% token；repo 內附 evals/benchmarks.json 佐證，非純行銷宣稱。（已查證：.claude-plugin/plugin.json、hooks/hooks.json、skills/bulk-reader/SKILL.md 實際內容與此一致。）

對本系統的借鑑點

  1. examples/plugins/llm-claude/plugin.json 的 claude.agent_loop 能力文件明講「不使用 --bare」，代價是「本迴圈會載入專案自身設定」——即目標專案的 .mcp.json／hooks／skills／CLAUDE.md 都會被 CLI 讀取套用。查證：Cordis repo 本身沒有任何 hooks.json 或 .claude-plugin（.claude/ 下僅 worktrees，非插件設定）。代表凡是用 claude.agent_loop 對某個 repo 跑多步讀檔分析（如 specs/headroom-insight/ 那次要讀 6716 行 content_router.py、43280 行 headroom-core），大檔全文都全額吃進 context，沒有任何攔截層——正是 shunt 要解決的問題。
  2. 落地面在「目標 repo」而非 Cordis 自身：只要在被分析的外部（或自身）repo 放一份仿 hooks.json 的 PreToolUse 設定＋等價 bulk-reader skill，claude.agent_loop 呼叫時 cwd 指到該 repo，CLI 會自動套用，Cordis 端零程式改動。
  3. 「便宜模型代讀摘要、原文不進主線」與 Cordis 剛定稿的 specs/llm-reducer/spec.md（機械歸約先於重模型呼叫）是同一治理精神的不同作用層——一個管「材料聚合」、一個管「單檔讀取」，互補不重疊，不與既有機制衝突。

建議行動

低風險：下次用 claude.agent_loop 對大型 repo 做深度分析前，先在該外部 repo 手動放一份 shunt 設定做一次前後 token 用量 A/B 量測，驗證實際節省幅度（不預設可轉嫁 90%，待查證）。

需人工決策：是否把這份 hooks 設定收進 Cordis 的範例目錄作為「輔助工具」而非核心插件——因為它只在「目標是某 repo 且用 claude.agent_loop 分析大檔」情境下有價值；以及摘要模型（Gemini Flash 或等價物）的 API 金鑰與外部成本由誰承擔，屬於需核准的外部依賴。
