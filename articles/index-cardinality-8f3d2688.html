資料庫 index 的 cardinality 如何影響選擇

技術深度研究daily-agent

主筆說明

我以 craft-clear、craft-rigor 視角撰文，基於公開言論與研究材料推斷，非本人觀點。選角理由：craft-clear清晰技藝視角; craft-rigor嚴謹工程視角

摘要

本研究報告旨在深入探討資料庫索引中的「基數」（Cardinality）概念，及其如何決定資料庫優化器（Query Optimizer）在執行計畫選擇上的關鍵行為。在現代資料庫架構中，索引的效能並非僅取決於索引是否存在，更核心的因素在於該索引所提供的「選擇性」（Selectivity）。本研究的核心問題在於：為何某些索引在理論上存在卻無法被優化器採用？以及在設計複合索引時，基數的排序如何直接影響查詢的執行速度與資源消耗？

為了探討上述問題，本研究採用了多維度的分析方法。首先，透過理論對比分析 Cardinality 與 Selectivity 的數學關係，區分高、中、低基數欄位的特性。參考資料指出，Cardinality 代表資料集中不同值的數量，而 Selectivity 則是條件過濾後返回結果佔總數的比例，兩者關係可簡化為 Cardinality = Selectivity × 總行數（https://unanswered.io/guide/selectivity-vs-cardinality）。研究進一步分析了 B+ Tree 結構在處理不同基數數據時的節點分割與查找邏輯，藉此理解為何低選擇性的索引（如布林值或狀態欄位）常被優化器忽略，轉而選擇全表掃描（Full Table Scan）（https://medium.com/@CodersWorld99/index-cardinality-explained-the-metric-most-developers-misunderstand-a688923122d6）。

在實務操作層面，本研究檢視了複合索引（Composite Index）的設計原則。根據多項技術文獻，將高基數欄位置於索引的最前端是優化查詢的關鍵策略，因為這能讓資料庫引擎在查詢早期階段就排除掉大部分不相關的資料（https://uptimerobot.com/knowledge-hub/observability/cardinality-in-databases-guide/）。此外，研究亦強調了「左前綴原則」與「等值過濾優先於範圍過濾」的設計邏輯，這些原則在實務中對於避免索引失效至關重要（https://oneuptime.com/blog/post/2026-03-31-mysql-composite-index/view；https://www.sqlservercentral.com/forums/topic/composite-indexes-higher-cardinality-first-or-lowest）。

主要的發現顯示，開發者最常遇到的效能瓶頸源於「統計資訊過時」與「數據分佈偏斜」。當資料庫內的統計資訊與實際數據分布脫節時，優化器可能會產生錯誤的行數預估（Row Estimation），導致選擇次優的執行計畫（https://runebook.dev/en/docs/postgresql/row-estimation-examples）。為了驗證並修正這些問題，研究強調必須利用 EXPLAIN ANALYZE 指令來對比預估行數與實際執行行數，並透過 ANALYZE 指令定期更新統計數據（https://www.postgresql.org/docs/current/sql.explain.html）。

最後，在研究的取捨與結論部分，本報告指出雖然高基數優先是通用最佳實踐，但在處理高度相關的欄位（如城市與郵遞區號）或複雜表達式時，單純依賴基數可能不足以確保最佳效能。開發者必須在「索引的覆蓋範圍」、「維護成本」與「查詢選擇性」之間取得平衡。透過對不同場景的深入剖析，本研究提供了一套從理論理解到實務驗證的完整框架，幫助開發者在複雜的資料庫環境中做出更精準的索引選擇。

關鍵詞

本章節旨在釐清資料庫效能優化的核心指標，透過定義與實務應用，解析 Cardinality 如何驅動查詢優化器的決策邏輯。

核心關鍵詞與脈絡解析

Cardinality（基數）：指資料集中唯一值的數量。在資料庫設計中，它是衡量索引有效性的基礎指標，區分為高基數（如 GUID、電子郵件）、中基數（如姓名、郵遞區號）與低基數（如布林值、狀態碼）。理解其分布對於判斷索引是否會被優化器忽略至關重要，相關深入解析可參考 https://developer.couchbase.com/tutorial-understanding-cardinality-and-selectivity/。

Selectivity（選擇性）：衡量特定條件過濾後返回結果佔總數的比例（0 到 1 之間）。雖然與基數密切相關，但優化器在選擇執行計畫時，更偏向於選擇性較高的索引，因為這能更有效地減少掃描範圍。兩者的數學關係與差異可詳見 https://unanswered.io/guide/selectivityvs-cardinality。

Low Selectivity Trap（低選擇性陷阱）：這是開發者最常誤解的效能瓶頸。當索引欄位的選擇性過低（例如在包含大量資料的表中僅過濾出 50% 的記錄）時，資料庫引擎往往會判定全表掃描（Full Table Scan）比索引掃描更高效。此現象在 https://medium.com/@CodersWorld99/index-cardinality-explained-the-metric-most-developers-misunderstand-a688923122d6 中有深入探討。

Composite Index Ordering（複合索引順序）：在設計多欄位索引時，欄位的排列順序直接影響查詢效率。最佳實踐通常是將高基數（High Cardinality）欄位優先放置，以便在查詢早期階段就排除大部分不相關的資料。相關實務建議可見於 https://oneuptime.com/blog/post/2026-03-31-mysql-composite-index/view 以及 https://uptimerobot.com/knowledge-hub/observability/cardinality-in-databases-guide/。

Row Estimation & Statistics（行數預估與統計資訊）：查詢規劃器依賴統計資訊來預估 Cardinality。若數據分布極度偏斜或統計資訊過時，預估誤差將導致錯誤的執行計畫。開發者應透過 ANALYZE 指令更新統計，並利用 EXPLAIN ANALYZE 工具來對比預估行數與實際執行結果，相關技術細節可參考 https://runebook.dev/en/docs/postgresql/row-estimation-examples 與 https://www.postgresql.org/docs/current/sql-explain.html。

B+ Tree & Index Selection（B+ Tree 與索引選擇）：大多數關係型資料庫使用 B+ Tree 結構。理解 B+ Tree 如何根據基數進行節點分割與查找，是深入優化查詢效能的基礎。相關原理可參考 https://planetscale.com/learn/courses/mysql-for-developers/indexes/index-selectivity。

引言

在現代資訊架構中，資料庫效能的優化往往是決定應用程式能否在極大規模數據下維持穩定運行的關鍵因素。當開發者在面對日益增長的資料量時，最常遇到的挑戰之一便是查詢速度的下降。雖然建立索引（Index）是解決此問題的標準手段，但許多工程師常陷入一個常見的誤區：認為只要在查詢條件中出現的欄位上建立索引，資料庫就能自動加速查詢。然而，實務經驗與底層原理告訴我們，索引的有效性並非僅取決於「有沒有」，更核心的關鍵在於「索引的選擇性（Selectivity）」以及與之高度相關的「基數（Cardinality）」。

問題界定：索引失效與預估偏差的技術核心

本研究的核心問題在於：為什麼某些索引在預期中應該發揮作用，但在實際執行計畫中卻被資料庫優化器（Query Optimizer）忽略？這往往與 Cardinality 的概念直接掛鉤。Cardinality 指的是資料集中不同值的數量（Unique Values），而 Selectivity 則是條件過濾後返回結果佔總數的比例。兩者之間的數學關係——Cardinality = Selectivity × 總行數——決定了資料庫引擎在處理查詢時的決策邏輯。

當我們處理低 Cardinality 的欄位（例如布林值、性別或狀態標記）時，即使建立了索引，由於這些欄位返回的資料比例過高，資料庫引擎可能會判定「全表掃描（Full Table Scan）」比「索引掃描（Index Scan）」更具成本效益。這種現象在複雜的生產環境中極為常見，往往導致開發者在不斷增加索引卻無法改善效能的困境中掙扎。此外，當數據分布極度偏斜（Skewed Distribution）或統計資訊過時時，資料庫規劃器對 Cardinality 的預估可能出現嚴重偏差，進而選擇錯誤的執行計畫。這不僅是單純的索引設計問題，更涉及對資料分布特性的深度理解與統計維護。

為何此刻值得關注：從開發到運維的效能瓶頸

在雲端原生架構與微服務普及的現狀下，資料庫的效能優化已從「可選的優化」轉變為「生存的基礎」。隨著數據規模進入千萬甚至億級，微小的查詢延遲會隨著併發數的增加而產生連鎖反應，最終導致系統崩潰。

目前，許多企業面臨著「索引爆炸」的問題——為了追求速度，盲目地在多個欄位上建立索引，這不僅增加了寫入操作的負擔（Overhead），更讓優化器在選擇最佳路徑時變得複雜且容易出錯。理解 Cardinality 如何影響選擇，對於建構高效的複合索引（Composite Index）至關重要。例如，在設計多欄位索引時，正確的欄位順序（如將高 Cardinality 欄位置於前端）能顯著提升過濾效率。若缺乏對此概念的掌握，開發者可能在錯誤的順序上浪費資源。

此外，隨著 PostgreSQL 等主流資料庫在複雜查詢處理上的應用日益廣泛，深入了解 EXPLAIN ANALYZE 工具如何對 Cardinality 進行預估，以及如何透過 ANALYZE 指令更新統計資訊，已成為資深後端工程師與資料庫管理員的必備技能。在數據變動頻繁的動態環境中，掌握這些細微的技術差異，是確保系統高可用性的關鍵。

文獻回顧

在資料庫系統架構與查詢優化領域中，理解「基數」（Cardinality）與「選擇性」（Selectivity）的關係是建構高效能查詢計畫的核心基礎。透過對既有學術與技術文獻的綜述，本章將深入探討這些指標如何影響資料庫優化器的決策機制，並分析在不同場景下的索引設計策略。

Cardinality 與 Selectivity 的理論基礎與定義差異

在資料庫工程實務中，開發者常將 Cardinality 與 Selectivity 混為一談，然而，兩者雖然高度相關，但在數學定義與優化器應用上存在顯著差異。根據技術文獻的定義，Cardinality 指的是資料集中不同值的數量，即一個欄位中唯一值的總數。例如，在一個包含一百萬名用戶的資料表中，若「使用者 ID」欄位的每一個值都是唯一的，則該欄位的基數極高；相反地，若「性別」欄位僅包含「男」、「女」兩個值，則其基數極低。

與此相對，Selectivity（選擇性）則是衡量一個查詢條件能過濾掉多少資料的比例，通常以 0 到 1 之間的數值表示。根據 https://unanswered.io/guide/selectivity-vs-cardinality 的說明，選擇性衡量的是條件過濾後返回結果佔總數的比例。這意味著，雖然 Cardinality 是靜態的屬性（描述數據本身的分布），但 Selectivity 往往是動態的（取決於特定的查詢條件）。兩者的數學關係可概括為：Cardinality = Selectivity × 總行數。

在實際的資料庫操作中，優化器更傾向於利用 Selectivity 來評估執行計畫的成本。一個高品質的索引應該具備高選擇性，意即它能夠精準地將搜尋範圍縮小到極少數的記錄。例如，在 https://developer.couchbase.com/tutorial-understanding-cardinality-and-selectivity/ 的研究中，作者將基數分為高、中、低三種等級：

  1. 高基數（High Cardinality）：如 GUID、電子郵件、使用者名稱。這些欄位具有高度唯一性，索引能極大提升查詢效率。
  2. 中基數（Medium Cardinality）：如姓名、郵遞區號。這些欄位雖然不唯一，但仍能提供一定的過濾能力。
  3. 低基數（Low Cardinality）：如布林值（Boolean）、狀態碼（Status）、性別。在這些欄位上單獨建立索引往往收效甚微，因為數據庫引擎可能會判定索引掃描的成本高於全表掃描（Full Table Scan）。

索引選擇性對查詢計畫的影響與效能陷阱

資料庫引擎（如 MySQL、PostgreSQL）在處理查詢時，核心目標是最小化 I/O 操作。為了達成此目標，優化器會預估不同索引的成本。這正是「低選擇性陷阱」發生的原因。許多開發者誤以為只要為欄位建立索引，查詢就會變快，但事實上，如果一個索引條件返回了資料庫中很大比例的記錄（例如在一個擁有千萬筆資料的表中，查詢「狀態為 active」的記錄，而 active 佔了 90%），優化器往往會選擇忽略該索引。

根據 https://medium.com/@CodersWorld99/index-cardinality-explained-the-metric-most-developers-misunderstand-a688923122d6 的分析，理解這一點對於避免效能瓶頸至關重要。當選擇性低於某個閾值時，資料庫認為從索引中讀取位址再回表（Bookmark Lookup）獲取資料的成本，高於直接掃描整張表。這也是為什麼在處理低基數欄位時，單獨建立索引往往無效的原因。

此外，B+ Tree 作為大多數關聯式資料庫的索引基礎結構，其效能高度依賴於節點的分割與查找過程。在 https://planetscale.com/learn/courses/mysql-for-developers/indexes/index-selectivity 中提到，理解索引如何根據基數進行物理組織，是優化複雜查詢的基礎。當基數高時，B+ Tree 的分支結構能更有效地將搜尋範圍縮小，減少讀取頁數。若基數過低，則索引節點可能包含大量重複的鍵值，導致樹狀結構的優勢無法發揮。

複合索引（Composite Index）的設計與欄位順序策略

當單一欄位的基數不足以滿足查詢需求時，開發者通常會採用複合索引。然而，複合索引的效能極度依賴於欄位的排列順序。在多欄位索引中，「左前綴原則」是基本準則，即查詢必須包含索引的最左側欄位才能觸發索引。但更深層的優化在於如何排列這些欄位。

根據 https://oneuptime.com/blog/post/2026-03-31-mysql-composite-index/view 的實務建議，建立複合索引時應優先考慮「高基數優先」原則。將高基數（高選擇性）的欄位放在索引的前面，可以讓資料庫引擎在查詢的早期階段就排除掉大部分不符合條件的資料，從而大幅減少後續處理的數據量。例如，若建立一個包含「城市」與「使用者 ID」的複合索引，將「使用者 ID」放在前面通常比將「城市」放在前面更有效，因為 ID 的唯一性更高。

在處理複雜查詢時，還有一項關鍵原則：將「等值過濾」的欄位放在「範圍過濾」的欄位之前。這是因為範圍查詢（如 > 或 <）會導致索引在該點之後的數據無法被有效利用。根據 https://www.sqlservercentral.com/forums/topic/composite-indexes-higher-cardinality-first-or-lowest 的討論，這種順序安排能確保優化器能夠最大化地利用索引的有序性。

此外，在某些場景下，開發者需要權衡單一欄位索引與複合索引的切換。https://leapcell.medium.com/sql-composite-indexes-when-to-use-1718a9161241 指出，當查詢頻繁涉及多個欄位的組合時，複合索引能顯著減少回表次數。而針對多欄位索引的深度優化，https://www.linkedin.com/pulse/optimizing-mysql-queries-mastering-art-multi-column-indexing-oktfc 則強調了透過精確的欄位選擇來平衡索引大小與查詢速度的藝術。

執行計畫驗證與統計資訊的動態管理

即使設計了完美的索引，若資料庫優化器無法正確預估 Cardinality，查詢計畫仍可能出現偏差。這是因為優化器是基於統計資訊（Statistics）來做出決策的。如果數據分布極度偏斜，或者統計資訊過時，優化器可能會選擇錯誤的執行計畫。

以 PostgreSQL 為例，其查詢規劃器會根據統計資訊預估返回的行數。在 https://runebook.dev/en/docs/postgresql/row-estimation-examples 中詳細說明了預估失敗的常見原因：

  1. 數據變動劇烈：當大量數據插入或刪除後，現有的統計資訊可能不再準確反映實際的基數分布。
  2. 數據分布偏斜（Skewed Distribution）：如果 99% 的數據都屬於同一個值，標準的基數預估可能會導致優化器過度樂觀地預測索引掃描的成本。

為了解決這些問題，開發者必須學會使用 ANALYZE 指令來更新資料庫內部的統計資訊，確保優化器擁有最新的基數數據。此外，利用 EXPLAIN 與 EXPLAIN ANALYZE 是診斷問題的核心工具。根據 https://www.postgresql.org/docs/current/sql-explain.html 的官方文件，EXPLAIN 僅顯示優化器預計的計畫，而 EXPLAIN ANALYZE 則會實際執行查詢並記錄實際回傳的行數。透過對比「預估行數」與「實際行數」，開發者可以精確判斷基數預估是否失準，進而決定是否需要重新調整索引結構或手動提供提示（Hints）。

在可觀測性與維運層面，https://uptimerobot.com/knowledge-hub/observability/cardinality-in-databases-guide/ 指出，監控查詢計畫中的基數預估偏差是維護大型資料庫穩定性的關鍵。當系統出現突發性的慢查詢時，往往是因為優化器因為基數預估錯誤而選擇了全表掃描，而非因為索引本身失效。

總結與研究缺口

綜觀現有文獻，Cardinality 是影響資料庫索引選擇的決定性因素。高基數欄位提供更好的選擇性，是建立高效索引的首選；而複合索引的設計則需遵循高基數優先與等值優先的原則。然而，目前的技術研究仍存在一些挑戰與缺口，包括：

  • 欄位相關性（Correlation）的預估：當兩個欄位高度相關（如「城市」與「郵遞區號」）時，優化器往往假設它們是獨立的，導致基數預估過高或過低，這在複雜查詢中仍是難以完全自動解決的問題。
  • 複雜表達式與函數的影響：在 WHERE 子句中使用複雜函數或類型轉換時，資料庫往往無法精確預估基數，這導致索引失效的頻率增加。
  • 動態數據的即時更新：如何在極高頻率寫入的系統中，保持統計資訊的準確性而不影響寫入效能，仍是資料庫工程中的一項平衡藝術。

透過對上述文獻的整合，本研究認為，優化資料庫查詢不應僅僅是「增加索引」，而應是基於對數據基數分布的深度理解，透過精確的索引設計、合理的欄位順序排列，以及持續的執行計畫監測與統計資訊維護，來達成系統的最優效能。

結果與討論

在深入探討資料庫效能優化的核心機制時，Cardinality（基數）與 Selectivity（選擇性）的關係是決定查詢執行計畫（Query Execution Plan）成敗的關鍵變數。透過對現有研究材料的分析，我們發現資料庫優化器並非僅僅在尋找「有沒有索引」，而是在不斷計算「使用哪個索引能最快排除不相關的資料」。本章將針對 Cardinality 如何影響索引選擇、複合索引的設計邏輯，以及預估機制失效的深層原因進行詳盡的討論。

Cardinality 與 Selectivity 的量化關係及其對優化器的影響

在資料庫系統中，Cardinality 指的是某一欄位中不同數值的數量（Unique Values）。然而，在實際的查詢優化過程中，資料庫引擎更依賴與此高度相關的指標：Selectivity。根據 https://unanswered.io/guide/selectivity-vs-cardinality 的定義，Selectivity 衡量的是特定條件過濾後，返回結果佔總數的比例，數值介於 0 到 1 之間。這兩者之間的數學關係可以簡化為：Cardinality = Selectivity × 總行數。

透過對不同類型的數據分布進行分類，我們可以清晰地看到 Cardinality 如何影響索引的實用性。正如 https://developer.couchbase.com/tutorial-understanding-cardinality-and-selectivity/ 所述，我們可以將資料分為三種等級：

首先是「高 Cardinality」數據。這類數據具有高度的唯一性，例如 GUID、使用者 ID、電子郵件或唯一的使用者名稱。在這些欄位上建立索引時，由於每個值對應的行數極少，其 Selectivity 極高。當優化器掃描這些索引時，能夠精準地定位到目標資料，極大地減少了磁碟 I/O 或記憶體掃描的負擔。

其次是「中 Cardinality」數據。這類數據雖然不是唯一的，但具有一定的區分度，例如姓名、郵遞區號或產品類別。在這些欄位上，索引仍然有效，但優化器需要處理較多的重疊值。

最後是「低 Cardinality」數據，這是開發者最容易陷入陷阱的區域。例如布林值（Boolean）、性別或狀態（Status）欄位。在這些欄位上單獨建立索引往往是無效的。原因在於，如果一個條件（例如 status = 'active'）會返回表中 90% 的資料，那麼優化器會判定「全表掃描（Full Table Scan）」比「索引掃描（Index Scan）」更快。這是因為索引掃描需要額外的操作來查找索引頁面並與數據頁面進行對應，若掃描範圍過大，這種額外的開銷反而會降低效能。這點在 https://medium.com/@CodersWorld99/index-cardinality-explained-the-metric-most-developers-misunderstand-a688923122d6 中得到了深刻的論證：增加索引並不等同於加快查詢，若該索引的選擇性低於特定閾值，優化器將完全忽略它。

複合索引（Composite Index）的設計與高 Cardinality 優先原則

當單一欄位的 Cardinality 不足以滿足查詢需求時，開發者通常會轉向複合索引（Composite Index）。然而，複合索引的欄位順序（Ordering）是極其關鍵的設計點。一個常見的誤區是認為只要將所有相關欄位放入索引即可，但事實上，欄位的排列順序決定了 B+ Tree 結構的分割效率。

根據 https://oneuptime.com/blog/post/2026-03-31-mysql-composite-index/view 的研究，最佳實踐是將「高 Cardinality」的欄位放在索引的最前面。這樣做的邏輯在於：讓資料庫引擎在查詢的早期階段就排除掉大部分不符合條件的資料。如果將低 Cardinality 的欄位放在首位，資料庫可能需要處理大量的相同值，導致索引的過濾效果大打折扣。

此外，我們必須考慮「左前綴原則（Leftmost Prefix Rule）」。為了讓索引發揮作用，查詢條件必須包含索引定義的最左側欄位。在設計複合索引時，除了考慮 Cardinality，還必須區分「等值過濾」與「範圍過濾」。通常建議將等值過濾（如 id = 100）的欄位放在範圍過濾（如 date > '2023-01-01'）之前。這是因為範圍過濾會導致索引掃描在該點停止，後續的索引欄位將無法有效利用。

針對這點，https://www.sqlservercentral.com/forums/topic/composite-indexes-higher-cardinality-first-or-lowest 提供了一個重要的討論視角：雖然高 Cardinality 優先是常見準則，但在某些特定的範圍查詢場景中，如果第一個欄位是範圍查詢，而第二個欄位是高 Cardinality 的等值查詢，則可能需要重新評估索引順序。此外，https://uptimerobot.com/knowledge-hub/observability/cardinality-in-databases-guide/ 強調了高 Cardinality 優先順序在減少掃描行數上的實務價值。透過正確的順序排列，資料庫可以更有效地利用 B+ Tree 的結構，減少分支節點的跳轉次數。

在實際應用中，我們還需要參考 https://leapcell.medium.com/sql-composite-indexes-when-to-use-1718a9161241 的建議，判斷何時該從單一索引轉向複合索引。當查詢經常涉及多個欄位的組合時，複合索引能顯著減少「索引合併（Index Merge）」的開銷，從而提供更穩定的執行速度。而 https://www.linkedin.com/pulse/optimizing-mysql-queries-mastering-art-multi-column-indexing-oktfc 則進一步解釋了如何透過多欄位索引的精細設計來優化複雜的 SQL 查詢，強調了對數據分佈的深入理解是設計索引的核心。

執行計畫驗證與 Cardinality 預估的偏差分析

即使設計了完美的索引，如果資料庫優化器無法正確預估 Cardinality，查詢計畫仍可能發生災難性的錯誤。這是因為優化器是基於統計資訊（Statistics）來做決策的。

在 PostgreSQL 等先進資料庫中，查詢規劃器會根據統計資訊預估返回的行數。如果這些統計資訊過時，或者數據分佈極度偏斜（Skewed Distribution），規劃器可能會選擇錯誤的計畫。例如，它可能預測某個條件只會返回 10 筆資料（選擇了 Index Scan），但實際上卻返回了 100 萬筆資料，導致系統嚴重卡頓。根據 https://runebook.dev/en/docs/postgresql/row-estimation-examples 的分析，當數據發生大規模變動時，統計資訊會變得陳舊，此時必須執行 ANALYZE 指令來更新資料庫內部的統計數據。

為了驗證優化器的決策，開發者必須熟練使用 EXPLAIN 與 EXPLAIN ANALYZE。根據 https://www.postgresql.org/docs/current/sql_explain.html 的官方文件，EXPLAIN 僅顯示優化器「預計」的計畫，而 EXPLAIN ANALYZE 則會實際執行查詢並記錄「實際」的行數與時間。透過對比「預估行數」與「實際行數」，開發者可以找出 Cardinality 預估失敗的具體原因。

預估失敗的常見原因包括：

  1. 數據分佈不均（Skewed Data）：如果 99% 的資料都屬於某個特定值，而標準的統計方法假設數據分佈是均勻的，預估就會大幅偏離。
  2. 欄位相關性（Correlation）：當兩個欄位高度相關（例如「城市」與「郵遞區號」）時，優化器往往會假設它們是獨立的，並將兩者的 Cardinality 相乘來預估結果。這種錯誤的假設會導致預估結果過高或過低。
  3. 複雜表達式與函數：在 WHERE 子句中使用函數（如 WHERE DATE(created_at) = '2023-01-01'）會導致優化器無法直接利用索引，且難以精確預估其 Cardinality。

總結來說，Cardinality 不僅是一個靜態的數據統計值，它是動態的效能關鍵。開發者必須從三個層次來處理它：首先是基礎層次的理解，區分高、中、低 Cardinality 並避免在低選擇性欄位上盲目建立索引；其次是設計層次的優化，在建立複合索引時遵循高 Cardinality 優先與左前綴原則；最後是維護層次的監控，透過 ANALYZE 維護統計資訊，並利用 EXPLAIN ANALYZE 持續驗證查詢計畫的正確性。只有深入理解這些細節，才能在複雜的資料庫環境中實現真正的效能優化。

原創論點

在資料庫架構的設計與優化過程中，Cardinality（基數）與 Selectivity（選擇性）的深度理解，是區分「初階開發者」與「資深資料庫工程師」的關鍵分水嶺。許多開發者常陷入一個常見的誤區，認為只要在頻繁查詢的欄位上建立索引，查詢速度就一定會提升。然而，實務經驗與資料庫引擎的底層邏輯告訴我們，索引的效能並非由「是否存在」決定，而是由「該索引能排除多少不相關資料」決定。

Cardinality 與 Selectivity 的核心辯證：從數值到行為的轉化

要理解 Cardinality 如何影響選擇，必須先釐清它與 Selectivity 之間的數學與邏輯關係。Cardinality 指的是資料集中不同值的數量（Unique Values）。例如，在一個擁有一百萬名用戶的資料庫中，「使用者 ID」欄位的 Cardinality 極高，因為每個 ID 幾乎都是唯一的；而「性別」欄位的 Cardinality 極低，因為它僅包含少數幾個固定值。

與此相對，Selectivity 則是衡量一個查詢條件能過濾掉多少資料的比例。從數學角度來看，Selectivity 往往是 Cardinality 的函數：Cardinality 越高，該欄位的 Selectivity 通常也越高。根據 https://developer.couchbase.com/tutorial-understanding-cardinality-and-selectivity/ 的定義，選擇性（Selectivity）介於 0 到 1 之間，數值越接近 0，代表該條件越能精準定位到極少數的資料。

這兩者的關係直接影響到資料庫優化器（Query Optimizer）的決策。當優化器在評估執行計畫時，它會計算預期的「返回行數」。如果一個索引的 Cardinality 過低，導致查詢條件返回了全表很大比例的資料（例如查詢所有 status = 'active' 的用戶，而該狀態佔了 90% 的數據），優化器會判定使用索引的成本（包括讀取索引頁面與隨後的隨機 I/O 查找）高於直接進行全表掃描（Full Table Scan）。這就是為什麼開發者常發現「明明建立了索引，查詢卻沒變快」的根本原因。

高、中、低 Cardinality 的實務分類與索引策略

在實際應用中，我們必須根據數據的特徵將欄位劃分為不同的 Cardinality 等級，並採取對應的索引策略：

  1. 高 Cardinality（High Cardinality）：

這類欄位具有高度的唯一性，例如 GUID、電子郵件、身分證字號或使用者名稱。這些欄位是建立單一索引的最佳選擇，因為它們能提供極高的選擇性。在 B+ Tree 結構中，高 Cardinality 的索引能讓引擎快速定位到目標節點，大幅減少掃描範圍。

  1. 中 Cardinality（Medium Cardinality）：

這類欄位具有一定的變異性，但並非唯一。例如姓名、郵遞區號或產品類別。對於這些欄位，單獨建立索引的效果可能不如高 Cardinality 欄位顯著，但在複合索引中，它們往往扮演關鍵的過濾角色。

  1. 低 Cardinality（Low Cardinality）：

這類欄位變體極少，例如布林值（Boolean）、狀態碼（Status）或性別。在這些欄位上單獨建立索引通常是無效的。正如 https://medium.com/@CodersWorld99/index-cardinality-explained-the-metric-most-developers-misunderstand-a688923122d6 所指出，低選擇性的索引往往會被優化器忽略。除非配合其他高 Cardinality 欄位組成複合索引，否則不應浪費資源在這些欄位上建立單獨索引。

複合索引（Composite Index）的設計核心：順序的藝術

當單一欄位的 Cardinality 不足以支撐高效查詢時，複合索引（Composite Index）成為核心解決方案。然而，複合索引的設計並非簡單的欄位堆疊，而是關於「排除效率」的排列藝術。

核心論點：高 Cardinality 優先原則

在設計複合索引時，最重要的一家之言是：應將高 Cardinality（高選擇性）的欄位放在索引的最前面。

這背後的邏輯在於「早期排除」。資料庫在掃描索引時，是從左到右匹配條件的。如果我們將一個低 Cardinality 的欄位（如 gender = 'F'）放在最前面，資料庫第一步就只能過濾掉極少數的資料，剩下的仍需在索引中進行大量掃描。相反，如果將高 Cardinality 的欄位（如 user_id）放在最前面，資料庫可以在第一步就排除掉 99% 以上不相關的資料，剩餘的掃描工作量將大幅降低。

此外，在處理複合索引時，還需遵循以下兩個關鍵原則：

  • 等值過濾優先於範圍過濾：通常建議將「等值過濾」（例如 status = 'active'）的欄位放在「範圍過濾」（例如 created_at > '2023-01-01'）的欄位之前。這是因為範圍過濾會導致索引掃描在某一點停止，後續的欄位將無法有效利用索引的有序性。
  • 左前綴原則（Leftmost Prefix Rule）：開發者必須意識到，查詢必須包含索引的左前綴才能觸發索引。如果索引是 (A, B, C)，查詢 WHERE B = 1 是無法有效利用到索引的。因此，將高 Cardinality 欄位放在左側不僅是為了效能，也是為了確保查詢能正確命中索引。

針對這點，https://oneuptime.com/blog/post/2026-03-31-mysql-composite-index/view 與 https://www.sqlservercentral.com/forums/topic/composite-indexes-higher-cardinality-first-or-lowest 等資源皆強調了順序對執行計畫的決定性影響。

統計資訊與預估偏差：當 Cardinality 成為「幻覺」

資料庫優化器並不是預知未來，它是基於「統計資訊」來預測查詢行為的。如果統計資訊與實際數據分布脫節，優化器可能會做出錯誤的選擇。這在數據量劇烈變動或分布極度偏斜（Skewed Distribution）時尤為明顯。

例如，如果一個欄位的數據分布極不均勻（例如 99% 的數據都是 status = 'completed'），而優化器仍認為該欄位的 Cardinality 分佈是均勻的，它可能會錯誤地選擇索引掃描，導致嚴重的效能下降。

為了應對這種情況，開發者必須掌握以下工具與技術：

  • ANALYZE 指令：當數據大幅變動後，必須手動或定期執行 ANALYZE 指令來更新資料庫內部的統計資訊，確保優化器看到的 Cardinality 是準確的。
  • EXPLAIN ANALYZE 的實戰應用：這是診斷 Cardinality 預估偏差的核心工具。透過 https://runebook.dev/en/docs/postgresql/row-estimation-examples 提供的範例可以看出，我們必須對比「預估行數（Estimated Rows）」與「實際執行行數（Actual Rows）」。如果兩者差異巨大，通常代表統計資訊過時或數據分布過於複雜，這時可能需要考慮建立部分索引（Partial Index）或調整統計採樣頻率。

最終取捨建議與架構觀點

基於上述研究，針對資料庫索引選擇的實務建議如下：

  1. 放棄「全域索引」的幻想：不要為了追求「保險」而對所有欄位建立索引。低 Cardinality 的欄位除非作為複合索引的一部分，否則不應單獨建立索引。這不僅節省儲存空間，更重要的是減少了寫入時的索引維護成本。
  1. 優先考慮高選擇性組合：在設計系統時，應優先識別出那些能將結果集縮減到最小的欄位（如 UUID、Unique Key）。在複合索引中，將這些欄位置於最左側，並與範圍查詢欄位結合。
  1. 動態監控與統計更新：在高度動態的系統中，Cardinality 是會變動的。建立自動化的監控機制來追蹤慢查詢，並定期執行統計更新。當發現 EXPLAIN 顯示預估行數與實際偏差過大時，應立即介入檢查數據分佈。
  1. 理解 B+ Tree 的限制：所有的索引選擇最終都受限於底層結構。理解數據如何被分割到節點中，以及 Cardinality 如何影響每個節點的填充率，能幫助開發者在設計複雜查詢時，預判資料庫引擎的反應。

總結來說，Cardinality 不僅是一個統計數字，它是資料庫優化器的「導航地圖」。正確的索引策略是將高 Cardinality 欄位作為第一道防線，利用其高選擇性迅速縮減搜索空間，並結合準確的統計資訊與合理的複合索引順序，來確保資料庫能在海量數據中精準地找到那一枚針。

結論

本研究旨在深入探討資料庫索引中的 Cardinality（基數）如何成為影響查詢執行計畫選擇的核心變數。透過對多個資料庫系統的技術文件與實務案例分析，我們可以得出以下關鍵結論：

總結：Cardinality 與 Selectivity 的決定性影響

Cardinality 與 Selectivity 是資料庫優化器（Query Optimizer）在評估索引效能時最核心的兩大指標。研究明確指出，Cardinality 代表欄位中不同值的數量，而 Selectivity 則是條件過濾後返回結果佔總數的比例。兩者的關係高度相關：高 Cardinality 通常對應高 Selectivity。當一個欄位的 Cardinality 較高（如 GUID、電子郵件或使用者名稱）時，資料庫引擎能夠透過索引精準地定位到極少數的目標行，這正是索引設計的核心價值。

相反地，低 Cardinality 欄位（如布林值、狀態標記或性別）往往會成為效能陷阱。由於這些欄位返回的資料比例過高，優化器為了避免頻繁的索引跳轉與資料頁讀取，往往會選擇全表掃描（Full Table Scan）而非使用索引。這解釋了為何「增加索引不等於加快查詢」的實務現象。開發者必須理解，索引的效能不僅取決於其存在與否，更取決於該索引在特定查詢條件下能排除多少不相關的資料。相關技術細節可參考 https://developer.couchbase.com/tutorial-understanding-cardinality-and-selectivity/ 以及 https://unanswered.io/guide/selectivity-vs-cardinality。

實務建議：複合索引與預估精準度

在實際的資料庫架構設計中，針對 Cardinality 的應用應遵循以下三個關鍵實務建議：

第一，在設計複合索引（Composite Index）時，應遵循「高 Cardinality 優先」原則。將具有高選擇性的欄位放在索引的最前面，能讓資料庫引擎在查詢的早期階段就排除大部分不符合條件的資料，從而大幅縮減掃描範圍。這在處理大規模數據集時尤為重要，相關實務指導可見於 https://oneuptime.com/blog/post/2026-03-31-mysql-composite-index/view 與 https://uptimerobot.com/knowledge-hub/observability/cardinality-in-databases-guide/。

第二，針對「等值」與「範圍」過濾的組合，建議將等值過濾欄位置於範圍過濾欄位之前。這能確保優化器先鎖定特定的基數區塊，再進行範圍掃描。相關討論可參考 https://www.sqlservercentral.com/forums/topic/composite-indexes-higher-cardinality-first-or-lowest。

第三，開發者必須養成使用 EXPLAIN 與 ANALYZE 指令的習慣。由於資料庫的統計資訊可能隨著數據變動而過時，導致優化器預估錯誤（Row Estimation Errors），透過實際執行的 ANALYZE 指令更新統計資訊是確保 Cardinality 預估準確的必要步驟。詳細的技術規範可查閱 https://runebook.dev/en/docs/postgresql/row-estimation-examples 與 https://www.postgresql.org/docs/current/sql.explain.html。

限制與後續研究方向

儘管 Cardinality 是關鍵指標，但在實務應用中仍存在顯著的限制與挑戰。首先是「數據分佈偏斜（Skewed Distribution）」的問題：當數據分布極不均勻時（例如 99% 的記錄都屬於某個特定狀態），標準的 Cardinality 統計可能無法反映查詢的真實成本，導致優化器選擇錯誤的執行計畫。此外，欄位之間的「相關性（Correlation）」也是一個重大難點。當兩個欄位高度相關（例如城市與郵遞區號）時，優化器若假設兩者獨立，會導致預估出的 Cardinality 產生嚴重偏差。

在複雜表達式（Complex Expressions）與動態類型轉換的場景下，資料庫引擎往往難以精確預估 Cardinality，這也是許多索引失效的隱性原因。

後續研究方向應著重於以下三點：

  1. 動態統計更新機制：研究如何針對高頻變動的數據集，實時更新 Cardinality 統計資訊以降低優化器預估誤差。
  2. 欄位相關性建模：探索如何更精確地在查詢規劃器中建模欄位間的相關性，避免因獨立性假設導致的錯誤計畫。
  3. 混合索引策略：針對極低選擇性的欄位，研究如何結合過濾索引（Filtered Indexes）或部分索引（Partial Indexes）來補足 Cardinality 的不足。相關技術討論可參考 https://planetscale.com/learn/courses/mysql-for-developers/indexes/index-selectivity、https://medium.com/@CodersWorld99/index-cardinality-explained-the-metric-most-developers-misunderstand-a688923122d6、https://leapcell.medium.com/sql-composite-indexes-when-to-use-1718a9161241 以及 https://www.linkedin.com/pulse/optimizing-mysql-queries-mastering-art-multi-column-indexing-oktfc。
