偵察提案：reverify（2akouwu/reverify）

專案是什麼

AI 讀二進位檔案的反幻覺工具。模型對二進位提出聲明（位元組、指令、字串等），確定性工具逐一比對實際位元組，判定 VERIFIED／REFUTED／INCONCLUSIVE。v0.8.0 起以 .reverify/ledger/.json 持久化已驗證與已駁斥的事實，防止模型在新的上下文重複同一個已被推翻的假設。786 stars、196 單元測試、19 個系統檔案基準測試 100% 抓出模型幻覺、零誤報，透過 MCP 暴露 re_verify_claim／re_ledger 工具。

對本系統的借鑑點

  • Cordis 的「查了再叫」（AGENTS.md）只保證「查詢當下正確」：resources get 猜錯 id 會拋錯（src/cli.mjs 第 86 行 Unknown resources subcommand／catalog 查無即拋），但這個錯誤不留痕跡——同一個 agent 換一次 context（子 Agent 重跑、跨 session）很可能重猜同一個錯 id。已核對 src/effect-ledger.mjs：現有 EffectLedger 只記錄外掛生命週期（fiber 狀態、lease），不記錄「此 id 不存在」這類否證事實，兩者不重疊，確非既有能力誤報。
  • 可借鑑「REFUTED 負面記憶」：resources get/ready 因 id 不存在拋錯時，同步寫入一筆結構化否證紀錄（如 state/resources-refuted.json），下次呼叫前可先查一次再決定要不要重猜。對 todoist-team 這種多子 Agent 並行、各自獨立 context 的場景最有價值。

建議行動

低風險：僅在 resources get／ready 的既有錯誤路徑加一筆本地否證紀錄，純檔案寫入、無外部副作用，不動既有查詢/執行流程。

需人工決策：是否讓 resources match 讀取否證紀錄以降低該 id 候選權重——這會動到 catalog 核心排序邏輯，需審慎評估是否值得為此增加複雜度。
