偵察提案：jev-chat/jev-chat-jarvis

專案是什麼

裝在手機上的對話副駕，在 QQ／X／飛書中讀懂對方訊息，生成候選回覆並一鍵填入輸入框，但發送權留給使用者。核心設計是「非侵入：只讀螢幕、不 hook、不改包」——用被動觀察取代對目標 App 的介入，成熟度未知（待查證：發布狀態、實際用戶量）。

對本系統的借鑑點

  • Cordis 的 commander.*（examples/plugins/commander/index.mjs:111-124）核准機制是結構性的：approvedPhaseIds 必須在 mission 規劃階段、內容尚未產生前就宣告要核准哪個 phase id。真正的訊息內容（如 LLM 生成的通知文案）在核准當下根本還不存在。
  • notify.agentflow（examples/plugins/notify-agentflow/index.mjs:71-73）送出前只跑 assertPublishable——這是語法級守衛（擋未解析模板洞、[object Object]、undefined/NaN），並非語意審核；一旦 phase 核准，LLM 產出的實際文案會直接外送，無人看過最終文字。
  • jev-chat-jarvis 的「觀察→生成候選→人工按送出」把核准點放在內容產生之後，正好補上 Cordis 現有兩層核准（phase 結構 vs. payload 語法）之間缺的「語意內容」一層。

建議行動

  • 低風險：為 commander.execute 加一個選用的 previewExternalPhases 模式——external phase 產出 output 後、實際呼叫 notify.* 前，先回傳草稿內容並暫停，等下一次呼叫帶 confirmedContent（或修改後版本）才真正送出。可先用既有的新聞摘要簡報 mission（docs/COMMANDER.md:81-91）做端到端驗證：跑 5 次含 compose/notify 的 mission，量測草稿被人工修改的比例與送出前後文字差異。
  • 需人工決策：是否讓此預覽層成為所有 effect: 'external' phase 的強制契約變更（會動到 Commander 現有 API），或維持選用旗標；決策前建議先查證 jev-chat-jarvis 原始碼是否真有可移植的「候選生成」演算法，而非僅有 UI 注入層。
