服務網格零停機升級：從流量切換機制看零停機升級的實現

摘要

服務網格把零停機升級從「多副本輪替」推進到「請求層級精細控制」。Kubernetes 原生 Rolling Update 保證 Pod 集合平滑替換[G8]，服務網格再疊加百分比流量切分、健康監控與即時回滾[G4]，兩層結合形成金絲雀與藍綠混合策略。雲廠商進一步把升級流程 API 化並加入 PreCheck 乾跑機制[G2]，而 AWS App Mesh 即將停止支援[G7]則顯示自建控制平面正被市場淘汰，開源標準加雲端代管正成為主流路線。

背景與現況

零停機升級的最基礎手段是 Kubernetes Deployment 的 Rolling Update：修改容器映像版本後，Deployment 會建立新的 ReplicaSet，以「起一個新 Pod、確認健康、再砍一個舊 Pod」的節奏逐步替換，全程維持至少一個健康 Pod 對外服務，舊 ReplicaSet 保留供一鍵回退（kubectl rollout undo）[G8]。這是絕大多數容器化系統零停機能力的地基，但它的控制粒度停留在「Pod 存不存在」，無法決定「這個請求該走新版本還是舊版本」。

服務網格正是疊加在這層之上的專用基礎設施：它是處理應用程式間所有通訊的軟體層，獨立於服務自身程式碼之外運作，提供服務探索、多種演算法（輪詢、最少連線、加權）的負載平衡，以及跨服務的可觀測性與流量控制[G6]。在此基礎上，業界已形成一套具體的實踐生態——Red Hat 的開源指南把零停機升級明確拆成控制平面與應用程式兩個場景處理[G1]；阿里雲服務網格（ASM）把整個升級流程封裝成一支帶乾跑選項的 API[G2]；HashiCorp 官方的 Well-Architected Framework 則完整說明了以流量切分（traffic splitting）取代傳統負載平衡器的技術路徑[G4]；第三方教學平台也針對 Istio 升級單獨成文[G3]。值得注意的現況訊號是：AWS 已公告將於 2026 年 9 月 30 日終止支援 App Mesh，並建議用戶遷移至 Amazon ECS Service Connect[G7]，這對判讀服務網格生態的走向有指標意義。

機制與技術分析

服務網格零停機升級的核心機制，是用「服務分流器（service splitter）」取代傳統負載平衡器的粗粒度分流。HashiCorp 的框架文件說明，服務分流器可以在服務層級做百分比流量切分、請求層級路由，並根據即時效能指標動態調整流量走向，這種能力是傳統 Load Balancer 做不到的[G4]。更關鍵的是，這種機制把金絲雀部署（canary，逐步小比例導流驗證）與藍綠部署（blue/green，整批切換但可瞬間回退）兩種策略的優點結合在一起：既能用生產流量真實測試新版本，又保留隨時整體回滾的能力[G4]。

把這個機制與 Kubernetes 原生的 Rolling Update 對照，可以看出兩者運作在不同的控制維度上：Rolling Update 決定「新舊版本各有多少個 Pod 存在」，是副本數量層級的控制；服務網格的流量切分決定「每一筆請求該進到新版本還是舊版本」，是請求層級的控制[G8][G4]。兩者並非互斥而是互補——Pod 數量的平滑替換保證運算資源本身不中斷，流量權重的動態調整則保證使用者體感不中斷，兩層疊加才是完整的零停機保障。這也解釋了為何 AWS 在說明服務網格價值時，特別強調「自動化服務探索與持續健康檢查」是先決條件[G6]：沒有即時健康訊號，流量切分只是盲切，一旦新版本異常仍可能大範圍影響使用者。

另一個容易被忽略的技術細節，是 Red Hat 文件對「升級對象」的拆分方式：它把整套零停機升級場景明確分成控制平面升級與應用程式部署兩塊，並強調應用程式的部署方式「不應該負面影響既有路由」[G1]。這意味著完整的零停機升級必須同時處理兩個變動來源——服務網格自身的 sidecar／control plane 版本升級，以及使用者應用程式的版本升級——若把兩者混在一次操作裡執行，會疊加故障面，不利於問題定位與回滾。

雲端代管方案則把這套邏輯進一步產品化。阿里雲 ASM 的 UpgradeMeshVersion API 提供一個 PreCheck 布林參數：設為 true 時只做升級可行性檢查、不真正執行升級[G2]。這相當於把人工經驗中「先做灰度驗證再正式動手」的步驟，轉換成一次可程式化呼叫的乾跑（dry-run），降低了升級操作對人工判斷的依賴，也讓升級動作本身變得可重複、可稽核（API 呼叫並綁定 RAM 權限控管）[G2]。

回滾能力上，兩個層級同樣各自提供保障：Kubernetes 層的 kubectl rollout undo 是 Pod 集合層級的即時回退，失敗的 Pod 會被清除、系統退回上一個穩定 ReplicaSet[G8]；服務網格層的流量權重回退則是請求層級的即時回退，只需把流量權重瞬間調回舊版本即可，不需要重新調度 Pod[G4]。兩者疊加使用，才能真正做到「秒級」止血。

應用與實務啟示

對於要在自己的系統中落地服務網格零停機升級，材料提供的線索可以整理成幾個可執行的原則：

第一，先確保 Kubernetes Deployment 層的 Rolling Update 基線本身健康（健康檢查、就緒探針配置正確），這是所有上層流量控制的地基，沒有這一層，服務網格的流量切分也救不了異常的 Pod 調度[G8]。

第二，在此基礎上導入服務網格的漸進式流量切分作為精細控制層，先以小比例導流新版本觀察錯誤率與延遲，再逐步放大權重，這正是 HashiCorp 描述的「用生產流量測試、保留瞬間回滾能力」的做法[G4]。

第三，升級服務網格本身（control plane／sidecar 版本）時，比照 Red Hat 的做法把「網格自身升級」與「應用程式版本升級」分開處理、分階段執行，避免兩種變動同時發生時難以定位問題根因[G1]。

第四，若使用雲端代管的服務網格，善用其乾跑或前置檢查能力（如阿里雲 ASM 的 PreCheck）在正式升級前先驗證相容性，把「猜測性升級」轉換成「有依據的升級」[G2]。

第五，即時監控指標（錯誤率、延遲、5xx 比例）應作為自動判斷是否繼續放量或觸發回滾的依據，而不是仰賴人工事後發現問題，這也呼應材料中反覆強調的「持續健康檢查」是流量安全切換的前提[G6][G4]。

值得對照的是，即使沒有服務網格，傳統基礎設施層也能透過藍綠切換達成零停機：降低 DNS TTL、建立浮動 IP 或負載平衡器、以 rsync 同步應用程式與資料庫、切換前做完整整合測試、切換後監控 30–60 分鐘並保留舊節點待命作為回滾依據[G5]。這套做法與服務網格方案在目標上是一致的，差異在於粒度與自動化程度：VPS 藍綠切換是「連線層級」的整批切換，操作單位是整台主機；服務網格則是「請求層級」的精細切分，操作單位可以細到單一服務、單一版本的流量比例[G5][G4]。對於高流量、多版本併存、需要漸進驗證的微服務環境，服務網格的精細度明顯更具優勢；但對於架構簡單、版本迭代不頻繁的系統，傳統藍綠切換的操作成本可能反而更低——這是選型時必須權衡的實務判斷，材料中並未給出何者「更好」的定論，需視系統規模而定。

觀點與趨勢判讀

綜合材料判讀，服務網格零停機升級的本質並非全新技術，而是把傳統藍綠／金絲雀部署中「靠人工在基礎設施層手動編排」的步驟，下沉為「宣告式流量規則 + 控制平面自動化」。VPS 藍綠升級指南裡人工執行的 DNS 降 TTL、rsync 同步、負載平衡器切換等一整套手動作業[G5]，在服務網格中被收斂成一組聲明式的流量權重設定與自動健康檢查[G4][G6]，這是這個技術方向最核心的價值主張：把「怎麼切」的操作細節，交給控制平面去自動化執行。

生態層面出現明顯分化訊號：AWS App Mesh 將於 2026 年 9 月 30 日終止支援，官方建議用戶遷移至 Amazon ECS Service Connect[G7]；相對地，阿里雲仍持續投入 ASM 的 API 化能力建設[G2]，HashiCorp 也持續在其官方架構框架文件中把服務網格列為零停機部署的推薦路徑之一[G4]，第三方社群也仍在產出 Istio 升級的專門教學[G3]。這幾條線索合起來看，指向一個判斷：以自研、封閉控制平面為主的服務網格方案（如 App Mesh）正在被市場邊緣化，而以 Istio／Envoy 等開源標準為底層、再由雲廠商包一層管理 API 或由基礎設施廠商（HashiCorp）提供編排框架的模式，生命力明顯更強。對於正在做技術選型的團隊，這是一個值得納入考量的訊號——投入自建或依賴單一雲廠商的封閉服務網格實作，存在被官方棄用的風險。

有一點材料未能充分佐證、仍屬未定之處：oneuptime 平台雖然針對「如何以零停機升級 Istio」單獨成文，顯示這是社群持續關注的具體痛點，但取得的材料內容多為頁面框架而未包含實際操作步驟細節[G3]，因此 Istio 版本間相容性升級的具體技術細節（例如跨大版本升級時的 CRD 相容性問題）仍待更多材料佐證，本報告不對此做進一步推斷。

最後必須提醒的是隱性成本：無論是 AWS 對服務網格的介紹，或是 HashiCorp 對流量切分的說明，都反覆強調自動化健康檢查與可觀測性是精細流量控制的前提條件[G6][G4]。這意味著導入服務網格以取得零停機升級能力，並非只是安裝一個 sidecar 那麼簡單，而是必須同步建置對應的監控與指標基礎設施——這部分投入常在技術選型階段被低估，卻是零停機能力能否真正兌現的關鍵。
