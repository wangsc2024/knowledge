偵察提案：unreal-agent（觀察名單，尚非借鑑提案）

專案是什麼

unreal-agent 的輸入素材只有一句「Async-first agent harness」。定位是以非同步為先的 agent 執行框架，核心機制與成熟度都待查證。依規則先降級為觀察名單。同批的 jev-chat-jarvis、deepopen、magpie 已有處置，disktree 與 PDoomVideo 與本系統無關。golive-skill 的描述被截斷，CLM 的描述是空的。

對本系統的借鑑點

以下是待驗證的假設，不是結論。

  1. 長任務的背景執行與續跑：claude.agent_loop（examples/plugins/llm-claude/index.mjs:316）是同步等待，timeoutMs 限 1000–600000（:372），逾時只能靠 killTree（:59）砍行程。要查 unreal-agent 有沒有「分離、輪詢、續跑」的設計，能不能補上這個缺口。
  2. 取消傳遞：defaultExecImpl 的 signal 會轉成 killTree（:80）。待查證 unreal-agent 的取消是否傳到子任務，以及與 Cordis 現行做法的差集。
  3. todoist-team 的並行任務調度：待查證它的事件流或狀態模型能否對應現有任務狀態。已有規則是只有 skipped 不吃 daily_limit，借用前要先核對語意是否相近。

建議行動

低風險：花一次閱讀時間查證 unreal-agent 的 README 與核心迴圈。樣本為 1 個 repo、3 個維度（背景執行、取消、續跑）。每個維度要附 file:line 證據，才算有證據。

  • 有證據的維度少於 2 個：標記 rejected 結案。
  • 有 2 個以上：先統計 todoist-team 近期任務中因 timed out 失敗的比例。比例過低就不值得改。

需人工決策：是否為 claude.agent_loop 新增非同步模式。這會動到插件契約，要走 specs/ 規格流程，不在本提案範圍內。
