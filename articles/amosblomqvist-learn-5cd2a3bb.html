偵察提案：amosblomqvist/learn

專案是什麼

建立在 pi 平台（earendil-works/pi）上的個人 AI 學習系統設定包，以 .pi 配置目錄形式發布。核心把「教學法」拆成三層：Skills（skills/teach 定義教學流程與哲學、skills/visualize 決定何時需要圖解）、Extensions（extensions/ask-user-question 彈窗提問、extensions/quiz 出題並給對錯回饋、extensions/md-log 把學習過程綁定到 Markdown 日誌、extensions/visual-tools 供視覺化子代理呼叫）、Agents（researcher 負責真實性查證、svg-maker／mermaid-maker 負責產圖）。README 明確標注 researcher 子代理承擔「truth verification」職責，主代理教學前會委派它核實內容。專案僅 2 次提交、4 個資料夾，屬輕量配置框架而非完整應用程式，但已有 793 星、81 分支的社群驗證；核心教學流程在無子代理外掛時仍可獨立運作。

對本系統的借鑑點

  1. 查證閘門插在「輸出前」而非「輸出後」：researcher 是教學內容產出前的强制查核步驟，而非事後補救。對照本系統 knowledge-query／code-assistant skill（D:/Source/skills/knowledge-query/SKILL.md）目前「查詢 API → 直接整合回答」的線性流程，可考慮在整合回答前加一道「與既有筆記/外部來源比對是否矛盾」的輕量核對步驟，而非在使用者發現錯誤後才修正。
  2. 橫切能力抽成獨立 Extension，而非塞進每個 Skill：learn 把「提問彈窗」「測驗回饋」「日誌記錄」都做成可掛載的 extension，供 teach／visualize 兩個 skill 共用。對照 C:\Users\user\.cursor\skills 現有 56 個 skill 是扁平各自實作，未來 skill-creator 新增 skill 時，可比照把「彈窗詢問」「Markdown 日誌」這類重複邏輯抽成共用元件，而非每支 skill 重寫一次。
  3. Markdown 日誌與本系統證據鏈方向一致：md-log 把每次學習 session 綁進 Markdown，性質上與 CLAUDE.md 規則中「實作」指令要求的 specs//evidence/.md 證據鏈相同方向，屬既有慣例的印證，非新機制，不需另立行動。

建議行動

  • 低風險可先做：實際讀取 agents/researcher 底下的 markdown 定義檔（本次僅查證到 README 對其職責的描述，尚未讀取其 prompt 全文），確認查證閘門的具體觸發時機與比對邏輯，評估是否能直接移植一段精簡版到 knowledge-query skill 的回答前處理。
  • 需人工決策：是否值得為 knowledge-query／code-assistant 新增查證子代理步驟——會增加每次查詢的延遲與 API 成本，需使用者評估準確度提升是否划算；若採用，建議先在單一 skill 小範圍試驗，觀察誤答率變化後再決定是否擴散到其餘 skill。
