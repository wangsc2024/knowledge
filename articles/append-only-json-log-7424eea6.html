大型 Append-Only JSON 狀態檔案的終態項歸檔模式：從 Log Compaction、Event Sourcing Snapshotting 到 LSM-Tree 分層儲存的軟體工程借鏡

摘要

context/improvement-backlog.json 已成長至 51107 行、1309 筆項目的單一 append-only JSON 陣列，其中 481 筆已是 archived 狀態、551 筆 deferred，卻仍與 196 筆 pending 活躍項目混雜同檔，每次讀寫都要載入全部歷史。這正是分散式系統儲存引擎數十年來反覆解決的問題：Kafka log compaction 用「保留每個鍵的最新值」取代全量保留；event sourcing 用「snapshot + 保留原始事件流」取代重播全部歷史；LSM-tree 用「分層 compaction（size-tiered vs leveled）」在寫入吞吐與讀取延遲間取捨。本簡報萃取三者的核心設計原則，交叉比對本專案既有的 tools/backlog_writer.py transition_status() 與 tools/backlog_archive_sync_cleanup.py，發現現有終態判定集合（{resolved, wontfix, closed, archived}）已具備部分能力但範圍過窄（漏未涵蓋 deferred/stale），且尚未有排程化、增量式的 compaction 觸發機制。建議方案聚焦「擴大終態定義＋排程化 compaction＋分層儲存」三個可立即落地的方向，而非重新發明資料庫引擎。

關鍵洞見

  1. Log compaction 的核心不是刪除歷史，而是「保留每鍵最新值」語意轉換：Kafka log compaction 將 topic 從「event log」轉換為「changelog-style current-state table」——只保留每個 key 最後一次更新的值，且此保留是無限期的（非基於時間視窗）。證據：Confluent 官方文件明確指出 compaction 適合「need to know the latest state of each key」的場景，而非單純事件流。→ 應用：improvement-backlog.json 的每筆項目已有唯一 id，可比照此語意——一個 id 一旦進入終態，不需要保留其完整歷史修訂，只需保留最終狀態快照。
  1. Tombstone（墓碑標記）機制證明「延遲刪除」比「立即刪除」更安全：Kafka 對已刪除的鍵不會立即清除記錄，而是寫入空值 tombstone，並保留至少 delete.retention.ms（預設 24 小時）才真正清除，目的是給下游消費者足夠時間讀到刪除事實，避免競態條件。證據：Confluent 與多篇部落格（Conduktor、Medium）交叉確認此機制與 "tombstones need to be cleaned at least twice before removed" 的雙重確認設計。→ 應用：本專案「退役只到人工佇列、永不自動刪」的既有原則與此高度同構——延遲/人工確認式刪除本就是業界對「不可逆刪除」風險的標準應對，非本專案特例，可視為已對齊業界最佳實踐的佐證。
  1. Event sourcing snapshot 是效能優化，不是資料替代——原始歷史永遠保留：eventsourcing.dev 明確指出 "Snapshots are just an optimization, not a replacement"，snapshot 需記錄其對應的事件版本號以決定重播起點，且應對 snapshot 格式做版本化（schema versioning），並在 snapshot 損毀時降級為完整重播。證據：多篇來源（AWS Prescriptive Guidance、Kurrent、OneUptime）一致強調「先建 snapshot、原始事件仍歸檔到低成本儲存（如 S3）」而非刪除。→ 應用：對應到 improvement-backlog.json，「歸檔」不等於「刪除」——现有 backlog_archive_sync_cleanup.py 已正確地把終態項「搬到」improvement-backlog-archive.json 而非直接刪除，這個設計已符合 event sourcing 的核心原則，只是觸發頻率與終態定義範圍需要擴大。
  1. LSM-tree compaction 策略選擇是吞吐量與延遲的顯式取捨，沒有免費午餐：Size-tiered compaction（STCS）寫入放大約為 tier ratio（常見值 4），讀取放大為 O(tiers × files_per_tier)，空間放大最高 2 倍；leveled compaction（LCS）寫入放大約 10 倍/層但讀取放大僅 O(levels)（通常每層 1 次）、空間放大僅約 1.1 倍。證據：ScyllaDB 官方部落格系列與 techinterview.org 的低階設計分析交叉確認此數據級距，並給出決策啟發式：「延遲敏感服務用 leveled，攝取密集管線用 tiered」。→ 應用：improvement-backlog.json 的讀寫模式是「持續 append（高寫入頻率）+ 偶爾全量掃描（審計/研究類任務）」，屬於 write-heavy 場景，若要設計 compaction 排程，應偏向 tiered（低頻率、批次合併）而非即時 leveled 重整，避免過度工程化。
  1. 大型狀態檔案治理的產業共識：治理需要「政策」而非只有「機制」：Archive Data Store 的技術指南明確指出 "Archiving without a retention policy is infrastructure without governance"，Terraform/OpenTofu 大型 state 檔案治理實務（OneUptime 系列文章）也強調需要明確的保留規則與生命週期政策，而非僅有搬檔工具。證據：多篇來源交叉確認「政策先於機制」的順序。→ 應用：本專案已有 _CLOSED_STATUSES = {resolved, wontfix, closed}（tools/backlog_archive_sync_cleanup.py）作為機制，但沒有排程化觸發（目前是「一次性 hygiene cleanup」手動執行），也未涵蓋 deferred（551 筆，佔比 42%）與 stale（11 筆）——這是政策範圍不足，而非機制不存在。

多透鏡洞察

透鏡選擇說明：本次選用 sam-altman（規模化平台思維）與 jensen-huang（全棧基礎建設投資角度）作為 primary lens，用以框架化「這個治理問題值得投入多少工程資源」；taleb 作為 adversarial lens，用以檢查是否落入過度工程化或引入新脆弱性的陷阱。三者組合可避免研究只停留在「抄業界模式」而不評估其在本專案規模下的成本效益。

  • Sam Altman 視角（規模化思維／快速部署反饋）：51107 行、1309 筆項目相對於 Kafka/LSM-tree 設計目標的 TB/PB 級資料量，屬於「極小規模」問題。Altman 式的決策啟發式是「先 ship 再迭代」——不需要設計完整的 tiered compaction 引擎，而是先用最小可行的機制（擴大終態定義 + 排程觸發既有 backlog_archive_sync_cleanup.py）驗證效果，再視實際成長速度決定是否需要更複雜的分層策略。快速部署反饋原則意味著：與其一次設計完美的歸檔架構，不如先讓現有工具排程化運作，觀察一個月後的檔案成長曲線再決定下一步。
  • 黃仁勳視角（全棧基礎建設投資／demand-driven 創新）：黃仁勳的「demand-driven 創新」啟發式是「先看 workload 再定義架構」。本專案的 workload 特徵是「高頻 append（每次 self-heal/audit/backlog_writer 呼叫）+ 低頻全量讀取（研究類任務、審計）」，這與資料中心「AI factory」全棧交付邏輯類比：不該只優化單一環節（例如只做壓縮不做讀取路徑優化），而應該像「軟硬體協同」一樣同時處理「寫入路徑」（追加項目時就標註是否可能很快進入終態）與「讀取路徑」（分層儲存讓多數消費端只需讀 pending 檔而非全量檔）。這呼應本專案既有的 -pending.json / 全量 legacy 檔雙檔設計，但目前雙檔同步反而增加維護負擔（見專案記憶：backlog defer-source 須雙寫、pending 不 dual-write legacy 等已知坑）——全棧角度看，這是「基礎建設投資不足」導致的技術債累積，值得一次性投資修正而非持續補丁。
  • Taleb 視角（反模式檢查／脆弱性與不對稱風險）：

- 過度工程化警示：51107 行 JSON（實測約數十 MB 級）遠低於真正需要 LSM-tree 分層儲存引擎的資料量級（該類引擎設計目標是處理無法全量載入記憶體的 TB 級資料）。完整實作 size-tiered/leveled compaction 引擎屬於典型的 Fragilista 行為——用複雜機制解決一個用簡單規則就能處理的問題，反而引入新的失敗模式（compaction 排程本身可能故障、schema 版本管理增加維護面）。

- Lindy Effect 對簡單方案的偏好：本專案現有的「搬檔到獨立 archive JSON + 保留全部歷史」機制，本質上就是最簡單、最經得起時間考驗的方案（等同於檔案系統層級的冷熱分離），不需要引入資料庫層級的抽象。塔勒布式的「經過時間檢驗的優於新穎時髦的」原則，支持優先擴大既有機制的覆蓋範圍，而非引入新概念（如真正的 LSM-tree 函式庫）。

- 不對稱風險檢查：任何自動化刪除/壓縮機制的下檔風險（誤刪珍貴稽核資料）遠大於「檔案略大、讀取略慢」的上檔風險。因此任何 compaction 機制都必須維持「只搬移不刪除」的不對稱防呆設計（skin in the game 對應到系統設計就是「開發者必須承擔誤刪的後果，因此系統本身要讓誤刪幾乎不可能發生」），這與本專案「退役只到人工佇列、永不自動刪」的既有原則完全一致，不應為了效仿業界壓縮機制而放鬆此邊界。

  • 透鏡盲區自陳：

- Altman／Huang 視角均以「規模化」為預設價值判準，容易低估「小規模但長壽命」系統（如本專案，設計壽命以年計）中，看似微小的技術債（如 42% 的 deferred 項目未歸檔）在複利效應下的長期維運成本；兩者的產業案例（OpenAI/NVIDIA）皆處理 PB 級資料與百萬級並發，其決策啟發式移植到千筆級 JSON 檔案時，「先 ship 再迭代」可能被誤用為「不需要治理」的藉口。

- Taleb 視角雖然提供有效的過度工程化煞車，但其「懷疑一切新機制」的傾向可能過度保守，導致明明已有明確業界驗證（如 tombstone 延遲刪除、snapshot 版本化）的成熟模式也被貼上「不必要複雜化」標籤而遲遲不採用；本簡報已嘗試以「業界模式 vs 本專案規模」的具體比對來平衡此傾向，但仍需人工複查判斷「這次真的只需要最小方案」還是「業界模式雖看似複雜，但恰好對應本專案已存在的真實增長軌跡（1309 筆且持續 append）」。

建議行動

  1. 擴大終態定義（最小成本，立即可行）：修改 tools/backlog_archive_sync_cleanup.py 的 _CLOSED_STATUSES（現為 {resolved, wontfix, closed}）與 _PENDING_CLOSED_STATUSES（現額外含 archived），評估是否應納入 deferred（551 筆，佔 42%，是否代表「長期不會再處理」需人工確認判定規則，例如「deferred 超過 N 天且無 followup」才視為準終態）與 stale（11 筆）。此為 policy 層修改，對應洞見 5（「政策範圍不足而非機制不存在」），比照 Kafka log compaction「保留每鍵最新值」的語意，deferred 若確認為事實上的終態，應與 resolved/closed 同等對待搬離主檔。
  1. 排程化既有 compaction 工具（呼應洞見 1、4）：目前 backlog_archive_sync_cleanup.py 為「一次性 hygiene cleanup」手動執行，建議新增排程任務（比照專案既有 HEARTBEAT 機制，如 asset-value-audit 每日 05:23 模式），以 tiered/batch 頻率（例如每日或每週一次，而非即時）觸發 --apply 模式，符合 LSM-tree size-tiered 策略「低頻率、批次合併」的取捨（write-heavy workload 場景不宜選 leveled 式即時整理）。
  1. snapshot 版本化與降級機制（呼應洞見 3）：若未來 improvement-backlog-archive.json 本身也持續成長（目前應已含 481+ 筆 archived 項目），可比照 event sourcing snapshot 的「schema versioning + 損毀降級」原則，為 archive 檔案本身加上結構版本欄位（如既有慣例 version: 頂層欄位），並確保讀取端在遇到未知版本時能優雅降級（如跳過解析而非崩潰），而非急於引入真正的分層儲存系統。
  1. 維持「只搬移不刪除」的不對稱防呆（呼應 taleb 透鏡）：任何後續優化都不應該讓 compaction 機制具備真正刪除能力，應持續遵守本專案既有的「退役只到人工佇列、永不自動刪」原則；tombstone 式的「延遲確認」設計已是業界驗證的最佳實踐，本專案的既有原則毋須因為本次研究而改變，只需擴大覆蓋範圍。
  1. 不建議事項（避免過度工程化）：不建議引入真正的 LSM-tree 函式庫（如 RocksDB）或完整重寫為事件溯源架構——本專案的資料規模（千筆級、數十 MB）遠低於這類技術的設計目標場景，屬於 Fragilista 式的不必要複雜化。若未來項目數成長至 10 萬+ 筆或檔案達 GB 級，才需要重新評估是否需要更完整的分層儲存機制。
