摘要

[李飛飛主筆] 我探討的問題是：MCP／A2A 協定互通爭論之外，代理式 AI 系統是否存在獨立於通訊協定選擇的基礎設施層架構收斂？本文以 51 篇候選、25 篇納入之外部論文與官方文件（A 級 14 篇）為證據基礎，採機械檢索加目標式補檢索、三角佐證法進行分析。核心發現：企業知識編排（Context Kubernetes）、複合式 AI 藍圖架構、多代理排程（Gradientsys）、目錄服務標準（AGNTCY／AgentDNS／OWASP ANS／Google ARD）與代理作業系統論（AOS）等五個彼此獨立發展的脈絡，均收斂於 Kubernetes 血緣的「宣告式登錄檔＋型別化排程器」架構原語；同時，MAST 失效分類學與 A2A 邊緣案例研究證實，中心化登錄在網路規模、高流失率代理族群下構成單點瓶頸，促使 Trust Fabric、Holos 等系統轉向去中心化市場式協調。本文主張，「登錄檔即基礎設施」是被協定標準化敘事掩蓋、卻應被獨立理論化的架構收斂軸線，其企業規模收斂與網路規模分歧併存的雙軌格局，是理解當前代理式 AI 系統演化的關鍵尚未充分探討的面向。

引言

[李飛飛主筆] 2025-2026 年間，代理式 AI 系統的架構討論多聚焦於 Model Context Protocol（MCP）與 Agent2Agent（A2A）能否終結編排層的協定分裂——這是通訊層的問題。但通訊協定之上，代理如何被發現、被排入執行序列，是另一個獨立的基礎設施層問題，卻鮮少被單獨檢視。本文的研究問題是：這個基礎設施層是否存在獨立於協定選擇的架構收斂？若存在，它與協定標準化爭議的關係為何？又是否對所有規模的系統一體適用？

本文的貢獻有三：第一，比對企業知識編排、複合式 AI 藍圖架構、多代理排程、目錄服務標準與代理作業系統論五個彼此獨立發展的技術脈絡，證明它們收斂於 Kubernetes 血緣的「宣告式登錄檔＋型別化排程器」原語；第二，論證此收斂與協定層之爭正交，發生於協定之上；第三，透過 MAST 失效分類學與網路規模系統的批判文獻，揭露此原語在高流失率代理族群下的瓶頸，以及 Trust Fabric、Holos 等系統的去中心化反例，呈現一個尚未被協定標準化敘事充分理論化的雙軌格局。

文獻回顧

[李飛飛主筆] 文獻回顧分組一：企業知識編排與複合式 AI 藍圖架構。 Context Kubernetes[S1：Context Kubernetes, 2026] 提出一套經 TLA+ 形式驗證的 Kubernetes 啟發宣告式登錄檔，管理企業代理系統的知識物件與存取關係，並審計 Microsoft／Salesforce／AWS／Google 四大平台的治理落差——本文僅取其「宣告式登錄檔＋declarative orchestration」的架構面向，刻意迴避其權限模型細節（該面向已由既有研究涵蓋）。同一時期，DAIS Workshop／ICDE 發表的藍圖架構論文[S2：Blueprint Architecture for Compound AI, 2025] 獨立提出以 agent 與 data 登錄檔搭配 QoS-aware 規劃器，透過「streams」協調複合式 AI 系統——兩篇論文分屬不同研究群體、不同會議脈絡，卻收斂於「登錄檔為核心協調結構」的相同判斷。

文獻回顧分組二：多代理排程與型別化介面。 Gradientsys[S3：Gradientsys, 2025] 是本文證據中最直接的排程器案例：以型別化 MCP 介面整合異質工具、搭配動態 ReAct 規劃器，在 GAIA benchmark 上於延遲、成本、成功率三項指標均優於 MinionS 基線，證明型別化介面＋排程器並非純理論建構而有實證效益。Microsoft 官方文件描述的 Semantic Kernel Runtime[S23：Semantic Kernel Agent Orchestration, 2025] 定義 5 種命名編排模式，共用型別化介面與需啟動／呼叫／閒置的明確 Runtime 物件——雖無獨立登錄檔，但 Runtime 功能上類比本地任務排程器，顯示同一原語在框架層的輕量變體。背景綜述[S4：AI Agents survey, 2025] 則提供感知／規劃／工具使用模組架構的分類框架，作為判斷各案例落於哪個架構層次的依據。

文獻回顧分組三：目錄服務與命名標準化。 這是本文證據最密集的一組。AGNTCY Agent Directory Service[S5：AGNTCY ADS, 2025] 採 Kademlia DHT 雙層映射（能力索引與內容定位解耦），沿用 OCI/ORAS 分發與 Sigstore 溯源，且建於 Open Agentic Schema Framework 之上，同時支援 LLM prompt agent、MCP server、A2A 元件——這是本文「登錄檔收斂與協定選擇無關」論證最直接的證據，因為同一登錄基礎設施可服務多種協定的代理。AgentDNS[S6：AgentDNS, 2025] 走 DNS 隱喻的路線，提出統一命名空間 agentdns:// 與語意式服務發現，並已提交 IETF Internet-Draft，顯示標準化企圖不僅止於學術論文層次。OWASP 的 Agent Name Service[S7：OWASP ANS, 2025] 則從安全治理角度切入，登錄檔內容涵蓋 DID、能力、安全政策、PKI 憑證，將問題明確框定為登錄服務設計任務。Google 的 Agentic Resource Discovery 規格[S19：ARD, 2026] 進一步將 MCP server、A2A agent、OpenAPI 工具皆納入同一「Catalog」原語，並以聯邦式爬取索引的「Registry」原語運作，其官方部落格明言 registries 的角色是「代理式網路的搜尋引擎」。相較之下，Anthropic 於 2025 年 9 月推出的 MCP Registry[S16：MCP Registry, 2025] 僅提供發現／目錄功能，尚無 QoS 或排程概念，顯示同一收斂軸線上不同專案的成熟度並不一致。另有一篇對比集中式／企業級／分散式登錄檔架構的分類研究[S9：Evolution of AI Agent Registry Solutions, 2025] 將「登錄檔」本身列為獨立架構類別，是「登錄檔已被承認為獨立架構類別」的後設證據，惟其作者群與 S5 AGNTCY 系脈絡重疊，此點於風險與限制段落另行揭露。

文獻回顧分組四：代理作業系統論與跨產業回應。 若前三組是「由下而上」從個別系統歸納，Agent Operating Systems 論文[S8：AOS, 2026] 則是「由上而下」從作業系統框架獨立推導出登錄檔＋排程器＋政策信任執行＋可觀測性的責任拆分——其論證路徑與 K8s 血緣完全不同，卻得出結構相同的結論，強化了「獨立收斂」而非「互相抄襲」的判斷。電信產業的聯邦式 AI 作業系統提案[S10：Federated Telco OS, 2025] 提供跨產業別的佐證：代理透過型別化服務介面（schema catalog）與統一註冊層曝露，輸入輸出 schema 遵循版本化強型別定義。產業界的回應則呈現梯度：Google Cloud 已推出具名的 Agent Registry 產品，官方文件[S17：Agent Registry libraries, 2026][S18：Agent Registry concepts, 2026] 定義 Agent／MCP Server／Endpoint／Skill／Tool／Binding 的正式資料模型，各以全域唯一 URN 定址，Skill 萃取自 A2A Agent Card 作為發現主鍵——功能上等同 Kubernetes labels/selectors 的型別化能力 schema。Microsoft 於 2025 年 5 月加入 MCP Steering Committee，貢獻授權規格與登錄服務設計[S22：Microsoft MCP Steering Committee, 2025]。相對地，AWS Bedrock 的多代理協作官方文件[S20：Bedrock multi-agent collaboration, 2025][S21：AWS multi-agent preview, 2024] 顯示監督代理仍以建置期 API 靜態關聯至多 10 個協作代理，並非動態執行期發現；CrewAI 官方部落格[S24：CrewAI, 2025] 則區分無中心登錄檔的 Crews 與事件驅動狀態化編排的 Flows，其登錄多為程式碼內宣告，是框架層而非平台層的輕量收斂資料點。

文獻回顧分組五：批判與反例。 這組文獻是本文與單純「產業敘事整理」區隔的關鍵。Cemri 等人的 MAST 失效分類學[S11：Why Do Multi-Agent LLM Systems Fail?, 2025] 分析 1,600+ 執行軌跡、7 個主流框架，發現弱編排器即使工作代理各自表現良好，仍會成為路由整合的瓶頸。2026 年的隱形編排器研究[S12：Invisible Orchestrators, 2026] 以預註冊 3x2 實驗（365 次執行）發現隱形中心化編排器造成內部狀態解離，標準行為評估偵測不到——這是治理與安全面向的風險，而非單純效能問題。A2A 邊緣案例研究[S13：Agent2Agent at Edge, 2025] 更直接指出登錄式與 API 式發現機制在大規模、高流失率代理族群下構成可擴展性瓶頸與單點故障。Trust Fabric[S14：Trust Fabric, 2025] 與 Holos[S15：Holos, 2026] 則是最激進的反例：前者主張代理應能跨網路邊界自主運作、不依賴中心化中介或登錄檔；後者是百萬級代理的網路規模系統，明確拒絕靜態或中心化編排，改採 Nuwa 引擎驅動的市場式自組織協調。最後，Kubernetes 官方文件本身[S25：kube-scheduler, 2026] 提供本文比較基準：以 etcd（經 API server）為宣告式登錄檔的 watch-and-bind 迴圈，以及 Filter→Score 兩階段排程演算法，正是上述多數代理編排平台所呼應的原型架構。

[Yann LeCun主筆] 檢索分兩層：機械 Phase 0 harvest 鎖定 arXiv／OpenAlex／Semantic Scholar，用「large language model architecture」「AI agent orchestration」「frontier model capabilities」三組關鍵詞，原目標候選池 40 篇，但「frontier model capabilities」一詞與物理、天文、金融文獻大量碰撞，機械 harvest 僅取得 24 篇合格候選——沒達標就沒達標，不假裝。缺口由兩個並行子 agent 執行目標式 Phase 1-4 補檢索補齊，最終達 51 篇篩選、25 篇納入。納入排除準則有三：對照全部 20 個既有 negative_topics 排除重題（實際排除／重新框定兩個候選：Orchestrator-Agent Trust 與 Context Kubernetes 的 RBAC 角度，兩者已被既有研究涵蓋）；來源分級採 A（同行評審論文／官方規範）／B（會議論文／官方文件）／C（技術部落格）三級，禁用 D 級（KB 筆記）；每個核心主張須有 ≥3 獨立來源方可標記「已驗證✅」，僅單一或官方來源標「待驗證⚠️」。三角佐證法的執行結果見結果與討論一節與附錄表。本節誠實揭露的限制是：這是一個從已定候選池收斂而來的敘事，不是窮舉式系統性文獻回顧（systematic review）——沒有 PRISMA 流程，沒有雙盲篩選者一致性係數，讀者應把它當成有嚴謹三角佐證支撐的深度技術報告，而非同行評審綜述論文。

結果與討論

[李飛飛主筆] 收斂的實證圖像：企業規模收斂 vs. 平台成熟度梯度。 以 Kubernetes kube-scheduler 的 watch-and-bind＋Filter→Score 架構[S25：kube-scheduler, 2026] 為比較基準，本文證據顯示至少五個獨立技術脈絡收斂於同構原語：Context Kubernetes 的宣告式登錄檔[S1]、藍圖架構的 agent/data 登錄檔＋QoS 規劃器[S2]、Gradientsys 的型別化介面＋ReAct 排程器[S3]、AGNTCY／AgentDNS／OWASP ANS／Google ARD 的目錄服務家族[S5][S6][S7][S19]，以及 AOS 從作業系統框架獨立推導的責任拆分[S8]。但收斂不等於均質：Google Cloud 已將登錄檔產品化為具正式資料模型的 Agent Registry[S17][S18]，Microsoft 以 MCP Steering Committee 成員身分共同設計登錄規格[S22]，而 AWS Bedrock 在本文撰寫時仍以建置期靜態關聯多代理協作[S20][S21]——三大雲端供應商在同一收斂軸線上，處於明顯不同的成熟度階段。這說明「登錄檔即基礎設施」的收斂是方向性的、而非全域已完成的事實。

收斂與協定層爭議的正交性論證。 本文的核心方法論判斷是：登錄檔收斂與 MCP／A2A 協定選擇正交。證據在於 AGNTCY ADS[S5] 同時支援 LLM prompt agent、MCP server、A2A 元件於同一登錄基礎設施之上；AgentDNS[S6] 的統一命名空間跨組織與技術邊界運作，不綁定單一協定；Google ARD 規格[S19] 明言將 MCP server、A2A agent、OpenAPI 工具皆視為同一「Catalog」原語的條目。換言之，即使 MCP／A2A 協定互通爭論從未解決，登錄檔層的收斂仍會獨立發生——因為它解決的是不同的問題（代理如何被發現與排程），不是協定本身要解決的問題（代理之間如何通訊）。這正是本文主張「登錄檔即基礎設施」應被視為獨立收斂軸線、而非協定標準化的副產品的實證基礎。

中心化瓶頸與去中心化反例的雙軌並存。 收斂的圖像並非沒有反例。MAST 失效分類學[S11] 以 1,600+ 執行軌跡的實證資料指出，弱編排器即使工作代理各自表現良好，仍會成為路由整合的瓶頸；A2A 邊緣案例研究[S13] 更直接指出中心化登錄／API 發現在高流失率、大規模代理族群下構成單點故障。這促成了兩個明確拒絕登錄檔＋排程器原語的網路規模系統：Trust Fabric[S14] 主張以經濟誘因取代登錄檔中介，讓代理跨網路邊界自主互動；Holos[S15] 是百萬級代理系統，明確採用市場驅動的自組織協調（Nuwa 引擎），拒絕靜態或中心化編排。這形成一個可操作的判準：企業規模（數十至數百代理，可控流失率）傾向收斂於登錄檔＋排程器；網路規模（數百萬代理，高流失率、跨信任邊界）則傾向去中心化市場式協調。兩者不是矛盾，而是規模軸線上的不同均衡點——這一點在既有的 MCP／A2A 協定互通討論中很少被單獨標舉。

實踐建議（Yann LeCun主筆）： 企業架構師若要為代理式系統選型登錄基礎設施，我建議用三個問題做成熟度評估：第一，你的代理族群規模與流失率——低於百級、流失率可控就用登錄檔＋排程器，這是已驗證的工程模式，不必自己發明；規模逼近網路級（Holos 等級的百萬代理、高流失率）才需要認真考慮去中心化市場式協調，否則是過度工程。第二，你的雲端供應商在這條收斂軸線上的實際成熟度——Google／Microsoft 已有具名產品化登錄檔，AWS 目前仍是建置期靜態關聯，選型前先查證，不要假設「大廠都一樣」。第三，登錄檔本身不解決協定分裂——如果你的痛點是「代理之間講不通話」，那是 MCP／A2A 的問題，不是登錄檔的問題，兩者要分開診斷，混為一談會導致選錯工具。

風險與限制（Yann LeCun主筆）： 三點誠實揭露。第一，S9 對比集中式／企業級／分散式登錄檔架構的分類研究，其作者群與 S5 AGNTCY 系脈絡重疊，這意味著本文對「獨立收斂」的論證，在目錄服務這一組證據上，有部分並非完全獨立的觀察者——我把這點攤開講，而不是假裝沒看到。第二，本文候選池的 L1（一般網頁）證據薄弱，25 篇納入來源全數為英語學術論文與官方文件，缺乏中文來源與非學術社群討論的視角，這是檢索策略的已知侷限，不是刻意排除。第三，多數官方文件（Google／AWS／Microsoft 的文件類來源）具高度時效性，雲端供應商的產品成熟度以月為單位變動，本文對「AWS 仍為建置期靜態關聯」的判斷僅反映撰寫當下的公開文件狀態，讀者查證時應核對來源年份與最新官方文件。

原創論點（一家之言）

[李飛飛主筆] 本文提出一個尚未見於既有文獻的判斷：協定標準化（MCP／A2A）之所以佔據絕大多數公共論述版面，不是因為它在架構上比登錄檔收斂更重要，而是因為它有天然的敘事優勢——協定有廠商公關戰、有版本號、有「誰的協定會贏」的競賽敘事可寫；登錄檔收斂則發生在產品文件與 TLA+ 形式驗證論文的縫隙裡，沒有一場「登錄檔大戰」可供媒體報導。這造成一種我稱之為「基礎設施能見度不對稱」的現象：企業架構決策者容易高估協定相容性的戰略重要性，低估登錄檔治理的戰略重要性，恰恰是因為後者不產生新聞稿。這個判斷本身不是對任何一篇既有文獻的重述，而是從本文五組獨立收斂證據與產業成熟度梯度並置後才浮現的推論。

第二個原創論點涉及治理與人本影響：登錄檔一旦成為基礎設施，「誰的代理被列入登錄檔」「誰擁有 schema 定義權」就從技術細節升級為准入權力問題——這與我長期關注的「誰被排除在數據之外」是同一種結構性提問，只是換了層。AGNTCY、Google ARD、OWASP ANS 目前各自定義互不相容的能力 schema，若缺乏跨組織協調，登錄檔收斂反而可能製造新的廠商鎖定，而非解決代理發現的碎片化——這是一個比「協定會不會統一」更迫切、卻幾乎未被本文檢索到的文獻直接處理的問題，我將其列為本文最重要的未竟研究缺口。

第三，本文主張「企業規模收斂、網路規模分歧」不應被理解為單純的規模效應，而應理解為兩種不同的信任模型在架構層的具象化：登錄檔與排程器的組合隱含一個可信的中央權威（誰來維護登錄檔），這在企業邊界內成立，因為企業本身就是那個權威；Trust Fabric、Holos 等網路規模系統之所以拒絕這套組合，本質上是拒絕「存在單一可信權威」這個假設，而非單純解決效能瓶頸問題——效能瓶頸只是這個更深層信任模型分歧的表面症狀。這個信任模型視角，是本文從證據中提煉、而非任何單一來源直接陳述的判斷。

結論

本文回答的研究問題是：代理式 AI 系統是否存在獨立於 MCP／A2A 協定選擇的基礎設施層架構收斂？證據顯示答案是肯定的——企業知識編排、複合式 AI 藍圖架構、多代理排程、目錄服務標準與代理作業系統論五個獨立脈絡，收斂於 Kubernetes 血緣的宣告式登錄檔＋型別化排程器原語，且此收斂與協定層爭議正交。但這個收斂並非均質完成，三大雲端供應商的登錄檔成熟度呈現明顯梯度；也並非普遍適用，MAST 失效分類學與網路規模系統的批判證據顯示，此原語在高流失率、超大規模代理族群下面臨結構性瓶頸，促成 Trust Fabric、Holos 等去中心化反例。本文的限制在於候選池語言單一（全數英語來源）、部分目錄服務文獻作者群重疊、以及產業文件的高度時效性。後續研究可朝三個方向推進：一是實證量測登錄檔治理的准入權力分布（誰被列入、誰定義 schema）；二是追蹤 AWS 等成熟度落後供應商是否在未來季度補上動態登錄能力；三是檢驗信任模型分歧（中央權威 vs. 市場自組織）是否能在單一系統內以混合架構並存，而非二選一。
