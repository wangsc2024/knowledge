偵察提案：deepopen-com/deepopen

專案是什麼

DeepOpen 是非自回歸「System 1」決策引擎：以 ModernBERT/mmBERT 做單次前向傳遞完成多維度分類（choice／score／noul 三種決策原始型），非逐 token 生成文字。提供三個檢查點（英文 421M、多語 322M、決策優化版），延遲 32.8–39.5ms，自託管零推論成本。Apache 2.0，1000+ stars、110 forks、18 次提交，有 PyPI 套件與 Banking77／CLINC150 基準測試，屬可執行、已驗證的成熟專案。限制：基礎檢查點零樣本準確率接近隨機（0.36 vs 多數類基線 0.46），須領域微調才有實用價值。

對本系統的借鑑點

本系統 src/resource-match.mjs 的 matchResources()／scoreEntry() 正是 AGENTS.md 所稱「決定論，不用 LLM」的匹配器實作：純詞袋 n-gram＋子字串比對，對 id/name/trigger/when/summary 給固定加權分（15/8/10/3/5/2），完全依字面重疊，同義改述或跨語言措辭一律得零分。目前目錄下有 144 個 plugin manifest（examples/plugins//plugin.json）與 45 個 skill 模板（examples/plugins/skill-prompt/skills/.md），規模足以支撐一個小型分類任務：

  1. DeepOpen 的 choice 原始型可作為 matchResources 之外的語意重排層（非取代），專門攔截與 id/trigger/when 無字面重疊但語意相符的意圖查詢。
  2. 其「先用純 Python 偵測語言／腳本再選檢查點」（<0.5ms）的路由設計，與本系統 tokenizer 已區分 Han-run／Latin 的做法同構，可用類似路由決定何時才值得跑語意重排、何時直接沿用現有字面比對。

建議行動

低風險先做（不動架構）：從既往偵察提案清單與過去半年的意圖查詢中，整理至少 30 條「已知應命中某 plugin/skill，但字面不重疊」的改述查詢，跑現有 matchResources 記錄 top-1／top-3 精準率作基線；同時用 deepopen-typed-decisions 檢查點以 144 個 plugin id ＋ 45 個 skill id 為類別做小規模微調，在同一組 30 條查詢上量測 top-1／top-3 精準率與延遲，比較兩者差距。

需人工決策：DeepOpen 是 Python/PyTorch 模型，本系統為純 Node（.mjs）、manifest-only 設計，導入需另立 Python 微服務或透過 onnxruntime-node 做 ONNX 匯出，屬新增外部依賴的架構決定；僅當上述離線評測顯示 top-3 精準率提升幅度顯著（如 ≥15 個百分點）且推論延遲仍低於 50ms 時，才值得評估是否引入此依賴邊界。
