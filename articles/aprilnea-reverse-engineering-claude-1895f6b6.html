偵察提案：AprilNEA/reverse-engineering-claude-code-antspace

專案是什麼

研究者對 Claude Code web 版的 Firecracker microVM 執行環境做 strace -p 1 層級的行為觀察，意外挖出 Anthropic 內部未公開的 PaaS 管線代號 Baku／Antspace：intent → Claude → Baku → Supabase → Antspace → 上線 App，且 Supabase 資料庫是由 MCP「靜默」佈建，使用者介面完全看不到這一步。這是一份研究/分析型 repo（README＋baku-analysis.md），非套件化工具，方法可轉移但無現成函式庫可依賴。

對本系統的借鑑點

  1. 揭露的核心風險是「宣稱介面 vs 實際行為」存在落差——使用者只看到結果，看不到背後真的碰了哪些外部資源。這與 Cordis 的 sideEffects 六級聲明機制正對應：src/manifest.mjs 的 SIDE_EFFECTS 集合（none/network/filesystem/process/llm/external）、src/contract-lint.mjs 的 permissionGaps()（第 37–48 行）目前只檢查「宣告為 network/filesystem/process/external 時，manifest.permissions. 是否非空」——這是純靜態、自我宣告式檢查，沒有任何機制驗證 plugin 的 activate() 實際執行時是否真的只做了宣稱的事。一個宣告 sideEffects:'none' 或 'llm' 的 capability，實際偷偷呼叫 node:fs／node:net／node:child_process，npm run check 抓不到。
  2. AprilNEA 用的方法是對執行環境做系統呼叫層級觀察，而非只讀文件宣稱——這正是 Cordis 目前缺的「行為稽核層」。src/process-plugin.mjs 已有 createContainerPlugin（network:none、read-only、cap-drop=ALL）與 createWasmPlugin（無 import 的純沙箱），但這兩者是執行期隔離，不是宣告一致性驗證——兩者互補而非重疊，值得補上後者。

建議行動

  • 低風險可先做：寫一支唯讀稽核腳本（如 scripts/audit-side-effects.mjs），對 examples/plugins 下宣告 sideEffects:'none' 或 'llm' 的 capability 抽樣 3–5 個，在測試模式呼叫其 activate()，用 async_hooks 或對 node:fs/node:net/node:child_process 做 monkey-patch 攔截並記錄實際呼叫，量測「宣告 vs 觀察到」的不一致率（mismatch 數／抽樣數），作為可行性驗證的起點，先不納入 CI 門檻。
  • 需人工決策：稽核結果是否升級為 npm run check 的強制門檻——間接依賴（如日誌函式庫內部觸碰 fs）可能造成誤判，需要人工判斷是否設白名單；以及是否將稽核擴及 process/external 等級，這牽涉是否要引入更重的觀察工具（如 strace/Process Monitor），超出目前 CI 環境的既有假設，需先評估可行性。
