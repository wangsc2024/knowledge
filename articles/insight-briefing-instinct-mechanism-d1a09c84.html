深度研究洞察簡報：Instinct 學習引擎 mechanism 階段深化——confidence 公式真實資料飽和失真、候選簇不減反增與 langgraph 品牌殘留

日期：2026-08-14　任務：insight_briefing　系列：instinct-behavior-learning-ddp-digest-memory（synthesis→mechanism，completion_pct 85%）

摘要

延續 research_series_advisor.py 標記的 mechanism 階段優先建議（days_since_active=19），本輪針對 2026-07-26 mechanism 草案的兩項未驗證假設做真實資料實測：P0 歸因修復（post_tool_logger.py:639 AGENT_NAME fallback）是否真的降低 MISSING agent 率、以及 confidence 衰減公式在生產資料量級下是否維持鑑別力。結果均為否：30 日窗實際僅 17 天有可讀日誌（logs/structured/ 2026-07-23~08-04 共 13 天僅剩 0-byte .lock），30290 筆事件中 MISSING agent 率 26.4%（7983 筆），與修復前基準 25.1%~27.3% 無顯著差異；L0 候選簇由 07-24 optimization 階段的 23 組膨脹至本次 54 組原始／36 組二階門檻，與 synthesis 「30 日後收斂至 ≤3 根因簇」的方向相反；套用 07-26 草案公式後，33~283 次事件的候選幾乎全數壓縮至 0.80–0.85 窄帶，喪失鑑別力。交叉驗證 2026 年 arXiv:2606.22030v2（Reliability-Conditional Updating）指出純頻率式信心更新在 LoCoMo 基準與 naive last-write-wins「打平」，並提出 r = min(provenance, content) 合成規則將 volumetric flooding 攻擊成功率由 100%→0%——為本次實測飽和現象提供獨立學術佐證。另發現 36 組候選中至少 10 組以 langgraph-* 為聚類鍵，但 ADR-20260529-052（2026-05-30）後實際 workflow_engine 已是 planner_executor，語意與執行層脫鉤 2.5 個月未修正。套用 3 組思考透鏡（Sam Altman／黃仁勳／塔勒布）完成多透鏡洞察小節。KB 語義快取 7 日 lookup/store=0、fastembed 不可用（degraded）。不建議依現行公式產出 context/behavior-instinct-candidates.json v1。

核心洞見

1. P0 歸因修復已落地但未閉合缺口——fallback 機制效果待查

hooks/post_tool_logger.py:639 確認存在「若 agent_name 為空，則用 phase 作為 fallback」的邏輯，對應 07-24 optimization 階段標記的 P0 修復。實測 2026-07-15~08-14 窗內可讀的 17 天資料（30290 筆事件）：agent 欄位為空字串的比例為 26.4%（7983/30290），與修復前 07-23/07-24 briefing 引用的基準 25.1%~27.3% 幾乎無差異。可能原因：phase 欄位本身在同一批事件中也常為空（fallback 鏈條上游即缺值），或 fallback 分支未覆蓋所有呼叫路徑（如非 hook 觸發的直接寫入）。此為下一輪 arch_evolution 應優先查證的具體缺口，而非本次臆測。

2. 候選簇規模不減反增，與 synthesis 收斂目標背道而馳

依 07-26 草案 L0 規則（agent+signal_tag 硬鍵合併）對真實資料重跑：io-guard-warn／loop-suspected 兩個訊號標籤下，17 天窗產生 54 組原始 (agent, signal_tag) 配對，套用 07-23 application 階段訂出的二階門檻（≥3 次且橫跨 ≥3 個獨立日期）後仍有 36 組通過——遠高於 07-24 optimization 階段快照的 23 組。synthesis 階段的成功標準是「P1 fingerprint 試行 30 日後收斂至 ≤3 根因簇」；目前趨勢顯示僅靠 L0 硬鍵合併不會自然收斂，必須依賴尚未落地的 P1 fingerprint 子分裂與根因合併層才可能達標，且合併層本身需要更多設計驗證才能宣稱可行。

3. confidence 公式在生產資料量級下飽和失真，喪失鑑別力

07-26 草案公式：base=0.35 + 0.05min(evidence_count,6) + 0.05min(distinct_days,4) - 0.10(若 >14d 未觀察)，count 項在 6 次即封頂。將此公式套用本次實測的 36 組 gated 候選：前 6 名事件數介於 70～283 次，全部因 count 與 days 項同時觸頂而落在 0.80～0.85 窄帶——公式無法區分「發生 3 次」與「發生 283 次」的候選優先序，等同於在生產資料量級下退化為近似常數。此為 07-26 草案未經真實資料驗證即被記錄為「草案」的直接後果，本次是首次以生產日誌量級對其做壓力測試。

4. 學術交叉驗證：純頻率式信心更新是已知的結構性弱點（arXiv:2606.22030v2，2026）

WebFetch 覆核論文《When Does Belief-Based Agent Memory Help? Reliability-Conditional Updating and Provenance-Capped Poisoning Defense》（Section 7-9）：純頻率式更新（無來源可靠度加權）在 LoCoMo 基準上與 naive last-write-wins「打平」（inert，Table 4）；改用來源可靠度加權的 Bayesian 更新後，在合成矛盾基準上得分 100 對 67（Table 5，Section 8）。該文提出的 provenance-capped 合成規則 r = min(provenance, content)——信心受限於「來源可靠度」與「內容合理性」兩者較低者——使 volumetric poisoning flooding 的攻擊成功率從 100% 降至 0%（Table 6，低通道層級 ≤0.5 時）。DDP 草案公式屬於論文定義的「純頻率」類別（僅計 count／distinct_days，無來源可靠度維度），本次實測的飽和現象是該學術發現在真實生產系統上的獨立實證，而非孤立的參數調校問題。注意：論文作者本身承認 provenance-capped 防禦「需要 taint-tracking，本文僅描述機制未實作」（Section 9），DDP 若採用此方向亦須從輕量版本（如以 tag 觸發路徑多樣性近似 provenance）開始，不宜直接照搬完整方案。

5. 聚類鍵語意殘留：`langgraph-*` 品牌在退役 2.5 個月後仍是主要聚類鍵

run-todoist-agent-team.ps1:1009：$env:AGENT_NAME = "langgraph-$key" 於 Start-PlannerExecutorJob 函式內原樣沿用（該函式本身已於 ADR-20260529-052 完成正確改名）。tools/workflows/langgraph_task_runner.py 內部確認實際路由：from tools.planner_executor.runner import ... run_task，回傳 "workflow_engine": "planner_executor"——即執行層已 100% 轉移，僅環境變數標籤未同步更新。本次 36 組 gated 候選中，langgraph-ai_deep_research（292 次/8 日）、langgraph-ai_workflow_github（255 次/8 日）等 至少 10 組以此退役品牌為聚類鍵之一。此為 07-26 草案未預見的資料品質細節：若未來導入 CLAG 式語意路由（依 agent 名稱推斷任務語意），退役品牌名稱會被誤判為獨立引擎類別。

6. 30 日回溯窗實際僅 17 天可用——資料完整性缺口影響本次量測基準

logs/structured/ 目錄 2026-07-23~2026-08-04（13 天，另 08-06 亦缺）僅存在 0-byte .jsonl.lock（寫入互斥鎖殘留），無對應 .jsonl 或 .bak 資料檔；同期其他日誌管線（logs/buddhist-audit-shadow-.jsonl、logs/structured/report-quality-lint-.jsonl）持續正常寫入，排除全域故障，指向 post_tool_logger 專屬的持久化或輪替環節異常。本次「30 日窗」實測因此僅覆蓋約 17 天真實資料，第 1、2、3 項數字均為此樣本下的保守估計，實際缺口期間的事件密度未知。

建議行動

  1. 暫緩 context/behavior-instinct-candidates.json v1 產出（07-26 建議動作 #1）：需先修正 confidence 公式，避免 evidence_count 項在生產量級下飽和——建議改對數尺度（如 0.05 * min(log2(count+1), 8)）或參考 arXiv:2606.22030v2 引入輕量版 provenance 維度（如以 tag 觸發路徑多樣性 / 是否跨多個獨立工具鏈近似可靠度），而非僅計原始次數。
  2. 追查 P0 fallback 未閉合缺口的根因：檢查 phase 欄位本身在同批事件中的填充率、以及是否存在繞過 hook 直接寫入 log 的路徑。
  3. 機械修復（低風險、已驗證路徑）：run-todoist-agent-team.ps1:1009 的 AGENT_NAME = "langgraph-$key" 建議改為與 workflow_engine 對齊的標籤（如 pe-$key），同步清理聚類語意雜訊；此為單行變更，Start-PlannerExecutorJob 函式本體已正確命名，僅環境變數字面值未同步。
  4. 排查 logs/structured/ 2026-07-23~08-04（13 天）持久化缺口成因，否則後續任何「N 日窗」型分析都將系統性低估樣本；若屬已知的輪替/歸檔邏輯限制，應在相關 workflow 或 ADR 中明確記錄，避免重複誤判為資料異常。

多透鏡洞察

透鏡選擇

| 透鏡 | 角色 | 選用理由 |

|------|------|----------|

| distill-sam-altman | primary | 快速部署反饋閉環：先 ship 觀察層、用真實資料校正假設，而非閉門推導公式 |

| distill-jensen-huang | primary | demand-driven 設計：先看 workload（真實事件量級）再定義規格（confidence 公式係數） |

| distill-taleb | adversarial | 不對稱風險與 skin in the game：錯誤 instinct 一旦寫入 state 即不可逆 |

框架化建議

  • Altman 視角：07-26 草案公式從未在真實資料上跑過就被記錄為「設計完成」，這正是閉門造車而非用戶反饋閉環的反例。正確順序應是：先用觀察模式收集真實 (agent, tag) 分佈（已具備 17 天樣本），再迭代係數——本次實測即是遲到但正確的那一步；下一步應把「公式壓力測試」機制化為候選寫入前的強制檢核，而非等到下次研究輪次才偶然發現。
  • Jensen 視角：workload 先於規格——公式的 min(count,6) 上限顯然是憑空估計，未依真實 workload（33~283 次的事件量級）反推。全棧設計原則要求先量測「工廠」實際產線節拍（真實資料分佈），再回頭定規格；本次 17 天樣本已提供足夠 workload 特徵，係數不該再憑空假設，應直接用實測分佈的分位數（如 p50/p90/p99）反推飽和點。
  • Taleb 視角：一個把「發生 3 次」和「發生 283 次」評為幾乎相同信心分數的公式，是 fragile 的——它對真實訊號強度不敏感，卻會製造虛假的確定性外觀（0.80-0.85 看起來「差不多都很可信」）。Skin in the game 檢驗：若這個公式的分數被拿去自動寫 state/behavior-instincts.json，錯誤簇會在每次 auto-task 執行時被放大且不可逆——這正是本系列先前 briefing 已標記的 antifragile 預設拒絕（report-only + 人工 approved）之所以必要的具體反例，而非重複警告；此次是拿到了具體失敗數字（0.80-0.85 窄帶）的第一手證據，而非泛泛的風險提示。

反模式檢查

  • 未用「權衡利弊」掩飾飽和問題：公式失真是可驗證的量化事實（0.80-0.85 窄帶涵蓋 33~283 次的全部候選），非主觀判斷。
  • 未憑訓練記憶編造 arXiv:2606.22030v2 的具體機制——已用 WebFetch 覆核 Section 7-9 原文，確認 Noisy-OR 為對照組（BeliefMem，非本文方法）而非本文採用的機制，避免張冠李戴。
  • P0 修復「未閉合缺口」是實測結果陳述，非對前次工作的否定；已明確標示待查根因而非直接歸咎於 fallback 邏輯本身錯誤。

透鏡盲區自陳

  • Altman／Jensen 透鏡皆偏向「先 ship 再迭代」的產品節奏，可能低估寫入 state 前的人工 approved 閘門在單人 Windows 排程系統中的必要摩擦成本——此系列的既有設計（report-only 預設）已是務實折衷，非過度保守。
  • Taleb 透鏡對「已存在的 fabrication_guards P1-P4」重複強調 antifragile 預設，惟本輪已提供具體失效模式（公式飽和）作為佐證，非泛化警告，此次盲區風險較低。
  • 三透鏡均未覆蓋佛學／內容類 task（langgraph-jiaoguangzong、langgraph-jingtu、langgraph-fahua）在候選簇中的分布特性是否與技術類 task 有系統性差異——留待下輪按 task_family 切片分析。
