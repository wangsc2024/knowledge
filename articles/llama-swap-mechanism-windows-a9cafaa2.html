深度研究洞察簡報：llama-swap 動態模型卸載機制 mechanism 階段 — 換入換出延遲、Windows taskkill 行為與 DDP 12B/26B 並發率 POC 判準

insight-briefing深度研究洞察簡報llama-swapllama.cppVRAM管理本地LLMmechanism-stage

摘要

llama-swap 是目前唯一填補「llama.cpp 單卡多模型原生共存」空白的第三方工具，foundation 階段已確認其架構可行性，但缺乏實測數據。本次 mechanism 階段研究確認三項機制細節：Windows 平台以 taskkill +5 秒優雅期停止程序（無 POSIX 訊號）、port 依模型 ID 字母序 + startPort 確定性分配、以及 llama.cpp 官方（ggml-org）明確拒絕在核心內建 VRAM-based 自動卸載、只接受外部監控觸發。搜尋未找到 llama-swap 本身的官方換入換出延遲基準（僅有通用模型冷啟動 5-30 秒的粗估與 NVIDIA 另一套不同機制的 2-3 秒，兩者不可互換套用），這是本階段最大缺口——DDP 若要決定是否投入 POC，必須先機械化量測自身 12B/26B 呼叫並發率作為 go/no-go 判準。

關鍵洞見

  1. Windows taskkill 5 秒優雅期是 mechanism 階段的第一道風險閘：llama-swap 在 Windows 因缺乏 POSIX 訊號改用 cmdStop: taskkill，程序有 5 秒時間優雅關閉，逾時才強制終止。DDP 現有 llama-server 實例若無法在 5 秒內釋放 VRAM，換入下一模型會直接撞上與既有 12B/26B 共存 OOM 教訓相同的風險。
  1. llama.cpp 官方立場是刻意留白，非暫時缺口：ggml-org/llama.cpp Discussion #19425 顯示官方傾向讓「VRAM 監控」留在外部程式（透過 /models 端點暴露 last-used timestamp），而非把偵測邏輯內建進核心，與 DDP 既有 KB 洞見交叉驗證一致。
  1. Port 分配是確定性演算法，與 DDP 現行固定埠慣例衝突：startPort 設定 ${PORT} 起始值（預設 5800），實際埠號依模型 ID 字母序遞增分配。DDP 目前「8082 埠固定跑 12B」的慣例若要接上 llama-swap，需改成「透過模型命名控制埠序」。
  1. llama-swap 定位介於 Ollama 與 vLLM 之間，只在「請求時間不重疊」時划算：Ollama 自動熱插拔但併發請求排隊；vLLM 鎖定單模型換取 16-20 倍吞吐量；llama.cpp server 原生無動態卸載能力。換入換出延遲成本只有在 DDP 12B/26B 呼叫時間很少重疊時才划算。
  1. 本階段最大知識缺口：找不到 llama-swap 本身的官方延遲基準，且 DDP 自身並發率基線尚未量測；不應把通用模型載入或 NVIDIA 另一套機制的數字套用到 llama-swap 的延遲預算規劃。
  1. 資料中心級效能數字不可外推至 DDP 消費級環境：dasroot.net 案例基於 Linux + Docker + DGX Spark 128GB 統一記憶體，效能數字與 DDP 的 Windows + 單卡 24GB 環境不可比。

POC go/no-go 判準

| 判準 | Go | No-go |

|------|-----|-------|

| 12B/26B 呼叫時間窗重疊率 | 低（如 <20% 落在彼此 30 秒內） | 高（常態同時服務） |

| 現有兩顆常駐 server VRAM 總和 vs 24GB 卡上限 | 逼近/超過上限 | 尚有餘裕 |

| 現有 server 乾淨關閉耗時 | 可在 taskkill 5 秒優雅期內完成 | 需強制終止，OOM 風險高 |

下一步（application 階段前提）：先機械化量測 DDP 12B/26B 實際呼叫的時間重疊率（比對 post_tool_logger.jsonl 或各 llama-server port 請求時間戳），作為 go/no-go 第一手數據。
