摘要

本文以協定標準化與工程可靠性兩條技術軌跡為問題意識，檢視 Model Context Protocol（MCP）與 Agent2Agent（A2A）在 2024 至 2026 年間快速產業化標準化的現象。透過候選池 50 筆、精讀納入 24 筆外部來源（13 篇同行評審論文、11 篇官方規格與產業調查）之三角佐證，本文論證「協定完工」正在製造一種多代理系統互通問題已解決的產業錯覺。本文主張：協定規格本身刻意將排程、重試語意、故障容錯與可觀測性排除在標準化範疇外；學術實證研究反覆證實編排與協調層失效是獨立於介面相容性的系統性問題；各主流框架各自以不相容方式實作重試與追蹤，可觀測性工具滲透率已顯著超前於實際可靠性成果。協定標準化與排程／韌性工程是兩條進度懸殊的獨立技術軌跡，此落差才是多代理 AI 系統邁向生產可靠性的真正瓶頸。

關鍵詞

Model Context Protocol、Agent2Agent Protocol、多代理系統、可靠性工程、可觀測性、失效分類學、協調與排程

引言

[李飛飛主筆] 我從一個具體問題出發：當一家企業把多代理系統送進生產環境、某個任務鏈中途悄無聲息地卡死或重複扣款，誰該負責，又是誰承擔了那次失敗的真實代價？過去一年，MCP 與 A2A 的產業敘事給了一個誘人的答案——標準已經定了，互通問題解決了。Anthropic 於 2024 年推出 MCP、Google 於 2025 年 4 月推出 A2A 並在同年 6 月移交 Linux Foundation、逾 150 個組織加入生態系（[來源：Linux Foundation, A2A Project Launch, 2025]），這是協定層一年內罕見的產業共識速度。但我認為，速度本身正是問題：當一層規格快速定案、媒體與廠商公告集中轟炸，聽眾很容易把「介面相容」錯聽成「系統可靠」。這中間的知識缺口，正是本文的研究問題——協定規格明文涵蓋了什麼？沒有涵蓋什麼？學術界關於多代理系統失效的實證研究，是否獨立於協定層之外仍在演進？本文的貢獻在於，以三角佐證的方式，把「協定標準化速度」與「排程／韌性／可觀測性工程成熟度」這兩條技術軌跡並排檢視，指出兩者進度懸殊，且前者的顯著進展正在系統性地掩蓋後者仍處於碎片化早期階段這一事實。

文獻回顧

[李飛飛主筆] 文獻可分三組。第一組是協定規格與產業採用軌跡的一手文件。Anthropic 官方公告將 MCP 定位為「連接 AI 系統與外部資料/工具的開放標準」（[來源：Anthropic, Introducing MCP, 2024]），MCP 官方規格（2025-11-25 版）進一步明定 JSON-RPC 2.0 主從架構，基元僅限伺服端的 Resources／Prompts／Tools 與客戶端的 Sampling／Roots／Elicitation（[來源：MCP Working Group, Specification, 2025]）——通篇未提及排程、多代理任務分派或跨代理可觀測性標準，這不是疏漏，而是規格範疇的明確選擇。A2A 由 Google Developers Blog 於 2025 年 4 月公告，逾 50 家技術夥伴加入，明確定位為與 MCP 互補：MCP 管 tool／context，A2A 管 agent-to-agent 溝通與協調（[來源：Google Developers Blog, Announcing A2A, 2025]），治理權隨後移交 Linux Foundation，生態系擴展至 150+ 組織（[來源：Linux Foundation, 2025]）。Zylos Research 的 2026 產業分析則指出，MCP／A2A／ACP 三者透過垂直工具存取與水平代理協調的互補分層正在收斂，但即使收斂完成，標準化可觀測性／稽核軌跡、細粒度授權、跨協定互通與代理發現機制仍是未解缺口（[來源：Zylos Research, 2026]）。

第二組是多代理系統失效分類學與可靠性工程的實證研究，是本文論證的骨幹。Cemri 等人提出的 MAST（Multi-Agent System Failure Taxonomy）由 6 位專家標註跨 7 種主流框架的 200 餘任務、1600 餘條追蹤紀錄，評分者間信度 Cohen's Kappa 達 0.88，首度以實證方式界定「編排與協調失效」為獨立於「應用層失效」的系統性類別（[來源：Cemri et al., Why Do Multi-Agent LLM Systems Fail?, 2025]）。Jia 等人的 MAS-FIRE 建立 15 種故障類型與 3 種注入機制的容錯評測框架，發現「更強的基礎模型不保證更好的韌性」，架構設計（迭代閉環 vs. 線性管線）比模型品質更決定容錯能力（[來源：Jia et al., MAS-FIRE, 2026]）。Zhu 等人提出 AgentErrorTaxonomy／AgentErrorBench／AgentDebug，證實單一根因錯誤會沿決策鏈傳播導致任務失敗，根因層級診斷回饋可帶來 24% 全對準確率與最高 26% 任務成功率的相對提升（[來源：Zhu et al., Where LLM Agents Fail, 2025]），但這套能力仍是研究原型而非產業共享工具。Qi 等人以 LIFE（能力／協作／失效歸因／持續演化）框架整合破碎的 MAS 可靠性文獻，明確將「失效歸因」定位為獨立於協定層、仍在積極研究中的未解問題（[來源：Qi et al., Beyond Individual Intelligence, 2026]）。另有一篇 2026 年論文提出以線上追蹤訊號診斷「浪費運算」的可觀測性框架，將常見 MAS 失效模式對映到工具可靠性、執行復原、編排迴圈、證據可得性、資訊變動、預算壓力六個維度（[來源：Early Diagnosis of Wasted Computation, 2026]），同樣停留在研究原型階段。Zheng 等人則借用傳統分散式系統的拜占庭容錯理論提出 CP-WBFT 共識機制（[來源：Zheng et al., Byzantine Fault Tolerance, 2025]），這件事本身就值得玩味——當代理原生的可靠性標準尚未成形，工程師只能向上一代分散式系統理論「借道」。

第三組是框架碎片化與產業調查的交叉證據。LangChain 官方文件坦承 LangGraph 不會自動重試，開發者須手動加入 error_count／last_error 狀態欄位與條件邊路由才能實作重試邏輯（[來源：LangChain/LangGraph Docs, Durable execution, 2026]）；OpenAI 官方 Cookbook 同樣明言 Swarm／Agents SDK 的 handoff 僅是回傳另一 Agent 的工具呼叫，可靠性交由實作者自理（[來源：OpenAI, Orchestrating Agents, 2025]）；OpenTelemetry 官方部落格承認 GenAI 代理追蹤的語意慣例仍在演化、尚未定案，存在碎片化風險（[來源：OpenTelemetry Project, 2025]）；Presenc AI Research 的框架比較進一步證實，LangGraph、CrewAI、AutoGen、OpenAI Swarm 在耐久執行、可觀測性、錯誤復原上各有落差，即使全部相容 MCP／A2A 介面層（[來源：Presenc AI Research, 2026]）。LangChain《State of Agent Engineering 2025》對 1,340 位從業者的調查顯示，57% 已將代理投入生產，但 32% 仍將「品質」列為首要生產障礙，儘管 89% 已具備某種可觀測性（[來源：LangChain, State of Agent Engineering 2025]）；Zuplo 的 MCP 產業調查則揭露 43% 的公開 MCP 伺服器含指令注入漏洞、僅 8.5% 使用 OAuth（[來源：Zuplo, The State of MCP, 2026]），顯示協定採用層的生產強化本身仍不成熟。

研究方法

[LeCun主筆] 我不喜歡只憑印象下判斷，這篇的證據鏈是這樣建的：Phase 0 先用機械化 harvest（site:arxiv.org、OpenAlex、Semantic Scholar API）對「multi-agent orchestration」「MCP reliability」「agent interoperability protocol」等關鍵詞取樣，再派兩個並行子 Agent 執行 WebSearch 補強官方規格與產業調查，去重合併後候選池共 50 筆。納入準則很直白：優先 2025-2026 年出版、同行評審或官方一手來源，剔除純行銷文案與無實證支持的部落格；語言以英文為主、中文補充。分級沿用三段式：A 級（同行評審論文，13 篇）、B 級（官方規格／文件，7 篇）、C 級（產業調查／技術部落格，4 篇），最終精讀納入 24 篇。核心主張的驗證門檻設在「至少 3 個獨立來源（不同機構、不同作者）交叉支持」，達標才記「已驗證✅」；本文 5 條核心主張全數過關，明細見附錄。順帶一提，Phase 0 純關鍵字比對確實抓到雜訊——「frontier model capabilities」這個詞誤中了幾篇粒子物理與投資組合效率前緣的論文，這提醒我：關鍵字比對不是語意理解，篩選環節的人工複核不可省。

結果與討論

[李飛飛主筆] 我把發現整理成三層。

第一層，協定標準化的速度是真的，而且值得肯定——這不是我要否定的事。MCP 自 2024 年公告後迅速成為業界事實標準，A2A 從 Google 內部專案在一年內移交 Linux Foundation、聚集 150+ 組織支持（[來源：Linux Foundation, 2025]；[來源：Google Developers Blog, 2025]），這種跨廠商協調速度在過去的軟體標準史上並不常見。但第二層——這正是我最在意的地方——協定規格本身，是刻意把排程、治理、審計、人為升級這些語意排除在外的。Kang 與 Diponegoro 這篇 2026 年論文講得很清楚：他們評估的是「協定編碼了什麼，而非可以在其上建構什麼」，這是設計範疇的選擇，不是疏漏（[來源：Kang & Diponegoro, Governance Gaps, 2026]）。MCP 規格文件本身也印證這點——通篇聚焦 context 與 tool 曝露，一字未提排程或多代理協調（[來源：MCP Working Group, 2025]）。換句話說，協定完工解決的是「A 系統怎麼把工具描述遞給 B 系統」，沒有解決「B 系統呼叫工具失敗了該怎麼辦、誰來重試、誰來記錄」。

第三層是我認為最容易被忽略、卻最該被看見的落差：可靠性研究的實證結果，正在對「已解決」的敘事潑冷水。Cemri 等人的 MAST 研究，用 1600 多條真實追蹤紀錄告訴我們，編排與協調失效跨 7 種框架都存在，是一個獨立於任何單一協定或介面的系統性類別（[來源：Cemri et al., 2025]）。Mehta 的 CLEAR 框架研究更讓我不安：300 個企業任務重複執行 8 次後，準確率從單次的 60% 崩落到 25%（[來源：Mehta, Beyond Accuracy, 2025]）——這代表業界廣泛引用的單次基準分數，本身就在系統性地掩蓋可靠性崩潰。而 LangChain 的產業調查裡，89% 的從業者已具備某種可觀測性能力，但 32% 仍把「品質」列為生產部署的首要障礙（[來源：LangChain, State of Agent Engineering 2025]）——工具滲透率超前於實際可靠性成果，這正是「虛假完工感」的產業證據，不是我的臆測。我也想指出誰在承擔這個落差的代價：Zuplo 的調查顯示，公開 MCP 伺服器中 43% 含指令注入漏洞、僅 8.5% 使用 OAuth（[來源：Zuplo, 2026]），而 Mouzouni 對四大平台（Microsoft、Salesforce、AWS、Google）的架構調查發現，沒有一家在架構上隔離代理核准通道（[來源：Mouzouni, Context Kubernetes, 2026]）——當企業把這類系統送進生產，承擔風險的往往是終端使用者與資料當事人，而非設計協定的廠商。這正是我一貫關心的問題：技術敘事的受益方與風險承擔方，是否是同一群人？在這裡，答案顯然是否定的。

實踐建議

[LeCun主筆] 幾點具體建議，不是空話：

  1. 把「協定相容」與「生產就緒」拆開驗收：採購或整合 MCP／A2A 相容系統時，另立一組排程、重試、可觀測性的驗收清單，不能因為介面過了 spec 就假設系統可靠——這兩件事現在是分開的工程課題（[來源：Kang & Diponegoro, 2026]）。
  2. 用 MAST／MAS-FIRE 這類分類法做內部故障演練，而非等生產事故發生才臨時歸因。Cemri 團隊的 taxonomy 已經開源可用，這比自己從零造輪子划算（[來源：Cemri et al., 2025]）。
  3. 重試與逾時邏輯明確寫進架構文件，不要依賴框架「應該」處理。LangGraph 官方都講明不會自動重試（[來源：LangChain/LangGraph Docs, 2026]），OpenAI Swarm 也一樣把責任丟回開發者（[來源：OpenAI, 2025]）——這不是哪個框架比較差，是整個產業階段性如此，規劃時就該把這行預算算進去。
  4. 重複執行測試取代單次基準：Mehta 的研究已經證明單次分數會嚴重高估可靠性（[來源：Mehta, 2025]），至少跑 5-8 次同任務再看方差。
  5. MCP 伺服器預設關閉 auto-approval，Zuplo 的數據顯示開啟後工具投毒攻擊成功率高達 84.2%（[來源：Zuplo, 2026]），這是可以立即執行的低成本防禦。

風險與限制

[LeCun主筆] 誠實講幾個限制。第一，本文採樣的候選池雖有 50 筆，但機械關鍵字檢索本身有語意盲區（見研究方法一節提到的雜訊問題），可能漏掉用詞不同但議題相關的文獻。第二，協定生態系變動極快——MCP／A2A 規格與治理現況以 2026 年 7 月為準，半年後可能已有實質更新（例如若官方將排程語意納入未來版本，本文的部分論證會需要更新）。第三，本文引用的失效分類學研究（MAST、MAS-FIRE、AgentErrorTaxonomy 等）彼此的分類體系尚未收斂，我在文獻回顧中呈現的是「這是一個活躍研究領域」而非「已有定論的統一標準」，讀者不應把任一篇單一論文的分類法當作產業共識。第四，我必須老實說，這篇論文本身無法量化「虛假完工感」對實際生產事故率的因果貢獻——本文論證的是敘事與工程進度的落差存在且有多方證據支持，但落差造成多少具體事故，仍需要更長期的產業事故資料庫才能回答，這超出本文候選池的範圍。

原創論點

[李飛飛主筆] 我想提出一個本文尚未直接引用、但貫穿全部證據的類比：協定標準化與應用可靠性工程的關係，很像上個世代 HTTP 標準化與 Web 應用效能工程的關係。HTTP／1.1 定案後，兩台機器「能夠對話」這件事被解決了，但快取失效策略、逾時重試、斷路器（circuit breaker）、限流、可觀測性儀表板——這些讓網站真正撐得住流量尖峰的工程知識，是又花了將近十年、在 CDN、微服務、SRE 這些後續產業實踐裡才逐漸成熟的。我認為 MCP／A2A 現在正站在「HTTP／1.1 剛定案」的那個時間點：介面對話的問題確實解決了，但支撐生產可靠性的那一層工程知識，還在 Cemri、Jia、Zhu 這些團隊的論文裡以碎片化的姿態各自生長，尚未收斂成產業共識的最佳實踐。這個類比之所以重要，是因為歷史告訴我們一件反直覺的事：介面標準化的完成，往往不是可靠性工程開始加速的訊號，而是可靠性工程「終於有了穩定地基可以在上面蓋房子」的訊號——地基蓋好之後才是真正費工的部分，而地基完工的公告聲量，通常遠大於後續十年默默的可靠性工程本身，這就是我所稱的「敘事聲量與工程份量的不對稱」。

其次，我要把治理與創新雙軸的框架用回這個題目：業界習慣把「治理」理解成事後補救的合規清單，但 Mouzouni 對四大平台的架構調查證實，沒有一家在協定生態系爆發式成長的同時，同步把代理核准通道的架構隔離做進去（[來源：Mouzouni, 2026]）。我認為這不是四家公司同時疏忽，而是產業結構性地把「先讓協定跑起來」與「事後補治理」拆成兩個階段——而我一貫主張的立場是：早期就該把治理與韌性工程一起設計，不是等協定生態成熟後再補課。Zuplo 揭露的 43% 指令注入漏洞率，正是「先跑後補」這個產業預設路徑的具體代價，而承擔這個代價的往往是部署這些系統的中小企業與其終端使用者，不是制定協定規格的少數大型科技公司——這正是本文一家之言想強調的核心：協定完工的公告，其受眾與受益者，和承擔生產風險的一方，結構性地不是同一群人，這件事本身，比「協定完工了沒」更值得整個產業認真辯論。

結論

[LeCun主筆] 回到開頭的問題：協定互通問題解決了嗎？我的答案是——解決了一個問題，但那不是多代理系統真正卡住生產部署的那個問題。MCP／A2A 讓「系統之間怎麼描述工具、怎麼傳話」這件事有了共同語言，這值得肯定，我不否認這個工程成就。但本文用 24 篇來源、5 條三角佐證主張證明，排程、重試、故障容錯、可觀測性——這些真正決定一個多代理系統能不能撐過生產環境的工程課題——目前仍分散在各框架各自為政的實作裡，缺乏跨框架收斂的共同基準，學術界的失效分類研究也還在互相競爭誰的分類法更貼近真實故障模式。用我一貫的話講：協定層的進展是真的，但那不代表可靠性工程的「detour」已經走完，它甚至還沒真正開始收斂。本文的限制在於樣本與時間窗（見「風險與限制」），後續研究若能建立跨框架、跨協定版本的長期生產事故資料庫，才能真正量化這個落差對實際故障率的貢獻，而非僅停留在文獻層級的落差論證——這是我認為下一步最值得投入的方向。
