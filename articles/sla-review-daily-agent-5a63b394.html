深度研究洞察簡報：sla_review_daily agent_crash 防護與監控盲點

日期：2026-07-18

系列：sla_fix / monitoring-blind-spot

觸發 backlog：backlog_task_failure_optimizer_20260704_160500469529（pending 12.79 天）

摘要

2026-07-03 sla_review_daily 以 agent_crash 失敗，當日 SLA 清零管線未執行，形成監控任務自身的監控盲點。本簡報交叉比對 DDP 既有 fail-safe 雙層佔坑（templates/shared/preamble.md + run-todoist-agent-team.ps1 L1539-1551）、results/ transient 語義（prompts/CLAUDE.md）、業界 silent failure 文獻（Boundev 2026、Frank Yao heartbeat/enforcer 模型）與 Argus/Sotis 步驟級不變量檢查，萃取 6 項核心洞見，套用 3 組思考透鏡（Sam Altman／黃仁勳／Taleb），提出以機械心跳 + LLM 路徑隔離為主的防護路線。

關鍵洞見

1. 監控任務失敗 = 結構性盲點，非一般任務失敗

context/improvement-backlog.json 記錄：2026-07-03 sla_review_daily 以 failure_type: agent_crash 失敗，monitoring_blind_spot: true。當日 backlog_sla_check 未跑完，violations 無法清零，workflow-closure-audit 持續標記 high_pending_unstarted（2026-07-17 仍 12.79 天滯留）。

證據：docs/audit-reports/workflow-closure-audit-2026-07-17.md P1-001 首條即為本議題。

2. DDP 已有 fail-safe 佔坑，但 agent_crash 發生在「佔坑之前」或「佔坑未被覆寫」

Phase 2 雙層保障：PS1 in_progress 佔坑 + Agent 首個 Write 寫 status: failed 的 Fail-Safe JSON（preamble.md L84-109）。run-todoist-agent-team.ps1 L1539-1551 偵測「任務啟動於…未完成主要步驟」並升級診斷。

缺口：若 Cursor CLI 程序在讀 preamble 之前 OOM／被 kill，或 crash 發生於 ps1_native 子程序且未寫結果檔，Phase 3 僅見 result_file_missing 或 placeholder，無法區分「未啟動」與「啟動後中途死亡」。

3. 跨輪監控讀 `results/` 是已知反模式

prompts/CLAUDE.md 明確：results/todoist-auto-*.json 為 transient，Phase 3 成功後 PS1 刪除；跨輪應讀 context/continuity/auto-task-{key}.json。2026-04-21~27 workflow-health-monitor 曾因讀 results 誤判「未執行」。

對 sla_review_daily：健康度應以 state/sla-remediation-last-run.json、state/backlog-sla-report.json 與 continuity 為準，而非 results 殘檔。

4. 業界共識：Agent 的「靜默失敗」比 HTTP 5xx 更危險

Boundev（2026）與 Tessary（2026）指出：Agent 可回傳語意正確、實務錯誤的輸出，基礎設施監控只看 200/exit 0 會漏報。Frank Yao 的 heartbeat 模型：排程任務應寫入「我完成了什麼」的週期信號，沉默即失敗。

DDP 映射：sla_review_daily 應在步驟 1（SLA report 刷新）後即寫 heartbeat，而非等 LLM remediation 結束才寫結果。

5. sla_review_daily 架構：ps1_native 外殼 + LLM gate 梯次為 crash 高風險區

prompts/team/todoist-auto-sla_review_daily.md：主流程由 scripts/auto-task-sla_review_daily.ps1 機械編排；僅在 violations_before>0 時走 Invoke-LlmGate profile=sla_remediation（kill switch DDP_SLA_REMEDIATION_LLM=off → apply-mechanical）。

推論：07-03 crash 最可能發生在 LLM 梯次或資源爭用（backlog 描述提及 VRAM），而非機械 SLA 檢查本身。防護應隔離 LLM 路徑，確保機械層單獨可完成 violations 報告與 ntfy。

6. 最小可行防護：heartbeat + 機械兜底 + agent_crash 專屬 escalate

| 層級 | 動作 | 成本 |

|------|------|------|

| L0 | 每步寫 state/sla-review-heartbeat.json（step、timestamp、violations_count） | 數行 PS1 |

| L1 | agent_crash 後自動 DDP_SLA_REMEDIATION_LLM=off 重跑機械層 | 已有 kill switch |

| L2 | phase_failure sub_category=agent_crash 觸發 ntfy priority=4（Update-FailureStats L1339） | 接線 backlog |

無需新建獨立 Skill；符合 ponytail「停在既有資產／標準庫」階梯。

框架化建議

Sam Altman 透鏡：SLA 清零是「必須跑通」的關鍵路徑，不能因 LLM 實驗性步驟阻塞。先讓機械層 100% 可觀測（heartbeat + violations 數字），再疊 LLM 優化——對齊「安全不能事後補」但不阻斷出貨的節奏。

黃仁勳透鏡：failure-stats.json 已有 agent_crash 子類（run-todoist-agent-team.ps1 L1339）；sla_tier_executor apply-mechanical 已存在。不要新建 EIR/ECR 式管線，把三個既有鉤子接線：stats → heartbeat 缺失告警 → mechanical 重跑。

Taleb 透鏡（反模式檢查）：把「SLA 任務成功」定義成「LLM remediation 完成」是 fragile——單點 LLM crash 讓整個監控失明。應改為 antifragile：LLM 失敗時自動降級機械處置並放大可觀測性（更高 priority ntfy），讓失敗暴露問題而非隱藏。

透鏡盲區自陳

  • 三透鏡均非 SRE/排程領域專家，具體 heartbeat 間隔需依 config/timeouts.yaml（sla_review_daily: 1800s）實測校準。
  • 07-03 原始 stderr 日誌本輪未逐行稽核（backlog 建議①），crash 根因仍為推論而非實證。
  • 外部文獻（Argus/Sotis）為通用 Agent 管線，與 DDP ps1_native 架構需人工映射。

建議行動

  1. 本週：在 auto-task-sla_review_daily.ps1 步驟 1 後寫 heartbeat；check-health.ps1 加「heartbeat >26h 未更新」告警。
  2. 本週：agent_crash 路徑文件化為 DDP_SLA_REMEDIATION_LLM=off 自動重試（一次）。
  3. 下週：關閉 backlog backlog_task_failure_optimizer_20260704_160500469529 前，用 07-18 後連續 3 天 violations 報告驗證。
