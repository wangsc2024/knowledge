Agent OS 的第一課：會分工，才會用 Agent

摘要

單一 AI 對話框已無法承載複雜工作，產業正從「找最強單一模型」轉向「拆解工位、分工協作」。實務案例（Axton Liu 的四工位設計）與理論框架（Agentic OS、多智能體協作模式）共同指向同一結論：Agent 系統的關鍵不在模型強弱，而在任務拆解、角色分工與人機邊界的設計 [G1][G2][G3]。

背景與現況

AI 工具的使用正經歷一次典範轉移。早期使用者將 ChatGPT、Claude、Codex 等工具視為「一個對話框干到底」的萬用助手——把所有需求丟進單一輪對話，期待模型一次到位完成研究、整理、判斷全部工作。但當任務規模擴大（例如數十個瀏覽器標籤、數百篇稍後讀文章長期積壓未處理），這種用法迅速失靈：模型容易在混雜任務中產生錯誤，使用者也無法追蹤問題出在哪個環節 [G1]。

Axton Liu 在影片中提出的解法不是尋找更強的模型，而是把單一任務拆成「抓取、提煉、核查、確認」四個工位，讓不同 Agent 分別負責流程中的一段，並刻意在提煉工位埋入錯誤資訊以測試核查工位能否揪出 AI 編造的數字與結論 [G1]。這種思路與學術界近年發展的 Agentic OS 概念相互呼應：後者主張 Agent 應從「一次性推理請求」升級為「持續運行的數字員工」，需要目標—規劃—工具調用—執行—反思的閉環，而非傳統作業系統「啟動—運行—結束」的進程模型 [G2]。同時，商業化多智能體平台（如 Kimi Agent Swarm）也將「基於角色的協作」（Role-based Collaboration）列為常見模式之一，讓不同智能體專注編碼、測試、除錯、部署等子任務 [G3]。三份材料分別代表實務教學、系統架構理論、商業產品文檔三個層次，共同印證「分工先於強度」已是產業共識。

機制與技術分析

工位拆解的核心邏輯

Axton Liu 的四工位設計本質上是一條資訊處理管線（pipeline），每個工位承擔單一、明確定義的職責：

  1. 抓取工位：從稍後讀 / 剪藏庫讀入標題、網址與已存正文，刻意不讓 AI 現場重新抓取原始網頁內容 [G1]。
  2. 提煉工位：將每頁正文提煉為要點，並判斷該內容是否值得保留 [G1]。
  3. 核查工位：帶著提煉出的筆記回頭比對原文，逐條核實，專門用來抓 AI 在提煉過程中「編出來」的數字與結論 [G1]。
  4. 確認工位：把核查結果彙總為「待確認提案」，只提出建議，不代替使用者執行刪除或保留的動作 [G1]。

這個設計呼應了 Kimi 資源頁定義的多智能體協作五要素模型：基礎模型（m）、目標（o）、環境（e）、感知（x）、輸出/行動（y）[G3]。對照來看，Axton 的每個工位其實就是一個獨立配置了目標與感知範圍的 Agent 實例——抓取工位的「環境」被限定在剪藏庫，提煉工位的「感知」僅來自抓取工位的輸出，核查工位再回頭比對原始環境（原文）以校驗提煉工位的行動是否忠實。這種限定感知範圍的設計本身就是一種風險控制手段：每個工位只能看到它該看到的資料，減少了單一 Agent 因上下文過載而產生幻覺的機會。

核查機制：用結構對抗幻覺，而非靠更強模型

材料中最值得深挖的技術細節，是核查工位的存在邏輯：提煉工位天生有editorializing（加工失真）的風險，尤其是把長文壓縮成要點時，AI 容易「腦補」出原文沒有的數字或結論。Axton 刻意在提煉階段埋雷測試，再用核查工位「回原文抓假數字」，這相當於在管線中插入一道獨立於生成路徑的驗證關卡（[G1] 時間戳 9:06、10:57）。這個做法與 Agentic OS 理論中強調的「Behavioral Audit（行為審計）」和「Tool Governance（工具治理）」概念在精神上一致——都是承認 Agent 輸出不可盲信，必須有系統層級的事後校驗機制，而非依賴模型自律 [G2]。

確認邊界：人機協作的治理紅線

四工位中最關鍵的收尾設計，是「確認邊界」：AI 可以整理、核查、提出建議，但刪除、保留、採信與否的最終決策權必須留給人類，否則知識庫可能被悄悄改壞而使用者渾然不覺 [G1]。這與 Agentic OS 論述中「Agent 自主執行能力越強，潛在風險也越高」的警示直接對應——原文列舉 Agent 若無節制地自動調用 API、操作資料庫、執行 Shell 命令，可能導致越權存取、高風險誤操作等系統性風險，因此需要 Fine-grained Permission（細粒度權限控制）與 Policy Engine（策略引擎）等治理機制 [G2]。Axton 的「只給建議、不代替動手」正是這套治理思想在個人知識管理場景的極簡實踐版本：不需要複雜的權限系統，只需要在流程設計上預留一個人工核准節點。

上下文私有化：模型可替換，上下文屬於使用者

影片提出「模型是租來的，上下文是自己的」（[G1] 時間戳 14:33）這一觀點，點出了 Agent OS 設計中容易被忽略的資產歸屬問題。工位化設計讓抓取、提煉出的中繼資料（要點、核查記錄、待確認提案）以標準化格式沉澱在使用者自己的工具鏈中（如 Obsidian），而非鎖死在特定模型供應商的對話記錄裡。這與 Agentic OS 理論中「AI 原生記憶系統」的四層記憶結構（Working / Episodic / Vector / Reflection Memory）呼應：真正有價值的長期資產是這些結構化記憶，而不是任何單一模型本身 [G2]。

應用與實務啟示

對個人知識工作者與開發者而言，這套思路的可落地啟示包括：

  1. 先拆流程，再選工具：在導入 Agent 之前，先把任務拆解成有明確輸入/輸出邊界的工位（如「抓取→提煉→核查→確認」），再決定每個工位用哪個工具（Claude Code、Codex、ChatGPT 皆可，[G1] 特別說明沒有安裝 Codex / Claude Code 的使用者也能用同一套提示詞在 ChatGPT 對話框中手動接力完成，時間戳 15:39）。這代表工位化設計本質上是「流程規格」而非「工具綁定」，具備跨工具遷移能力。
  2. 核查工位是必要成本，不是可選項：任何涉及「AI 摘要/提煉大量原始資料」的場景（讀書筆記、會議記錄、研究彙整），都應該預留一道獨立的回原文核查步驟，尤其是數字、日期、結論性陳述這類最容易被幻覺污染的內容類型。
  3. 明確設定人工確認節點：對於會修改既有資產（知識庫、資料庫、程式碼庫）的 Agent 流程，應在架構設計階段就劃定「AI 只能提案、人類才能執行」的邊界，這比事後補救更可靠。Kimi 資源頁列舉的「軟體工程與開發自動化」場景也印證了同一原則——編碼、測試、除錯、部署雖可分派給不同 Agent，但整合與最終合併通常仍需人工把關 [G3]。
  4. 多智能體協作模式的選型：Kimi 資源頁歸納的三種協作模式（基於規則、基於角色、基於模型）可作為架構決策參考——結構化、可預測的任務（如 Axton 的四工位）適合「基於角色的協作」，而需要處理不確定性與動態環境的任務則可能需要「基於模型的協作」（依賴機率推論與貝葉斯更新）[G3]。

觀點與趨勢判讀

三份材料呈現出清晰的三角印證關係：[G1] 是一線實務教學，示範「小而具體」的分工方法論；[G2] 是系統層級的理論框架，試圖為 Agent 協作建立作業系統等級的抽象（消息總線、調度器、共享記憶、沙箱）；[G3] 則是商業產品文檔，展示廠商如何把多智能體協作包裝成可直接調用的產品能力（Kimi Agent Swarm）。三者雖然材料互為孤證、彼此未直接引用，但描述的核心機制高度一致——這種跨來源、跨層級（教學/學術/商業）的收斂，本身就是對「分工協作是 Agent 系統下一階段核心命題」這一判斷的有力佐證。

值得指出的判讀是：[G1] 的四工位設計本質上是 [G2] 理論框架與 [G3] 協作模式在「個人知識工作」這一具體場景的輕量化落地——它沒有使用消息總線、策略引擎等重型基礎設施，而是用「提示詞 + 人工確認」達成同等的治理效果。這說明 Agentic OS 式的系統級能力（權限治理、行為審計、語義通信）不一定需要等待廠商提供完整平台才能實踐；個人使用者現在就可以用提示詞工程手動模擬出簡化版的工位隔離與審計機制。

尚未定論之處在於：當任務規模從「個人知識庫整理」擴大到「企業級多 Agent 系統」時，[G1] 式的人工確認邊界是否仍可擴展？[G2] 提出的 Agent Sandbox、Policy Engine 等基礎設施正是為了解決這個擴展性問題而生，但材料中並未提供實證數據說明這些機制在生產環境的實際效果，這是三份材料共同的空白地帶，也是判斷「Agent OS」是否會成為真正產業標準的關鍵未定變數。
