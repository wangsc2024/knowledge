ReDoS 漏洞如何發生

技術深度研究daily-agent

主筆說明

我以 craft-clear、craft-rigor 視角撰文，基於公開言論與研究材料推斷，非本人觀點。選角理由：craft-clear清晰技藝視角; craft-rigor嚴謹工程視角

摘要

本研究報告旨在深入探討正規表達式拒絕服務攻擊（Regular Expression Denial of Service，簡稱 ReDoS）的技術成因、運作機制及其對現代軟體架構的影響。隨著網路應用程式高度依賴正規表達式進行輸入驗證、資料解析與內容過濾，ReDoS 已成為一種極具威脅的安全性漏洞，其核心問題在於傳統正規表達式引擎在處理特定複雜模式時，會陷入「災難性回溯」（Catastrophic Backtracking）的陷阱。當攻擊者提供精心構造的惡意字串時，引擎會嘗試所有可能的匹配路徑，導致 CPU 資源被耗盡，進而造成服務掛起或完全癱瘓。

核心問題：災難性回溯與複雜度爆炸

ReDoS 的核心技術問題源於回溯式（Backtracking）正規表達式引擎的運作邏輯。大多數主流語言（如 JavaScript、Python、Java）採用的引擎在面對嵌套量詞（Nested Quantifiers）或重疊字符類（Overlapping Character Classes）時，若輸入字串無法完全匹配，引擎會嘗試回溯到之前的狀態並重新嘗試不同的匹配路徑。例如在模式 ^((a+)+)$ 中，當輸入為 aaaaa! 時，由於 a 的重複匹配存在多種組合方式，引擎必須窮舉每一種可能性。根據研究顯示，這種路徑的數量會隨著輸入字串長度的增加呈指數級增長，導致僅僅 30 個字符的輸入就可能讓 CPU 占用率達到 100% 並持續數分鐘（https://safeguard.sh/resources/blog/regular-expression-denial-of-service-redos-explained）。這種從線性時間複雜度轉變為指數級複雜度的現象，正是 ReDoS 攻擊得以發生的根本原因。

研究方法：引擎對比與實務識別

本研究採用多維度的分析方法來剖析 ReDoS。首先，透過對比不同正規表達式引擎的設計架構，我們分析了傳統 PCRE（Perl Compatible Regular Expressions）與 Google 開發的 RE2 引擎之間的差異。PCRE 採取「樂觀」策略，雖然提供了強大的功能如回溯引用與複雜前瞻，但其設計本質上容易受到 ReDoS 攻擊。相較之下，RE2 採用 NFA（Nondeterministic Finite Automaton）編譯，保證了線性時間複雜度，從根本上避免了 ReDoS 問題（https://github.com/google/re2）。此外，研究亦參考了 Rust 生態系中的 regex crate，該實作高度參考 RE2 的安全設計，旨在提供預測性的性能保證（https://stemjail.github.io/rustdoc/regex/index.html）。

在實務識別層面，本研究強調了性能監測與靜態分析的結合。透過觀察性能指標，若特定字串的匹配耗時與長度呈非線性增長（例如 20 字元耗時 10ms，而 25 字元耗時 500ms），則高度疑似存在 ReDoS 漏洞（https://blogs.jsmon.sh/what-is-regular-expression-denial-of-service-redos-ways-to-exploit-examples-and-impact/）。

主要發現與取捨：安全性與功能的權衡

研究的主要發現指出，ReDoS 的防禦與解決方案存在顯著的「功能與安全性權衡」。回溯式引擎雖然在處理複雜匹配場景（如需要複雜回溯引用或特定前瞻斷言）時更具靈活性，但其安全性風險極高。特別是在 Node.js 等單執行緒環境中，任何 CPU 密集型的正規表達式匹配都會直接阻塞事件循環（Event Loop），導致整個應用程式無法處理任何新請求（https://www.myutilitybox.com/blogs/regex-catastrophic-backtracking-nodejs）。

為了對抗此類風險，目前的解決方案主要分為兩大方向：一是從底層引擎切換，如採用 RE2 或 Rust 的 regex 庫，這些引擎透過限制特定語法（如禁止回溯引用）來換取固定的線性時間性能（https://en.wikipedia.org/wiki/RE2_(software)；https://rust-locale.github.io/rust-locale/regex/index.html）。二是透過開發特定的防禦機制，如在輸入驗證前限制字串長度、使用更精簡的正規表達式模式，或在 WAF 層級攔截明顯的惡意模式（https://payloadplayground.com/blog/regular-expression-denial-of-service-redos-explained）。然而，目前仍缺乏通用的自動化工具能將複雜的回溯表達式完美轉換為線性時間的 RE2 兼容表達式，這意味著在許多遺留系統中，開發者仍需進行手動重構以確保系統的健壯性。

關鍵詞

災難性回溯（Catastrophic Backtracking）、嵌套量詞（Nested Quantifiers）、正規表達式拒絕服務（ReDoS）、線性時間複雜度（Linear Time Complexity）、NFA（非確定性有限狀態自動機）、PCRE（Perl Compatible Regular Expressions）、RE2 引擎、事件循環阻塞（Event Loop Blocking）、重疊字符類（Overlapping Character Classes）、預測性性能（Predictable Performance）。

在深入探討 ReDoS 漏洞的成因時，理解上述關鍵詞的相互關聯至關重要。首先，災難性回溯（Catastrophic Backtracking） 是所有 ReDoS 攻擊的核心機制，當正規表達式引擎在處理包含嵌套量詞（Nested Quantifiers）（如 (a+)+）的模式時，若輸入內容無法完全匹配，引擎會嘗試所有可能的組合路徑，導致計算量呈指數級爆炸。這種現象在傳統的 PCRE 引擎中極為常見，因為其設計邏輯偏向「樂觀」匹配。

為了對抗此類風險，Google 開發了 RE2 引擎（https://github.com/google/re2），該引擎的核心設計哲學是採用 NFA 結構來確保線性時間複雜度，從根本上避免了回溯導致的資源耗盡。與 RE2 不同，許多開發語言（如 JavaScript 或 Python）的原生 Regex 仍保留回溯功能，這在 Node.js 等單執行緒環境中尤為危險，因為一旦觸發 ReDoS，會直接導致事件循環阻塞（Event Loop Blocking），使整個應用服務掛起（https://www.myutilitybox.com/blogs/regex-catastrophic-backtracking-nodejs）。

此外，在 Rust 生態系中，regex crate 透過與 RE2 相似的設計，提供了一種具備預測性性能的實作，確保在處理用戶輸入時不會產生不可預期的延遲（https://stemjail.github.io/rustdoc/regex/index.html）。識別這些漏洞時，開發者必須警惕重疊字符類與複雜的嵌套結構，並透過監控性能指標來判斷是否存在潛在的 ReDoS 威脅（https://blogs.jsmon.sh/what-is-regular-expression-denial-of-service-redos-ways-to-exploit-examples-and-impact/）。透過對這些關鍵技術概念的掌握，研究者能更有效地在功能性與安全性之間取得平衡，並選擇適合的正規表達式引擎來防禦惡意攻擊（https://safeguard.sh/resources/blog/regular-expression-denial-of-service-redos-explained）。

引言

在現代網路架構與軟體開發的生態系中，正規表達式（Regular Expressions，簡稱 Regex）已成為處理字串處理、資料驗證、網頁爬蟲以及網路封包分析等任務的核心工具。從簡單的電子郵件格式檢查到複雜的自然語言處理（NLP）預處理，Regex 提供了一種高度抽象且強大的語法，讓開發者能以極簡的代碼實現複雜的模式匹配。然而，這種強大的能力往往伴隨著隱蔽的技術風險。其中最為典型且具備高度破壞性的安全漏洞，便是「正規表達式拒絕服務攻擊」（Regular Expression Denial of Service，簡稱 ReDoS）。

問題界定：隱藏在語法背後的計算陷阱

ReDoS 並非傳統意義上的記憶體溢出或直接的代碼執行漏洞，而是一種利用正規表達式引擎在處理特定模式時產生的「災難性回溯」（Catastrophic Backtracking）現象所導致的資源耗盡攻擊。當一個正規表達式引擎（如 JavaScript、Python、Java 或 PHP 常用的 PCRE 引擎）遇到複雜的嵌套量詞（Nested Quantifiers）或重疊字符類（Overlapping Character Classes）時，若輸入的字串與預期的模式部分匹配但最終失敗，引擎會開始嘗試所有可能的匹配路徑。

這種路徑的嘗試往往呈指數級增長。例如，在處理如 ^((a+)+)$ 這樣的模式時，當輸入為 aaaaa!（最後一個字符導致匹配失敗）時，引擎必須窮舉所有可能的 a 分組組合。這種計算複雜度的爆炸，會導致 CPU 占用率瞬間飆升至 100%，並在極短的時間內鎖死處理執行緒。根據技術文獻指出，在某些實作中，僅僅是 30 個字符的輸入，就足以讓系統陷入長達數秒甚至數分鐘的計算泥淖，這正是 ReDoS 的核心機制（https://safeguard.sh/resources/blog/regular-expression-denial-of-service-redos-explained）。

為何此刻值得關注：單執行緒架構與現代雲端環境的脆弱性

在當前的技術環境下，ReDoS 的威脅比以往任何時候都更加緊迫。首先，隨著微服務架構與容器化技術的普及，許多應用程式（特別是基於 Node.js 等單執行緒事件循環架構的服務）高度依賴高效的非阻塞 I/O。然而，ReDoS 攻擊正是針對 CPU 密集型任務的。在 Node.js 環境中，一個耗時的正規表達式匹配會直接阻塞事件循環（Event Loop），導致所有其他的併發請求都被掛起，從而造成整個服務的癱瘓（https://www.myutilitybox.com/blogs/regex-catastrophic-backtracking-nodejs）。這意味著攻擊者不需要大量的流量，只需要發送一個精心構造的惡意字串，就能輕易地讓整個伺服器失去響應。

其次，現代網路應用中，用戶輸入的驗證（如表單檢核、URL 解析、Header 解析）幾乎不可避免地會用到 Regex。如果這些驗證邏輯是基於用戶提供的內容，且開發者未能意識到特定的模式可能觸發災難性回溯，那麼系統就處於極高的風險之中。此外，隨著雲端自動擴展（Auto-scaling）技術的應用，ReDoS 攻擊可能導致雲端資源的快速消耗，進而產生高昂的成本支出，甚至觸發連鎖反應導致整體的基礎設施崩潰。

首先，本報告將深入剖析「災難性回溯」的數學原理，幫助讀者理解為什麼某些特定的 Regex 組合會導致計算複雜度的指數級爆炸。我們將透過具體的範例，展示如何識別出高風險的模式，例如嵌套量詞與重疊字符類。

文獻回顧

在深入探討正規表達式拒絕服務攻擊（Regular Expression Denial of Service，簡稱 ReDoS）的技術細節之前，必須先建立一個關於正規表達式引擎運作邏輯的學術基礎。ReDoS 並非一種傳統意義上的記憶體溢位或緩衝區溢位攻擊，而是一種利用演算法複雜度缺陷所導致的資源耗盡攻擊。本章將綜述現有研究中關於災難性回溯的理論基礎、不同引擎的設計哲學，以及在現代程式語言生態系中如何防禦這些漏洞的實務研究。

災難性回溯的演算法機制與數學基礎

ReDoS 的核心成因在於「災難性回溯」（Catastrophic Backtracking）。在許多主流的正規表達式引擎中，如 JavaScript、Python、Java 和 PHP，為了實現強大的匹配功能，開發者採用了回溯算法。這種算法在處理帶有嵌套量詞（Nested Quantifiers）或重疊字符類（Overlapping Character Classes）的模式時，若遇到無法匹配的輸入，引擎會嘗試所有可能的匹配路徑。

根據現有研究，當正規表達式包含如 (a+)+ 這樣的嵌套結構時，引擎在處理每個輸入字符時，可生成的匹配狀態數量會呈指數級增長。例如，當輸入為 aaaaa! 時，由於最後一個字符 ! 無法匹配，引擎必須回溯到之前的每一個位置，並嘗試將前面的 a 分組以不同的方式組合。這種組合的數量隨著輸入長度的增加而迅速膨脹。研究指出，在某些特定實作中，僅僅 30 個字符的輸入就足以導致 CPU 占用率達到 100% 並持續數秒甚至數分鐘，這正是 ReDoS 攻擊的技術核心（https://safeguard.sh/resources/blog/regular-expression-denial-of-service-redos-explained）。

此外，研究強調了「樂觀」與「悲觀」匹配策略的差異。傳統的 PCRE（Perl Compatible Regular Expressions）引擎通常採取樂觀策略，優先嘗試最常見的替代方案，但在面對複雜嵌套時，這種策略會導致引擎陷入無窮盡的嘗試循環。為了對抗這種現象，學術界與工業界開始研究如何透過限制引擎的行為來保證時間複雜度。例如，某些研究提出，若能識別出具有指數複雜度的表達式，系統可以在執行前進行靜態分析或限制其最大執行時間。

不同引擎架構的對比研究：RE2 與 PCRE

在處理 ReDoS 問題時，學術界與工程界最顯著的對比在於回溯式引擎與非回溯式引擎的設計差異。Google 開發的 RE2 引擎是研究中的重要對標對象。與傳統的 PCRE 不同，RE2 採用了有限自動機（Finite Automata）的設計理念，特別是 NFA（Nondeterministic Finite Automaton）編譯。

RE2 的核心設計目標是保證線性時間複雜度（Linear Time Complexity）。為了實現這一目標，RE2 採取了「悲觀」策略：它不提供回溯功能，如回溯引用（Backreferences）或複雜的前瞻/後瞻（Look-ahead/Look-behind）斷言。雖然這犧牲了某些高級語法的功能，但它從根本上避免了 ReDoS 攻擊，因為無論輸入內容如何，匹配過程的時間複雜度與輸入長度成線性比例（https://github.com/google/re2）。這與 PCRE 的設計邏輯形成了鮮明對比，PCRE 因為支持豐富的語法，往往在處理用戶提供的不可信輸入時變得脆弱。

此外，RE2 的技術基礎可追溯到 Ken Thompson 的 Plan 9 grep 實作。研究指出，RE2 通過同時處理多個狀態來避免測試每一個可能的替代方案，這與傳統引擎逐一嘗試路徑的方法有著本質上的區別（https://en.wikipedia.org/wiki/RE2_(software)）。這種架構的差異為我們理解 ReDoS 提供了重要的視角：ReDoS 往往是為了追求功能豐富性（Feature-rich）而犧牲安全性（Security）的典型案例。

現代程式語言與系統架構中的防禦實踐

在實際的軟體開發中，ReDoS 的影響往往會被放大在特定的執行環境中。例如在 Node.js 等單執行緒環境中，由於 JavaScript 的事件循環（Event Loop）機制，任何 CPU 密集型的正規表達式匹配（如 ReDoS 攻擊）都會阻塞整個執行緒。這意味著攻擊者只需發送一個精心構造的請求，就能導致整個應用伺服器停止響應所有其他請求，造成大規模的服務中斷（https://www.myutilitybox.com/blogs/regex-catastrophic-backtracking-nodejs）。

為了應對這一問題，不同的程式語言生態系發展出了不同的防禦機制。以 Rust 為例，其 regex crate 在設計上高度參考了 RE2 的原則。Rust 的正規表達式實作旨在提供一種安全的匹配機制，預設不包含回溯引用和複雜的前瞻/後瞻斷言，以確保在處理用戶提供的正規表達式時具有預測性的性能（https://stemjail.github.io/rustdoc/regex/index.html）。這種設計選擇反映了系統級語言在安全性與性能之間的權衡。

此外，研究也提到 Rust Locale Regex 等相關實作，這些實作旨在提供與 RE2 語法高度一致的規範，以確保在多語言與複雜字符處理場景下，依然能保持對 ReDoS 的防禦能力（https://rust-locale.github.io/rust-locale/regex/index.html）。

在實務操作層面，研究建議開發者採取多重防禦策略。首先是靜態分析，識別出如 ^((a+)+)$ 或 ^(\w+\s?)*$ 等具有嵌套量詞的危險模式。其次是性能監控，透過觀察輸入長度與耗時的關係來判斷漏洞。例如，如果 20 個字符的輸入耗時 10 毫秒，而 25 個字符的輸入卻耗時 500 毫秒，這通常是災難性回溯的明確指標（https://blogs.jsmon.sh/what-is-regular-expression-denial-of-service-redos-ways-to-exploit-examples-and-impact/）。最後，針對高風險場景，應考慮使用如 RE2 這樣保證線性時間複雜度的引擎，而非傳統的 PCRE 引擎。

總結來說，現有文獻與研究顯示，ReDoS 是一個由演算法複雜度缺陷引起的系統性安全問題。從災難性回溯的數學原理，到 RE2 與 PCRE 的架構對比，再到 Node.js 等特定環境下的阻塞機制，這些研究共同構成了一個完整的防禦框架。雖然目前仍缺乏通用的自動化工具能完美地將複雜回溯表達式轉換為線性時間的表達式，但透過理解這些核心原理，開發者可以更有效地在功能需求與系統穩定性之間取得平衡。

研究方法

本研究旨在深入剖析「正規表達式拒絕服務攻擊」（Regular Expression Denial of Service，簡稱 ReDoS）的技術成因、運作機制及其在不同程式語言環境中的表現差異。為了確保研究的嚴謹性與全面性，本報告採用多維度的研究方法，結合理論分析、技術對比與實務案例研究。以下為本研究的具體方法論說明：

分析取向

本研究的分析取向聚焦於「結構性脆弱性」與「工程設計權衡」。我們不單將 ReDoS 視為一個簡單的 Bug，而是將其視為正規表達式引擎在提供強大功能（如回溯引用、前瞻/後瞻）時，為了追求表達力而犧牲掉的安全邊界。

分析的核心維度包括：

  • 複雜度分析：量化解釋為何特定的嵌套結構會導致處理時間呈指數級增長，並建立數學模型來預測攻擊的影響範圍。
  • 引擎對比研究：深入對比 PCRE 與 RE2 的設計哲學。分析 RE2 如何透過放棄部分語法功能來換取線性時間複雜度的保證，並討論這種「悲觀策略」在實際開發中的適用場景。
  • 環境影響分析：分析 ReDoS 攻擊在不同運算模型下的影響，特別是針對 Node.js 等事件驅動架構中，CPU 密集型任務如何導致整個服務掛起。
  • 防禦策略評估：綜合分析現有的防禦手段，包括開發層面的引擎替換、架構層面的資源限制，以及檢測層面的靜態與動態分析，評估各項措施在複雜生產環境中的有效性與限制。

結果與討論

在深入探討正規表達式拒絕服務攻擊（Regular Expression Denial of Service，簡稱 ReDoS）的技術細節後，本研究發現，此類漏洞並非單純的程式錯誤，而是源於正規表達式引擎在處理複雜邏輯時，與計算複雜度之間的本質性矛盾。透過對核心機制、引擎設計差異以及實務防禦手段的綜合分析，我們得出以下關鍵發現與深度討論。

災難性回溯的數學原理與運算邏輯

ReDoS 的核心技術基礎在於「災難性回溯」（Catastrophic Backtracking）。為了理解這一現象，必須先剖析傳統正規表達式引擎（如 PCRE、JavaScript 引擎、Python 的 re 模組等）的運作模式。這些引擎通常採用回溯算法，這是一種「嘗試並回溯」的策略。當引擎嘗試匹配一個模式時，它會從左到右掃描輸入字串。如果某個部分匹配成功，它會繼續匹配後面的部分；然而，如果後面的部分匹配失敗，引擎會「退回」到上一個匹配點，嘗試另一種可能的組合路徑。

問題在於，當正規表達式中包含「嵌套量詞」（Nested Quantifiers）或「重疊字符類」（Overlapping Character Classes）時，這種回溯路徑的數量會呈指數級增長。例如，考慮一個經典的漏洞模式：^((a+)+)$。當輸入為 aaaaa!（末尾有一個無法匹配的字符）時，引擎會面臨巨大的挑戰。對於連續的 a，引擎有極多種方式來分配這些 a 到內層或外層的 + 量詞中。例如，三個 a 可以被劃分為 (aaa), (aa)(a), (a)(aa), (a)(a)(a) 等多種組合。隨著 a 的數量增加，這些組合的可能性會以 $2^n$ 的速度爆炸式增長。

根據相關研究指出，在某些特定的實作中，僅僅是 30 個字符的輸入，就可能導致引擎嘗試數十億甚至更多的路徑，進而導致 CPU 占用率瞬間達到 100% 並持續數秒甚至數分鐘（https://safeguard.sh/resources/blog/regular-expression-denial-of-service-redos-explained）。這種現象就是所謂的「災難性回溯」。從計算複雜度的角度來看，這意味著某些正規表達式在處理特定輸入時，其時間複雜度變成了指數級（Exponential Time Complexity），這正是 ReDoS 攻擊的技術核心。

典型漏洞模式識別與實務風險分析

在實務應用中，識別 ReDoS 漏洞需要對正規表達式的結構進行細緻的靜態與動態分析。研究發現，最常見的漏洞模式通常與模糊的邊界定義和過度寬鬆的量詞有關。

首先是嵌套量詞。如前所述，((a+)+) 是典型的例子。但在實際開發中，開發者可能會寫出更複雜的變體，例如 (a+)+$ 或 ([a-zA-Z]+)$。這些模式在處理長且不符合預期結尾的字串時，會觸發大量的回溯。其次是重疊字符類，例如 ^(\w+\s?)$。當輸入包含大量連續的字母或數字，且結尾沒有匹配到預期內容時，引擎會不斷嘗試不同的空格與字符分配組合。

為了有效識別這些漏洞，研究建議採用以下兩種方法：

  1. 靜態分析與模式檢查：開發者應審查所有與用戶輸入相關的正規表達式，特別是那些包含 +、* 或 {n,} 量詞且嵌套在括號內的結構。任何包含嵌套量詞的表達式都應被視為高風險。
  2. 性能指標監控：在動態環境中，ReDoS 的特徵非常明顯。如果一個正規表達式的匹配時間隨著輸入字串長度的增加而呈現非線性增長（例如，字串長度增加 1，耗時增加 10 倍），則極大機率存在 ReDoS 漏洞（https://blogs.jsmon.sh/what-is-regular-expression-denial-of-service-redos-ways-to-exploit-examples-and-impact/）。

ReDoS 的影響在現代 Web 架構中尤為嚴重。特別是在 Node.js 等單執行緒環境中，由於正規表達式的匹配過程是同步且阻塞式的，一個精心設計的 ReDoS 攻擊 payload 可以在極短時間內佔用整個事件循環（Event Loop）。這意味著，除了正在處理該攻擊請求的連線外，所有其他進來的請求都會被阻塞，導致整個服務陷入掛起狀態，從而達成拒絕服務的目的（https://www.myutilitybox.com/blogs/regex-catastrophic-backtracking-nodejs）。這種攻擊不需要大量的帶寬，只需要一個精確計算過的短字串，就能癱瘓整個後端服務。

引擎設計的權衡：RE2 與 PCRE 的對比

針對 ReDoS 問題，學術界與工業界提出了兩種截然不同的設計哲學。這在 Google 開發的 RE2 引擎與傳統的 PCRE（Perl Compatible Regular Expressions）引擎之間的差異中體現得最為明顯。

PCRE 引擎（回溯式）：這類引擎採取的是「樂觀」策略。它們旨在支持極其豐富的功能，如回溯引用（Backreferences）、複雜的前瞻（Lookahead）與後瞻（Lookbehind）斷言。為了實現這些功能，引擎必須能夠「回溯」到之前的狀態。然而，這種靈活性是以犧牲安全性為代價的。當面對嵌套量詞時，PCRE 引擎會嘗試所有可能的組合，導致了上述的災難性回溯。

RE2 引擎（非回溯式）：為了從根本上解決 ReDoS 問題，Google 開發了 RE2。RE2 的核心設計在於它不使用回溯算法，而是採用 NFA（Nondeterministic Finite Automaton）或 DFA（Deterministic Finite Automaton）模型。RE2 在編譯時會將正規表達式轉換為狀態機，並保證在處理輸入時具有線性時間複雜度（Linear Time Complexity）。

為了達成線性時間的保證，RE2 做出了一些功能上的讓步：它不支持回溯引用，也不支持某些複雜的前瞻與後瞻斷言。雖然這在某些極其複雜的文本處理場景中可能不如 PCRE 靈活，但它提供了一個極其重要的安全保證：無論輸入內容是什麼，匹配過程都不會導致 CPU 耗盡（https://github.com/google/re2）。

這種設計差異體現了「功能與安全性」之間的權衡。在處理用戶提供的正規表達式時，RE2 或類似的設計是更安全的選擇，因為它能預測性能上限。

Rust 生態系的防禦實踐與安全標準

在現代系統程式語言中，Rust 社群對安全性的追求也體現在其正規表達式庫的設計上。Rust 的 regex crate 在設計上高度參考了 RE2 的核心理念。

regex crate 旨在提供一種安全的正規表達式實作。它預設不包含回溯引用，並在處理複雜模式時避免進入災難性回溯的陷阱。透過採用與 RE2 相似的 NFA/DFA 構建方式，Rust 的 regex 庫能夠確保在處理用戶輸入的正規表達式時，其執行時間與輸入字串的長度成線性比例關係（https://stemjail.github.io/rustdoc/regex/index.html）。

此外，Rust 社群中的 rust-locale 等相關項目也強調了與 RE2 語法的一致性。透過限制某些可能導致指數級複雜度的語法特徵，Rust 提供了一個對用戶輸入具有預測性性能的環境（https://rust-locale.github.io/rust-locale/regex/index.html）。這種設計理念在處理網路通訊協定、解析用戶上傳的格式（如 JSON、XML）或處理複雜的字串驗證時，能有效防止惡意攻擊者利用 ReDoS 漏洞來癱瘓系統。

深度討論：ReDoS 防禦的實務策略與未來挑戰

雖然我們已經了解了 ReDoS 的成因與防禦機制，但在實際的軟體開發中，如何平衡「表達式功能」與「系統穩定性」仍是一個持續的挑戰。

1. 實時檢測的難度與監控策略

在生產環境中，區分「正常的複雜匹配」與「惡意的 ReDoS 攻擊」往往具有高度挑戰性。例如，處理大型文件的正規表達式可能本身就耗時較長。因此，單純依靠靜態檢查是不夠的。企業應建立基於性能監控的防禦機制：當某個正規表達式的匹配時間超過預設閾值（例如 100ms）時，系統應自動中斷該匹配並記錄警告。這在 Node.js 環境中尤為重要，因為這能防止單一請求阻塞整個事件循環。

2. 自動化修復的技術瓶頸

目前，學術界與工業界仍缺乏一種通用的自動化工具，能夠將複雜的、帶有回溯功能的表達式（如 PCRE 格式）完美轉換為線性時間的 RE2 兼容表達式。這是因為某些功能（如回溯引用）在數學上與線性時間複雜度是互斥的。因此，當開發者發現表達式存在 ReDoS 風險時，通常需要手動重構邏輯，例如將複雜的嵌套量詞拆分為多個簡單的匹配步驟，或使用更具體的字符類來縮小匹配範圍。

3. 防禦層級的深度防禦

為了全面防禦 ReDoS，建議採用多層次的防禦策略：

  • 輸入驗證層：在進入正規表達式匹配之前，先對輸入字串的長度進行限制。大多數 ReDoS 攻擊需要較長的字串才能觸發明顯的延遲。
  • 引擎選擇層：在處理不可信的用戶輸入（如用戶自定義的搜尋規則）時，優先選擇 RE2 或 Rust regex 等保證線性時間的引擎。
  • 超時機制層：在執行正規表達式匹配時，使用非同步或多執行緒的處理方式，並配合嚴格的超時（Timeout）機制，確保單一匹配操作不會導致系統資源耗盡。

總結來說，ReDoS 漏洞是計算複雜度理論在實際軟體工程中的體現。透過深入理解災難性回溯的運作原理，並選擇適合的安全引擎（如 RE2）或採用嚴格的性能監控策略，開發者可以在維持功能靈活性的同時，有效防禦這類高風險的網路攻擊。在未來，隨著自動化靜態分析工具的進步，我們預期將能更精準地在開發階段識別並修復這些隱藏在正規表達式中的安全陷阱。

原創論點

在探討正規表達式拒絕服務攻擊（Regular Expression Denial of Service, ReDoS）的技術核心時，我們必須首先釐清一個關鍵的架構矛盾：正規表達式的「表達能力」與「執行效率」之間的權衡。ReDoS 並非單純的程式錯誤，而是由特定類型的正規表達式引擎設計邏輯與複雜匹配邏輯相互作用產生的結構性弱點。

嵌套量詞與指數級時間複雜度的數學陷阱

ReDoS 漏洞的核心機制在於「災難性回溯」（Catastrophic Backtracking）。為了深入理解這一點，我們必須剖析回溯引擎在處理嵌套量詞（Nested Quantifiers）時的運作邏輯。當一個正規表達式包含如 (a+)+ 或 ([a-zA-Z]+)* 這樣的結構時，引擎在面對不完全匹配的輸入（例如大量的 a 加上一個結尾的 !）時，會陷入一種「試錯」的無限循環。

具體來說，當引擎處理 (a+)+ 時，對於輸入 aaaaa，它可能將這些 a 分組為：

  • (aaaaa)
  • (aaaa)(a)
  • (aaa)(aa)
  • (aaa)(a)(a)
  • (aa)(aa)(a)
  • ...以此類推。

每增加一個字符，可能的組合路徑數量會呈指數級增長。在實際應用中，這種現象被稱為「災難性回溯」。根據相關研究指出，僅僅是 30 個字符的輸入，在某些回溯引擎中就可能導致 CPU 占用率瞬間飆升至 100%，並持續數秒甚至數分鐘，這正是攻擊者利用 ReDoS 癱瘓服務的手段（https://safeguard.sh/resources/blog/regular-expression-denial-of-service-redos-explained）。這種現象在處理長字串時尤為嚴重，因為時間複雜度往往是 $O(2^n)$ 甚至更高，這意味著微小的輸入變動就能產生巨大的計算資源消耗。

引擎設計的範式轉移：PCRE 與 RE2 的對立

針對 ReDoS 的防禦，技術社群產生了兩種截然不同的設計哲學。這兩者的對立，正是研究 ReDoS 漏洞時最重要的技術取捨點。

第一種是傳統的「回溯式引擎」，如 JavaScript 原生 Regex、Python 的 re 模組或 PHP 的 PCRE。這些引擎採用「樂觀策略」，旨在提供極高的表達靈活性。它們支援回溯引用（Backreferences）、複雜的前瞻（Lookahead）與後瞻（Lookbehind）斷言。然而，這種靈活性是以允許「災難性回溯」為代價的。當引擎遇到複雜的嵌套結構時，它會嘗試所有可能的替代方案，直到耗盡所有計算資源。

第二種是「非回溯式引擎」，最典型的代表是 Google 開發的 RE2。RE2 的設計核心是為了對抗 ReDoS。它採用 NFA（Nondeterministic Finite Automaton）編譯，並保證在任何輸入下都能在線性時間內完成匹配。為了實現這一目標，RE2 採取了「悲觀策略」：它主動放棄了回溯引用和某些複雜的前瞻/後瞻功能。這種設計從根本上杜絕了 ReDoS 的發生，因為它不會在匹配失敗時嘗試所有可能的組合路徑，而是通過 NFA 結構同時處理多個狀態（https://en.wikipedia.org/wiki/RE2_(software)）。

在實務應用中，這意味著開發者必須做出取捨：如果您需要極致的語法表達能力（例如需要複雜的條件判斷），您可能必須忍受 ReDoS 的風險並實施嚴格的輸入驗證；如果您追求系統的穩定性與安全性，尤其是處理用戶提供的正規表達式時，則應優先選擇如 RE2 或 Rust regex crate 等基於線性時間複雜度的引擎（https://github.com/google/re2）。

Node.js 環境下的單執行緒阻塞風險

在現代 Web 開發中，ReDoS 的影響往往被放大。以 Node.js 為例，其單執行緒的事件循環（Event Loop）架構使得 ReDoS 攻擊具有極高的殺傷力。由於 Node.js 在執行正規表達式匹配時是同步阻塞 CPU 的，一旦一個惡意的 ReDoS 請求進入，它將佔用整個執行緒。這不僅是該請求處理緩慢，而是導致整個應用程式無法處理任何其他進來的請求，包括健康的 API 調用或基礎的連線維持。

這種「全域阻塞」現象是 ReDoS 在後端服務中成為高風險漏洞的主因。正如研究所示，在 Node.js 環境中，一個精心構造的惡意字串（例如與複雜正規表達式匹配的長字串）足以讓服務陷入長時間的掛起（https://www.myutilitybox.com/blogs/regex-catastrophic-backtracking-nodejs）。這要求開發者在處理用戶輸入時，不僅要考慮「匹配是否正確」，更要考慮「匹配過程是否安全」。

實務中的識別與防禦策略：從靜態分析到動態監控

要有效防禦 ReDoS，研究者與工程師必須建立一套多維度的識別機制。

首先是靜態分析與模式識別。開發者應警惕任何包含「量詞嵌套」或「重疊字符類」的表達式。例如，^(\w+\s?)*$ 是一個典型的危險模式，因為 \w+ 與 \s? 在某些情況下會產生重疊的匹配路徑。在代碼審查階段，應重點檢查 WAF（Web Application Firewall）規則、資料庫查詢條件以及任何涉及用戶輸入驗證的正規表達式。

其次是動態性能監控。在生產環境中，一個簡單的指標可以幫助識別 ReDoS 攻擊：觀察輸入長度與處理時間的比例。如果一個 20 字符的輸入耗時 10ms，而一個 25 字符的輸入卻耗時 500ms，這幾乎可以確定存在災難性回溯（https://blogs.jsmon.sh/what-is-regular-expression-denial-of-service-redos-ways-to-exploit-examples-and-impact/）。這種非線性的時間跳躍是 ReDoS 攻擊的典型特徵。

最後是架構層級的防禦。對於必須使用回溯引擎的場景，建議採取以下三種策略：

  1. 輸入長度限制：在正規表達式處理之前，嚴格限制輸入字串的最大長度。這是最簡單且有效的防禦手段。
  2. 時間超時機制：在執行正規表達式匹配時，使用外部監控或特定的執行環境來強制超時，防止單一請求耗盡所有 CPU 資源。
  3. 引擎替換：在處理不可信的用戶輸入（如用戶自定義的搜尋過濾條件）時，強制使用 RE2 或 Rust regex 實作。Rust 的 regex crate 在設計上高度參考了 RE2，旨在提供一種安全的正規表達式實作，預設不包含回溯引用，確保在處理用戶提供的正規表達式時具有預測性的性能（https://stemjail.github.io/rustdoc/regex/index.html）。

總結來說，ReDoS 漏洞的發生是計算複雜度與正規表達式引擎設計缺陷的產物。要防禦這一漏洞，我們不能僅僅依賴於「寫出正確的表達式」，而必須從引擎選擇、輸入限制、性能監控以及對災難性回溯機制的深度理解這四個維度共同構建防禦體系。在追求功能極致的同時，必須意識到回溯算法帶來的安全代價，並在關鍵路徑上選擇更具預測性的線性時間引擎。

結論

本研究報告針對 ReDoS（Regular Expression Denial of Service）漏洞的成因、機制及其在現代軟體架構中的影響進行了深入剖析。透過對災難性回溯（Catastrophic Backtracking）的技術探討，我們發現 ReDoS 並非單純的語法錯誤，而是正規表達式引擎在處理嵌套量詞與重疊字符類時，因追求「樂觀匹配」而導致的計算複雜度爆炸。當引擎在面對無法匹配的輸入時，會陷入無窮盡的狀態嘗試中，導致 CPU 資源被耗盡。這種現象在 Node.js 等單執行緒環境中尤為致命，因為任何耗時的正規表達式匹配都會直接阻塞事件循環（Event Loop），導致整個服務無法處理任何新請求（https://www.myutilitybox.com/blogs/regex-catastrophic-backtracking-nodejs）。

總結

綜合研究結果顯示，ReDoS 漏洞的核心在於回溯式引擎（如 PCRE 變體）與非回溯式引擎（如 RE2）在設計哲學上的根本差異。回溯式引擎為了提供豐富的語法功能（如回溯引用、複雜的前瞻與後瞻），允許引擎在匹配失敗時回溯到之前的狀態並嘗試不同的分支。然而，當模式中出現如 (a+)+ 般的嵌套結構時，輸入長度每增加一個字符，可能的匹配路徑數量可能呈指數級增長（https://safeguard.sh/resources/blog/regular-expression_denial_of_service_redos_explained）。這種「災難性回溯」使得攻擊者只需提供極短的惡意字串，即可輕易癱瘓伺服器。

相較之下，Google 開發的 RE2 引擎透過採用 NFA（Nondeterministic Finite Automaton）結構，確保了匹配過程的線性時間複雜度（https://github.com/google/re2）。雖然這意味著必須捨棄某些複雜的語法特性，但它從根本上消除了 ReDoS 的可能性。Rust 生態系中的 regex crate 亦遵循類似的設計原則，透過限制回溯功能來換取預測性的性能與安全性（https://stemjail.github.io/rustdoc/regex/index.html）。因此，ReDoS 的防禦不僅是編寫正確的正規表達式，更在於選擇正確的底層引擎。

實務建議

為了有效防禦 ReDoS 攻擊，開發者與系統架構師應採取以下多層次的防禦策略：

  1. 選擇安全的正規表達式引擎：在處理不可信的用戶輸入時，應優先考慮使用 RE2 或 Rust regex 等保證線性時間複雜度的引擎。這些引擎在設計上即排除了災難性回溯的風險（https://en.wikipedia.org/wiki/RE2_(software)）。
  2. 嚴格限制輸入長度：在將字串送入正規表達式匹配之前，應先驗證輸入的長度。由於 ReDoS 的複雜度往往與輸入長度成指數關係，限制輸入長度是降低風險最簡單且有效的方法。
  3. 實施時間超時機制：對於必須使用回溯式引擎的場景，應在執行匹配操作時設置嚴格的超時（Timeout）。若匹配超過預設時間（例如 100ms），應立即中斷並拋出異常，避免單一請求耗盡整個服務資源。
  4. 靜態分析與自動化測試：開發團隊應建立自動化的掃描流程，檢查程式碼中的正規表達式模式。特別是針對嵌套量詞（Nested Quantifiers）與重疊字符類（Overlapping Character Classes）進行審查。若發現複雜模式，應參考 https://payloadplayground.com/blog/regular-expression_denial_of_service_redos_explained 中的實務指南進行重構。
  5. 監控與警報：在生產環境中，應監控 CPU 使用率與事件循環的延遲。若發現特定路徑的請求導致 CPU 突發性飆升，應能快速識別並攔截相關的惡意請求。

限制與後續研究方向

儘管目前的防禦技術已相當成熟，但在實務應用中仍存在一些限制與挑戰。首先是「功能與安全的權衡」：許多現有的業務邏輯高度依賴回溯引擎提供的複雜功能（如回溯引用），若直接切換到 RE2，可能導致現有邏輯失效。目前仍缺乏一種通用的自動化工具，能夠將複雜的回溯表達式完美且無損地轉換為線性時間的 RE2 兼容表達式，這仍需大量的人工介入與重構。

此外，在處理極高併發的環境下，如何精準區分「正常的複雜匹配」與「惡意的 ReDoS 攻擊」仍是一個技術難點。後續研究方向應著重於以下三個面向：

  1. 自動化重構工具開發：研究基於 AI 或靜態分析的工具，自動識別並重寫具有災難性回溯風險的正規表達式，並提供優化的替代方案。
  2. 動態監控與隔離技術：研究如何在不阻塞主執行緒的情況下，將正規表達式匹配操作隔離到獨立的執行緒池或工作隊列中，並實施動態的資源配額管理。
  3. 混合引擎架構：開發一種混合引擎架構，能夠根據輸入內容的複雜度動態選擇不同的匹配策略。對於簡單的模式使用快速的 NFA 匹配，對於複雜的模式則在受控的沙盒環境中執行回溯匹配。

透過持續的研究與技術演進，我們能夠在保持表達式靈活性的同時，構建更具韌性的軟體系統，從根本上抵禦 ReDoS 等資源耗盡類攻擊。
