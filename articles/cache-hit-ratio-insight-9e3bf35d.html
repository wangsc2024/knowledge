深度研究洞察簡報：cache_hit_ratio 回升驗收（kb_insight_eval 0.123→0.224）

產出日期：2026-07-08 | 任務：insight_briefing | 系列：ddp-cache-governance（optimization 階段）

摘要

本輪驗收 kb_insight_eval（2026-07-01）觀測的 API 快取命中率回升：自低谷 0.123 一度升至 0.224，但 2026-07-08 context/system-insight.json 顯示 0.193（sample=166），仍低於 warning 門檻 0.400。交叉比對 8 篇來源（A 級 3、B 級 4、C 級 1）與專案內 commit 6bba1409、cache-policy v20，萃取 6 項核心洞見。結論：TTL 微調帶來階段性改善，但需轉向 miss 分類診斷與雙帳本（API cache / KB semantic cache）觀測，方能穩定穿越 40% 門檻。

關鍵洞見

1. 6bba1409 因果鏈需與 cache 回升分離

  • 證據：commit 6bba1409 主體為 token-budget-enforcer Skill frontmatter 補齊、context/token-usage.json 初始化——修復 kb_system_optimize partial streak=2 的任務完成率阻斷，而非直接修改 cache-policy.yaml。
  • 含義：0.123→0.224 回升更可能來自 2026-07-07 前後連續 TTL 微調（knowledge/kb_hybrid 17280m、gmail 7776m）與 miss 分類改善，不宜將單一 commit 視為命中率因果。
  • 來源：CHANGELOG.md L274；config/cache-policy.yaml L20-46

2. 峰值 0.224 後回落至 0.193——改善未固化

  • 證據：kb_insight_eval 記錄 0.224 峰值；當日 system-insight cache_hit_ratio=0.193、cache_hit_ratio_sample=166，warning 持續（dedup_key=system_insight:cache_hit_ratio_warning:date=2026-07-08）。
  • 含義：TTL 單邊加大存在邊際遞減；closed-loop-review-2026-07-02 已明訂「ratio 不升反降時禁止重複純加大 TTL」。
  • 來源：context/system-insight.json L10-52；KB 筆記「系統優化落實報告 2026-07-06」

3. miss 分類診斷優先於 TTL 旋鈕

  • 證據：KB 落實報告（2026-07-04/06）均指向 cache_miss_diagnoser 分類擴充與 Forge 建議 cache_hit_ratio-tool-gap，目標是改善分母準確度與可解釋 miss，而非再調 TTL。
  • 含義：下一階段應串 tools/cache_miss_diagnoser（或同類）→ adaptive_ttl 回授，對齊 ADR-023 d-TTL。
  • 來源：KB note a03b01f1/c305addf；config/cache-policy.yaml adaptive_ttl.enabled=true

4. API cache 與 KB 語義快取須分帳監控

  • 證據：kb_semantic_cache stats --days 7 顯示 7 日 log_events 全 0、fastembed_available=false、entry_count=0；與 API cache_hit_ratio 是獨立帳本。
  • 含義：insight_briefing 步驟 0b 已納入語義快取遙測；未安裝 uv sync --extra semantic-cache 時 degraded 不視為任務失敗，但不得用 API ratio 代替 KB 語義命中評估。
  • 來源：本輪 kb_semantic_cache stats 輸出；skills/knowledge-query/SKILL.md 步驟 0.5

5. 產業對照：穩定 prefix + 可觀測性（LLM Prompt Caching）

  • 證據：OpenAI/Anthropic 2026 prompt caching 強調穩定 prefix、prompt_cache_key 路由黏性、監控 cached_tokens；前綴任一 byte 變動即 cache miss。
  • 類比 DDP：auto-task prompt 若每輪注入變動時間戳於共用前綴，等效於破壞 prefix 穩定性；應將變動欄位移至 suffix，並以 endpoint+參數 hash 作為 cache key。
  • 來源：OpenAI Prompt Caching 201（A）；AI Workflow Lab 2026 Guide（B）

6. Cache-aside 工程底線：jitter + 失效優先於盲調 TTL

  • 證據：Redis/Microsoft/RaidFrame 2026 指南一致：cache-aside 預設模式、必設 TTL、hit rate <80% 表示 miskey 或 TTL 過短、寫入時 invalidate 優先於 update-in-place；jitter ±10% 防 thundering herd。
  • 含義：DDP adaptive_ttl 已啟用，需驗證是否對 knowledge/kb_hybrid 低波動源套用 jitter 與 soft-TTL 模式。
  • 來源：redis.io cache-aside（A）；Microsoft Cache-Aside Pattern（A）；RaidFrame Redis Production Guide（B）

建議行動

  1. 短期（本週）：執行 cache_miss_diagnoser 全量分類，產出 endpoint 級 miss 原因分布，對照 0.193 回落時段。
  2. 中期：落地 cache_hit_ratio-tool-gap Forge 建議——整合 miss 診斷 + adaptive_ttl 回授，設定「連續 3 日 ratio 下降則凍結 TTL 調大」閘門。
  3. 可選：評估 uv sync --extra semantic-cache 啟用 fastembed，讓 KB 語義快取帳本脫離全 degraded 狀態。

多透鏡洞察

透鏡選擇與理由

precompute 選定 distill-sam-altman（primary）、distill-jensen-huang（primary）、distill-taleb（adversarial），rationale=task_profile:insight_briefing。主題涉及系統效能驗收與工程投資回報，適用「快速部署反饋」與「workload/TCO 優先」框架；Taleb 透鏡用於檢視把單點 TTL 調整當成確定性解的風險。

框架化建議

快速部署反饋（Sam Altman 模型3）：cache 優化應以可觀測閉環驗收——每次 TTL 變更需綁定 7 日 cache_hit_ratio 與 sample 量，像產品迭代一樣「ship → measure → iterate」，而非一次性調參後不再讀取 system-insight。

TCO 而非標價（黃仁勳啟發式2）：延長 knowledge TTL 至 17280 分鐘降低 API 呼叫「標價」，但若 stale 資料導致 Agent 重試或 partial，總擁有成本可能上升。應按來源 volatility 分層：kb_live_status 120m vs knowledge 17280m 的差異即 workload-aware 分層。
