偵察提案：ApodexAI/FrontierAgent

專案是什麼

FrontierAgent 是 Apodex 公司隨其 Apodex 1.1 模型一併開源的 Agent Runtime，提供原生命令列 TUI，支援兩種模式：ReAct（單一 agent 在任務範圍沙箱內研究、讀檔、寫產出、跑指令並迭代）與 Agent Team（協調者維護任務看板，將工作拆解、委派給並行子 agent，收集回報後整合）。架構上刻意將 framework／tools／workflows／evaluation 四層分離、各自可重用；同一套 workflow engine 也用來跑 Apodex 模型的 benchmark。並支援以 YAML 組合多個 MCP server 成自訂 agent 配置。屬近期隨模型發布的新專案，社群成熟度（stars、issue 活躍度）待查證。

對本系統的借鑑點

  1. Agent Team 的協調者＋任務看板機制 → 對應 [[todoist-team-migration]] 目前的批次並行＋健康守望設計。FrontierAgent 把「拆解→委派→收集回報→整合」做成可觀察的看板結構（sidebar 顯示 plan/task board、即時工具活動、session-scoped diff），可借來補強 todoist-team 現有排程分層機制的可視化層，讓每輪批次任務的執行狀態不必事後看日誌才知道。
  1. YAML 組合多 MCP server 成自訂配置 → 對應 [[cordis-plugin-router-pattern]]（每個外部服務各自一個插件、薄路由層組合，仿 llm-router）。FrontierAgent 用宣告式 YAML 決定「這次 agent 該掛哪些 MCP server」，此思路可用於 Cordis 插件路由層：把「哪些插件對哪個任務啟用」外部化成配置檔，而非寫死在路由邏輯裡，降低新增插件時對路由層的改動幅度。
  1. framework/tools/workflows/evaluation 四層分離 → 對應規格驅動流程中 specs//evidence/ 的證據鏈要求。FrontierAgent 把「跑任務」與「評估任務結果」拆成獨立可重用層（同一 workflow engine 服務生產與 benchmark 兩種場景），可借鑑來讓 驗收 指令產出的 verification-report.md 更結構化——把「執行」與「驗證」在程式層面也分離，而不只是文件層面分離。
  1. task-scoped sandbox + session diff → 對應 Cordis 插件在跑外部 I/O（真實 Adapter）時缺乏統一的「本次變動快照」機制。若插件執行涉及檔案寫入（如 kb-site-publish），採用 session-scoped diff 的概念可讓每次執行的變更範圍一目了然，便於出錯回溯。

建議行動

  • 低風險，可先做：閱讀 FrontierAgent 的 MCP YAML 配置格式範例，評估是否能簡化 Cordis 插件路由層的「插件啟用清單」表達方式（不涉及既有插件邏輯改動，純配置層原型）。
  • 低風險，可先做：在 todoist-team 既有日誌基礎上，補一個簡易任務看板視圖（純呈現層，不改動排程與配額邏輯），驗證「協調者＋看板」的可視化價值。
  • 需人工決策：是否要把 todoist-team 的批次協調邏輯，從目前的排程分層改為 FrontierAgent 式的「協調者 agent + 並行子 agent + 整合」正式架構——這涉及對既有 59 任務系統的核心改動，且對方專案成熟度（社群驗證、長期維護承諾）待查證，建議先觀察一段時間再評估。
  • 需人工決策：evaluation 層獨立化是否值得投入——需先確認 Cordis 現有 驗收 流程的痛點是否真的來自「執行與驗證耦合」，而非文件格式問題。
