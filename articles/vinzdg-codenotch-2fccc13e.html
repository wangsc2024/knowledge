偵察提案：vinzdg/codenotch

專案是什麼

一款 macOS 應用程式，把 Claude Code、Cursor、Codex、Antigravity 這幾支 AI CLI 工具的用量上限即時釘在螢幕邊緣顯示。核心機制是持續輪詢各 CLI 本機的用量／額度狀態，做成常駐視覺化 overlay，讓使用者在真的撞到限額前就先看到。成熟度屬個人工具規模的 macOS 小應用，非伺服器端服務。

對本系統的借鑑點

已讀取 examples/plugins/llm-claude/index.mjs 核實現狀：

  • claude.status（index.mjs:157-174）目前只回報 CLI 是否可用、版本號、耗時，不含任何用量／額度剩餘資訊。
  • LIMIT_PATTERN（index.mjs:20）是事後比對錯誤文字（usage limit／rate limit／quota exceed 等），只有在呼叫已經失敗後才判斷「這是額度問題」，屬於反應式偵測，不是主動可查詢的狀態。
  • Cordis 本就用 llm-claude／llm-cursor／llm-kiro／codex 四個插件各自包這四支 CLI（docs/SKILL-INDEX.md §4 已有逐 CLI 行為差異表，但沒有用量額度這一欄），與 codenotch 監控的對象完全重疊。
  • 可借鑑之處：把 codenotch「主動輪詢＋常駐顯示」的精神，換成「在 *.status capability 裡新增 quotaRemaining／resetAt 欄位」，供 scripts/todoist-team.mjs 的 provider fallback（index.mjs:18 註解已提到「usage limits lift on their own (next provider now)」的既有邏輯）在呼叫前就避開快到頂的 CLI，而不是現在這種「先打下去、失敗了才靠文字比對換下一個」。

建議行動

  • 低風險，可先做：查證 Claude Code CLI／cursor-agent／codex CLI 本機是否真的有可讀的用量或額度資訊來源（例如設定目錄下的 usage 檔、或 CLI 自帶的 usage／status 子指令）——這是 codenotch 實際抓取數據的手法基礎，須先確認來源存在，才知道能否比照複製；目前尚未查證，標記待查證。
  • 需人工決策：若查證後確有可讀來源，是否要把「主動額度可見性」接進 *.status 契約與 scheduler 的 fallback 判斷邏輯——這會動到現有 LIMIT_PATTERN 重試機制的相容性（新舊兩套判斷同時存在時誰優先），屬於架構層改動，不建議未經討論就落地。
