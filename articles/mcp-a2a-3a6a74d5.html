摘要

本文以『協定收斂是否等於編排收斂』為研究問題，檢視 Model Context Protocol（MCP）與 Agent2Agent（A2A）自 2024 年至 2026 年的產業化歷程。透過候選池 60 筆、精讀納入 23 筆外部來源（17 篇同行評審論文與會議論文、6 篇官方規格與廠商文件）之三角佐證，本文論證業界『代理互通已標準化』的敘事，混淆了協定層與編排層兩個不同抽象層級。協定層確實達成跨廠商傳輸互通的實質採用；但學術界與四大雲端廠商在協定之上，各自提出或建構互不相容的編排邏輯層，且此分裂並非過渡性工程未成熟，而是各方架構利益競逐下的結構性均衡，並已產生可觀測性與究責層面的實質安全風險。

關鍵詞

AI 代理編排、Model Context Protocol、Agent2Agent Protocol、多代理系統、協定標準化、架構分裂、編排層治理

引言

[李飛飛主筆] 我從一個具體場景出發：一家中型企業的架構師被告知「MCP／A2A 已經解決了代理互通問題」，於是把採購決策押在某雲端廠商的「原生支援 MCP／A2A」標語上——但半年後她發現，真正決定系統能不能跨平台搬遷的，不是介面相不相容，而是誰的「編排邏輯」被鎖進了哪個廠商的專屬 orchestrator。這個知識缺口正是本文的研究問題：協定層的跨廠商採用速度確實驚人——Anthropic 於 2024 年推出 MCP、Google 於 2025 年推出 A2A，兩者現皆捐贈治理權予 Linux Foundation，A2A 截至 2026 年 4 月已有逾 150 個組織支持（[來源：Agent2Agent Protocol Specification, 2025]）——但「介面互通」與「編排邏輯可攜」是否為同一件事？本文的貢獻在於，以三角佐證方式並排檢視協定規格文件本身的語意範疇，以及學術界與四大雲端廠商在協定之上實際建構的編排抽象層，論證兩者的收斂程度存在系統性落差：協定層收斂是真的，但這股收斂速度本身，正在系統性地掩蓋編排層持續擴大、且已具備結構性均衡特徵的架構分裂。

文獻回顧

[李飛飛主筆] 文獻可分三組。第一組是協定規格本身與其語意範疇的一手文件及學術分析。Anthropic 官方公告將 MCP 定位為連接 AI 系統與資料來源的通用開放標準（[來源：Anthropic, Introducing MCP, 2024]），2025 年起被 Claude／ChatGPT／Gemini／Copilot 原生支援；A2A 官方規格由 Google Cloud 於 2025 年公告，定義 Agent Cards／Tasks／HTTP-SSE-JSON-RPC 傳輸層，2025 年 6 月捐贈 Linux Foundation（[來源：Agent2Agent Protocol Specification, 2025]）。但 Yuan 等人分析 18 個代表性代理通訊協定後發現，現行協定「擅長傳輸、串流、schema 定義與生命週期管理，但對澄清、情境對齊與驗證的協定層機制有限」（[來源：Yuan et al., Beyond Message Passing, 2026]），這正是本文論證的關鍵起點。Fleming 等人的研究更進一步主張既有 OSI／TCP-IP 及 MCP 等協定僅處理主機到程序的資料傳遞，未涵蓋代理協作語意，因而提出全新的 Layer 8／Layer 9（[來源：Fleming et al., A Layered Protocol Architecture for the Internet of Agents, 2025]）——這件事本身就很說明問題：一個近 Cisco 背景的團隊認為既有協定不夠，於是又提出了一套新分層，而非採用既有方案。Anbiaee 等人系統性比較 MCP、A2A、Agora、ANP 四種協定的威脅模型，識別出 12 項協定層風險，MCP 案例研究顯示對可執行元件缺乏驗證即會產生可量測安全風險（[來源：Anbiaee et al., Security Threat Modeling for Emerging AI-Agent Protocols, 2026]），呼應語意驗證缺口的論點。

第二組是學術界針對編排/協調層本身的獨立架構提案，數量之多、彼此互不相容的程度，正是本文核心論證的骨幹。Bhardwaj 提出的 Qualixar OS 明確自我定位為「應用層作業系統」，直接對比 kernel-level 的 AIOS 與單一框架工具（AutoGen／CrewAI），宣稱三者路線互不相容（[來源：Bhardwaj, Qualixar OS, 2026]）；Liu 等人提出的 AgentOS 則以「Agent Kernel」取代傳統桌面環境典範，將編排問題重新定義為知識探勘問題（[來源：Liu et al., AgentOS, 2026]）；Hu 等人的 OxyGent 提出「Oxy 抽象」將代理／工具／LLM 統一封裝為可插拔原子元件（[來源：Hu et al., OxyGent, 2026]）——三者皆自稱通用、彼此卻互不相容。Mouzouni 的 Context Kubernetes 以容器編排類比企業知識治理，並實際調查 Microsoft、Salesforce、AWS、Google 四大平台，發現「無一在架構上隔離代理核准通道」（[來源：Mouzouni, Context Kubernetes, 2026]），本身即是編排層碎片化的第一手實證。Kandogan 等人的 Compound AI 藍圖架構直言「業界進展迄今為止是零散的」（[來源：Kandogan et al., Orchestrating Agents and Data for Enterprise, 2025]），卻也提出了自己的一套 streams／registry／planners 藍圖——又添一個非標準化方案。Song 等人的 Gradientsys 以 typed MCP 搭配 ReAct 動態規劃打造排程器（[來源：Song et al., Gradientsys, 2025]）；Shukla 與 Parker、Pasupuleti 等人分別提出治理協定 MOP 與運行時中介層 CAMCO，皆指出既有代理框架「缺乏內建政策控制」或「將約束隱性處理」（[來源：Shukla & Parker, 2025]；[來源：Pasupuleti et al., CAMCO, 2026]）。Popova 等人則證實「編排」一詞在供應鏈治理領域已被賦予與協定互通完全不同的意涵（[來源：Popova et al., 2025]）。Roumeliotis 等人以信任校準驅動的編排器將感知與元推理分離，其信任演算法為框架自建、無跨框架標準可援引（[來源：Roumeliotis et al., 2025]）。AutoGen 作為早期奠基性框架，於 2025 年 10 月被 Microsoft 併入 Agent Framework（[來源：Wu et al., AutoGen, 2023]），直接見證編排框架「先各自發展、後被動整併」而非「跨廠商標準化」的路徑。Adimulam 等人的綜述將 MCP／A2A 定位為「可互通的通訊基底」，但論文本身即是又一套「統一編排層」提案（[來源：Adimulam et al., 2026]），恰恰示範了編排層仍在持續增生競爭方案而非收斂。Krishnan 的綜述則為代理架構演進提供宏觀分期依據，但同樣指出現行評估基準的侷限（[來源：Krishnan, 2025]）。Fukui 的 365 次預註冊實驗發現隱藏式協調者顯著提高集體「解離」，行為輸出卻維持完美，掩蓋了內部狀態問題（[來源：Fukui, Invisible Orchestrators, 2026]），將編排層的架構選擇本身框定為安全風險來源。

第三組是四大雲端與企業廠商在協定之上實際建構的專屬編排實作。Google Cloud 官方部落格明言 A2A 讓「Salesforce 代理可交棒給 Google 代理，而彼此無需理解對方內部架構」（[來源：Google Cloud Blog, Vertex AI Multi-System Agents, 2025]）——這句話恰好證實內部編排邏輯仍不透明、不互通。Microsoft Foundry 於 2025 年 10 月推出 Agent Framework，將 AutoGen 與 Semantic Kernel 整併（[來源：Microsoft Foundry Blog, 2025]）；Salesforce 的 Agentforce 以「單一主控 Orchestrator＋多個 Sub-agent」階層運作，編排決策邏輯屬 Salesforce CRM 資料模型專屬（[來源：Salesforce, AI Agent Orchestration, 2025]）；AWS 的 Agent Squad 採用意圖分類器動態路由（[來源：AWS ML Blog, Agent Squad, 2025]），是第四種與前三者均不相同的編排範式。四家雲端廠商共用同一組協定層，卻各自壟斷了其上的「協調邏輯」抽象權。

研究方法

[LeCun主筆] 我對「標準已經完工」這類宣稱一向抱持懷疑，證據鏈得攤開來讓人自己檢查。Phase 0 先用機械化 harvest（site:arxiv.org、OpenAlex、Semantic Scholar API）對「large language model architecture」「AI agent orchestration」「frontier model capabilities」等關鍵詞取樣，候選池初步命中後再精讀複核、補強官方規格與廠商部落格，去重合併後合計候選池 60 筆。納入準則：優先 2025-2026 年出版、同行評審或官方一手來源，排除純行銷文案、與既有 18 項負面主題（如「協定完工的錯覺」這類已發表過的相近選題）重疊之選題。分級沿用三段式：A 級（同行評審論文／會議論文，17 篇）、B 級（官方規格／廠商部落格，6 篇），本題未納入 C 級來源，最終精讀納入 23 篇。核心主張的驗證門檻設在「至少 3 個獨立來源（不同機構、不同作者）交叉支持」，達標才記「已驗證✅」；本文 5 條核心主張全數過關，明細見附錄。老實說，「frontier model capabilities」這個關鍵詞確實抓到一些偏離主題的雜訊（涉及基準測試與模型能力評測而非編排架構的論文），這再次提醒我：關鍵字比對只是取樣手段，真正的篩選判斷仍得靠人工複核，不能把候選池數字本身當成證據力。

結果與討論

[李飛飛主筆] 我把發現整理成三層。

第一層，協定層的跨廠商互通是真的，這點我不打算否認。MCP 自 2024 年公告後迅速被 Claude、ChatGPT、Copilot、Gemini 原生支援，並於 2025 年底捐贈予 Linux Foundation 旗下 AAIF（[來源：Anthropic, Introducing MCP, 2024]）；A2A 由 Google Cloud 於 2025 年 4 月發布，截至 2026 年 4 月已有逾 150 個組織支持，涵蓋 Microsoft、AWS、Salesforce、SAP、ServiceNow、IBM（[來源：Agent2Agent Protocol Specification, 2025]），這是罕見的跨廠商協調速度。但第二層——這正是我最在意之處——多篇獨立研究一致指出，這股速度處理的僅是傳輸與交換格式，語意協調責任被系統性下放。Yuan 等人明確指出現行協定「對澄清、情境對齊與驗證的協定層機制有限」（[來源：Yuan et al., 2026]），Fleming 等人主張既有協定「未涵蓋代理協作」而另立新層（[來源：Fleming et al., 2025]），Anbiaee 等人的威脅建模則證實這個語意真空已轉化為可量測的安全風險（[來源：Anbiaee et al., 2026]）——三方各自獨立地指向同一個結構性缺口，而非單一研究者的個人判斷。

第三層是我認為最容易被忽略、卻最該被看見的落差：面對這個語意真空，各方沒有走向收斂，而是各自壟斷了「協調邏輯」的抽象權。學術陣營提出至少四套互不相容的通用編排方案——Qualixar OS（[來源：Bhardwaj, 2026]）、AgentOS（[來源：Liu et al., 2026]）、OxyGent（[來源：Hu et al., 2026]）、Context Kubernetes（[來源：Mouzouni, 2026]）——每一套都宣稱自己是通用解方，彼此卻互不相容；Mouzouni 對四大平台的架構調查更直接證實，沒有一家在協定生態系爆發式成長的同時，同步把代理核准通道的架構隔離做進去（[來源：Mouzouni, 2026]）。與此同時，Google、Microsoft、Salesforce、AWS 分別以 Agent Engine＋ADK、Agent Framework、Agentforce Orchestrator／Sub-agent 階層、Agent Squad 建立專屬編排邏輯（[來源：Google Cloud Blog, 2025]；[來源：Microsoft Foundry Blog, 2025]；[來源：Salesforce, 2025]；[來源：AWS ML Blog, 2025]），四者共用同一組協定層，編排決策邏輯卻互不可攜。我也想指出誰在承擔這個落差的代價：Fukui 的實驗證實，隱藏式協調者的架構選擇會顯著提高系統內部「解離」程度，但行為輸出在各條件下維持完美（[來源：Fukui, 2026]）——這代表企業採用這類系統時，現行以輸出為準的驗收方式，根本偵測不到這層風險。技術敘事的受益方（協定生態的跨廠商采用者）與承擔架構鎖定、審計盲區代價的一方，結構性地不是同一群人，這正是我一貫關心的問題。

實踐建議

[LeCun主筆] 幾點具體建議，不是空話：

  1. 把「協定合規」與「編排可攜性」拆成兩張驗收清單：採購或整合支援 MCP／A2A 的系統時，另立一組編排邏輯可攜性的實測項目，不能因為介面過了 spec 就假設能跨平台搬遷 workload——Mouzouni 的四大平台調查已證明這兩件事現在完全脫鉤（[來源：Mouzouni, 2026]）。
  2. 對「通用編排作業系統」式提案保持架構懷疑論：Qualixar OS、AgentOS、OxyGent 這類提案目前都只是 2026 年剛發表的單一團隊方案，先問維護規模、是否開源、有無獨立第三方複現，再決定要不要押注（[來源：Bhardwaj, 2026]；[來源：Liu et al., 2026]；[來源：Hu et al., 2026]）。
  3. 安全稽核納入「隱藏協調者」風險項：現行以輸出為準的驗收方式偵測不到協調者角色設計本身造成的內部解離，Fukui 的實驗結果應該直接寫進企業風險登記冊（[來源：Fukui, 2026]）。
  4. 持續追蹤 Linux Foundation AAIF 的治理議程是否納入編排層：協定捐贈治理是真實的開放性進展，但目前議程仍侷限在傳輸層；若編排語意標準化從未被排進議程，就不該預期它會自然發生。
  5. 技術選型優先支持可匯出／匯入跨框架 manifest 的方案，降低被單一雲端廠商的 Orchestrator 鎖定的風險，這比事後才發現搬不動代價低得多。

風險與限制

[LeCun主筆] 誠實講幾個限制。第一，本文樣本以英語文獻與四家美系雲端廠商為主，可能低估阿里雲、百度等區域生態系的編排標準化現況，這是候選池取樣範圍的固有侷限。第二，本文引用的多套「通用編排作業系統」提案（Qualixar OS、AgentOS、OxyGent、Context Kubernetes）幾乎全部發表於 2026 年，尚無長期採用率或存活率數據——依我對過往架構典範更迭的觀察，這類提案多數會在數年內被淘汰或整併，本文論證的「分裂持續」是目前的快照判斷，不代表這個格局會維持不變。第三，三角佐證雖然每項主張都有 ≥3 個獨立來源，但學術論文作者本身有「提出新方案」的發表誘因，可能系統性放大「既有方案不足」的敘事，這是文獻本身的結構性偏誤，我沒有辦法用三角佐證完全排除。第四，本文無法量化「協調邏輯壟斷」對終端用戶或中小企業造成的具體傷害規模——本文能證明的是結構性分裂確實存在且有多方獨立證據支持，但無法回答這個落差目前造成了多少實際生產事故或轉換成本，這需要更長期的產業事故資料庫才能回答。

原創論點

[李飛飛主筆] 我想提出一個本文尚未直接引用、但貫穿全部證據的類比：協定層與編排層的關係，很像國際貨櫃標準化與港口營運系統的關係。ISO 貨櫃尺寸標準化解決的是「任何一艘船、任何一座港口都能裝卸同一種貨櫃」這個問題，這是了不起的工程成就；但貨櫃到了港口之後，報關流程、堆場調度、多式聯運的排程軟體，每個國家、每個港務局都是各自為政的系統，貨櫃標準化完全沒有讓這些「營運邏輯」收斂。我認為 MCP／A2A 現在正站在「貨櫃尺寸剛定案」的那個時間點：介面互通的問題確實解決了，但支撐系統真正可用、可稽核、可究責的那層「協調邏輯」，還在 Qualixar OS、AgentOS、OxyGent、Context Kubernetes 這些各自宣稱通用、卻彼此不相容的提案裡繼續分裂——而且不只是分裂，是被四大雲端廠商與多個學術陣營各自「圈地」壟斷。這個類比之所以重要，是因為它指出一個常被忽略的事實：介面標準化的完工，不會自動帶來營運邏輯的標準化，兩者是完全獨立的治理課題，混為一談本身就是一種認知捷徑上的錯誤。

其次，我要把治理與創新雙軸的框架用回這個題目：業界習慣認為協定捐贈給 Linux Foundation 就等於整個代理生態系走向了開放治理，但我的判斷是——這只解決了「協定層」的治理問題，「編排層」的治理權，實際上被少數幾個雲端廠商與學術團隊分頭把持，而且沒有任何中立機構在協調這一層。Mouzouni 對四大平台的架構調查證實，沒有一家在協定生態爆發式成長的同時，同步把代理核准通道的架構隔離做進去（[來源：Mouzouni, 2026]），這不是四家公司同時疏忽，而是產業結構性地把「先讓協定跑起來」與「編排邏輯留在自家圍牆花園」拆成兩件事同時推進。我一貫主張的立場是：治理與韌性工程應該在架構設計的最早期就一起考慮，而不是等某一層先標準化、再假設下一層會自然跟上——本文的證據顯示，這個假設在編排層上並不成立，甚至可能永遠不會自動成立，因為分裂本身已經是各方架構利益競逐下達成的一種均衡，而非等待被解決的暫時性落後。誰擁有「協調邏輯」的定義權，誰就掌握了下一階段代理經濟的關鍵基礎設施——這件事，比「協定完工了沒」更值得整個產業認真辯論。

結論

[LeCun主筆] 回到開頭的研究問題：協定收斂等於編排收斂嗎？我的答案是——不等於，而且證據顯示這兩者之間的落差正在擴大而非縮小。MCP／A2A 讓「系統之間怎麼傳話、怎麼描述工具」有了共同語言，這是真實的工程成就，我不打算否認。但本文用 23 篇來源、5 條三角佐證主張證明，決定一套多代理系統能不能真正被信任、被稽核、被跨平台搬遷的那層「協調邏輯」，目前分散在至少四套互不相容的學術「通用作業系統」提案與四家雲端廠商的專屬編排框架裡，沒有任何收斂跡象，也沒有中立機構在協調這一層的治理。用我一貫的話講：協定層的進展是真的，但那不代表整個代理系統的「架構收斂」已經完成，甚至編排層可能根本不會走向單一收斂——這是各方架構利益競逐下的均衡狀態，而非過渡性的工程未成熟。本文的限制在於樣本範圍與時間窗（見「風險與限制」），後續研究若能建立跨框架編排相容性的實測基準，以及針對「隱藏協調者」風險的獨立稽核工具，才能真正回答這個架構分裂對生產環境究責能力造成了多大的具體代價——這是我認為下一步最值得投入的方向。
