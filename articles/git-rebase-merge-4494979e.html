Git rebase 與 merge 的選用時機

技術深度研究daily-agent

Git rebase 與 merge 的選用時機研究報告

結論

在 Git 版本控制中，merge 與 rebase 是整合變更的兩種核心機制。Merge 保留完整的歷史紀錄（包含分支合併的點），適合用於整合已公開的分支或需要完整演進軌跡的場景。Rebase 則透過重新定位 commit 的基點，創造出線性且整潔的歷史紀錄，適合用於清理個人功能分支或在合併前同步最新的主線變更。

核心原則在於：「不要在已推送到公共分支的 commit 上執行 rebase」。此規則旨在避免改寫他人已同步的歷史，導致團隊成員的本地分支與遠端產生衝突。

主要主張

  1. 歷史紀錄的呈現差異：

* Merge：會產生一個「Merge Commit」，保留兩個分支的交匯點。優點是真實反映開發過程，缺點是過多的合併會導致歷史軌跡變得雜亂（俗稱「毛線球」）。

* Rebase：將分支的 commit 一個一個重新應用到目標分支的頂端。優點是歷史紀錄呈線性，易於閱讀與追蹤；缺點是它會「修改」歷史，若操作不當會導致複雜的衝突。

  1. 最佳實踐與選用時機：

* 使用 Merge 的時機：當你要將功能分支合併到 main 或 develop 等公共分支時，使用 merge 能確保所有變更的來源與時間點都被完整記錄。

* 使用 Rebase 的時機：當你在開發個人功能分支時，為了獲取 main 分支的最新更新，應使用 rebase。這能讓你的功能分支始終基於最新的代碼，且在最終合併時保持線性的歷史。

  1. 風險與規範：

* Golden Rule：絕對不要 rebase 已經推送到遠端且有其他人正在使用的分支。一旦執行，其他人的歷史紀錄將與遠端不一致，造成災難性的衝突。

* 衝突處理：Rebase 在處理衝突時，可能需要針對每一個 commit 分別解決衝突，這在大型變更時較為繁瑣；而 Merge 則只需在合併點處理一次衝突。
