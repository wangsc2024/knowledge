偵察提案：donvito/codex-astra-luna-orchestrator

專案是什麼

在 Codex CLI 之上設定角色分工：「Astra」擔任主控（orchestrator），「Luna」擔任子代理（subagent），於同一 Codex session 內分層執行多階段任務。從一行描述判斷屬輕量設定／腳本層級專案，非獨立框架；實際程式碼結構與是否僅為 model-profile 設定，待查證。

對本系統的借鑑點

已實際讀碼核實：本系統 examples/plugins/agent-recursion.mjs 已有巢狀 agent loop 的深度上限（DEFAULT_MAX_AGENT_DEPTH=3，經 withAgentDepth 追蹤），codex.agent_loop（examples/plugins/llm-codex/agent-server.mjs:161）在 thread/start 只吃單一 model: input.model，且 workflow-composer/allowlist.mjs 建構的工具 schema 不會自動注入 model 欄位——也就是說巢狀呼叫時，子代理該用哪個模型完全沒有系統層規則，落到「有深度管控、無角色分級模型」的狀態。Astra/Luna 這種「主控用強模型、子代理用輕量模型」的分工，可對應到讓 codex.agent_loop 依 currentAgentDepth() 在深度 >1 時預設帶入較便宜的模型，作為既有深度天花板之外的第二道成本控制。

建議行動

低風險：先在既有排程（如 team-scheduler 手動觸發一次）不改程式碼、只是把同一任務分別以「全程單一模型」與「人工手動指定深層呼叫用較便宜模型」各跑一次，比較 token usage 與輸出品質落差，作為是否值得做成系統規則的依據。

需人工決策：若驗證有效，是否要把「依深度分級模型」正式寫入 codex.agent_loop 的 capability 介面（涉及 sideEffects: llm 的核可流程與 schema 變更），以及是否需要同步套用到 responses.agent／nvidia.responses.agent，避免只有 codex 分支不一致。
