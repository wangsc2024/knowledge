偵察提案：Tencent/WeMM-Embedding

專案是什麼

騰訊微信視覺團隊開源的通用多模態嵌入模型系列（2B/4B/9B），支援文字、圖像、視頻、視覺文檔與交錯多模態輸入（不含音訊）。核心特色是 Matryoshka 表示學習：單一模型可輸出 64～2048 多種維度嵌入，256 維即保留 98.7% 全維度性能。已發表技術報告（arXiv 2608.24053），提供推理程式碼、三組權重、MMEB-v2 benchmark（4B 模型平均 79.2，優於主流對標），Apache 2.0 授權，可用 transformers/SentenceTransformers 本機推理，或以 vLLM 0.27.0／SGLang 0.5.9 起服務，需 GPU。成熟度高，非概念驗證專案。

對本系統的借鑑點

已核實對應物：examples/plugins/knowledge-base/index.mjs 的預設語意檢索退回路徑，是純雜湊子詞向量（hashBucket 用 FNV-1a 雜湊落桶，index 標記明白寫著 'local hashed subword (not semantic embedding)'），並非真語意嵌入；真正的語意檢索需靠 examples/plugins/knowledge-semantic-index/plugin.json 代理外部 RAG_Skill 服務（CORDIS_SEMANTIC_INDEX_URL 未設定即整支插件啟動失敗，自動退回上述雜湊實作）。這代表 KB 目前「沒有外部服務時＝沒有真語意檢索」，是明確缺口。

  1. 本機語意退回層：可用 WeMM-Embedding 2B（Apache 2.0、transformers 可跑）取代雜湊子詞向量，作為 knowledge-semantic-index 未啟用時的第二層退回，讓「沒接 RAG_Skill」不再等於「沒有語意」。
  2. Matryoshka 維度彈性：現行雜湊向量固定 VECTOR_DIMENSIONS 桶數；WeMM 的可變維度（如 256 維，98.7% 效能）可讓 KB 依索引規模動態選維度——小知識庫用低維省算力，全文檢索用高維求精度，不必重新訓練或換模型。
  3. 輸出形狀相容：knowledge-semantic-index 已定義好回應形狀（results/totalChunks/index/sources），本機 WeMM 適配器可依同一 capability 契約（knowledge.base.search-index）實作，保持插件路由模式（每服務一插件、薄路由層）一致，不需改動路由層。

建議行動

  • 低風險可先做：在獨立分支起一個最小 PoC，用 WeMM-Embedding 2B（transformers，256 維）對現有 KB 幾筆文件跑嵌入比對，驗證中文語意檢索品質是否明顯優於現行雜湊向量，作為決策依據。此步驟不動生產程式碼。
  • 需人工決策：

1. GPU 可用性——本機/KB 伺服器是否有 GPU 可常駐跑 2B 模型；若無，需評估 CPU 推理延遲是否可接受，或改走批次預先索引（離線嵌入、線上僅查詢）。

2. 是否值得新增第三個 provider（現行是 hashed 與 RAG_Skill 代理兩層），還是直接升級雜湊退回層本身——後者改動面較小但需重新設計 hashBucket 相關程式碼路徑。

3. 授權與相依性審查：新增 transformers/PyTorch 級相依對現有 Node.js 插件 runtime 是否合適，可能需要另起 Python 子服務並比照 knowledge-semantic-index 的 HTTP client adapter 模式接入，而非直接嵌入 Node 進程。
