深度研究洞察簡報：AI Agent 記憶系統分層與淘汰策略 application 階段——mem0/Graphiti/Letta 2026 最新設計對照 DDP continuity/archival_tier 落地評估

日期：2026-07-19

系列：agent-memory-tiering-ddp-archival（application 階段，foundation 2026-06-05 / mechanism 2026-06-29 已完成，本次完成 application）

次序：延續 17 天前中斷的系列（last_active 2026-07-02），優先於近 3 日已飽和的 agent_crash／self_heal 主題（07-16～07-18 已連續 3 篇），依 diversity_guard 換方向

摘要

config/memory-policy.yaml 對 mem0／Graphiti／Letta 三個開源 Agent 記憶專案的引用集中於 2026-06-05～06-10 的 REST star 觀測，本次重新查核三者的當前設計並對照 DDP 自身 8 層記憶治理策略。核心發現：mem0 已於 2026-04（README「New Memory Algorithm」段落，經 WebFetch 原始碼庫二次驗證）由 ADD/UPDATE/DELETE/NOOP 四操作模式轉向 single-pass ADD-only 架構，DDP deduplication_policy（DDP_CONTINUITY_EXTRACT，預設關閉）對 mem0 機制的描述性註解已落後於官方現況，但因功能本身停用，不構成實際風險，僅是文件溯源需覆核。同時發現 DDP 現有「不刪除只降權」（[STALE]／[speculative]／[low_quality] 標記）與 archival_tier 摘要壓縮設計，方向與 Graphiti 雙時態邊改寫、業界 2026 綜述強調的「staleness 需應用層監督」高度一致，屬於已印證的正確設計選擇，非缺口。萃取 6 項核心洞見，套用 Sam Altman／黃仁勳／Taleb 三組思考透鏡，KB 匯入 1 篇，backlog 新增 2 條文件與欄位級改善建議，research-series 系列進度 40%→60%。

關鍵洞見

  1. mem0 官方架構已轉向 ADD-only，DDP 文件註解落後於現況（已 WebFetch 原始 README 二次驗證）：config/memory-policy.yaml 第 65-74 行 deduplication_policy 描述「Mem0-inspired 智能層 ADD/UPDATE/DELETE/NOOP」，引用「2026-06-10 github_scout」觀測；但 mem0 官方 README 明確記載自 2026-04 起改為「Single-pass ADD-only extraction -- one LLM call, no UPDATE/DELETE. Memories accumulate; nothing is overwritten」。DDP 該功能預設 default: false（kill switch DDP_CONTINUITY_EXTRACT），未上線不構成實際故障，但文件溯源已與官方現況脫節。（來源：github.com/mem0ai/mem0 README「New Memory Algorithm (April 2026)」段落，WebFetch 2026-07-19 二次驗證）
  1. mem0 真正的官方淘汰機制是 opt-in 的「Memory Decay」搜尋期軟衰減，非真刪除：近期存取記憶獲 1.5x 分數加成，長期未用降至 0.3x，但衰減後的記憶若仍是最佳匹配依然會被檢索到，「沒有東西被真正刪除」。相較之下 DDP continuity 層 retention_runs: 3 是機械式硬截斷（超過 3 筆直接移除或轉入 archival_tier 壓縮摘要），比 mem0 官方預設更明確、更可預測，且已有 archival_tier（valid_from/valid_until）保留摘要而非物理丟棄，實質上已補上 mem0 官方「軟衰減」與「真淘汰」之間的折衷地帶。（來源：mem0.ai/blog/memory-eviction-and-forgetting-in-ai-agents）
  1. Graphiti 雙時態模型與 DDP archival_tier 高度吻合，但多做了一步「邊改寫」：Graphiti 判定舊事實過期時，除設定 expired_at 外，會用 LLM 重寫該邊的敘述文字反映狀態轉變（例：「是 junior manager」→「曾是 junior manager，直到升遷」），查詢時只回傳當下 valid 版本。DDP archived_summary 目前只做摘要壓縮＋valid_until 時間戳，未做「明示被何者取代」的改寫；可用低成本欄位補齊此差距（見建議行動 B）。（來源：blog.getzep.com/beyond-static-knowledge-graphs、arxiv.org/html/2501.13956v1）
  1. Letta 三層記憶完全交由 agent 自主 self-edit，DDP 刻意選擇機械式規則——本次研究印證此設計選擇方向正確：Letta archival memory 無自動淘汰機制，決策權完全交給 agent 在推理迴圈中判斷「什麼該存檔」；2026 業界綜述（arxiv.org/html/2603.07670v1）同時指出，過度依賴 agent 自主判斷易致「靜默細節遺失」（激進摘要造成罕見但關鍵事實消失）。DDP 選擇 config 驅動的 retention_days/retention_runs/decay_rule（而非 LLM 自主決定該留該刪）與此警示一致，也符合本專案自身「機械優先」ponytail 原則——這是一次由外部研究驗證既有架構選擇而非發現缺口的案例。
  1. 業界 2026 綜述明確點名「memory staleness → confidently wrong」為未解問題，DDP 已有的三種降權標記正是對應的應用層監督：多篇 2026 綜述（arxiv.org/html/2604.16548v2、arxiv.org/pdf/2606.30306）強調「僅靠基礎設施層 decay/eviction 演算法不足以防止陳舊資訊污染，必須有應用層監督」。DDP templates/shared/preamble.md 已實作 [STALE]（finding_expires_days 過期）、[speculative]（confidence<0.5）、[low_quality]（quality_score<2）三種降權標記（僅降權不刪除），與此共識方向一致，屬於 2026-07-02 已落地且持續有效的設計。
  1. MaRS Priority Decay + K-LRU（RAM/disk 置換）概念，可作為 DDP digest_memory／state_files 層未來升級的具體參考起點：digest_memory 層現行規則是「stale_after_days=30 且 access_count < low_access_threshold(3)」，已具備存取頻率因子，但 archival_memory 層目前只有 recency_boost_30d（時間）無存取頻率加權；K-LRU「高頻存取留熱層、低頻移冷層」的思路可作為未來 recency_boost 演算法升級（疊加 frequency 因子）的具體設計來源，非急迫但值得記錄供 optimization 階段參考。（來源：towardsdatascience.com/a-practical-guide-to-memory-for-autonomous-llm-agents、arxiv.org/pdf/2606.30306）

多透鏡洞察

透鏡選擇與理由

本次透鏡由 temp/insight-briefing-lens.json 依 task_profile:insight_briefing 預先選定（Sam Altman／黃仁勳為 primary、Taleb 為 adversarial），非依本次「記憶分層」主題語意動態挑選；套用於本次分析時，Altman 的「快速部署反饋」模型與黃仁勳的「demand-driven 創新」模型恰好都能對應 DDP 記憶治理設計的兩個面向（已上線驗證 vs 按需求定製），Taleb 則提供對「引用來源時效性」的懷疑論檢查，三者組合仍具解釋力。

框架化建議

Altman：快速部署反饋（模型 3）——DDP 的 archival_tier 並非先完美設計再上線，而是 enabled: true 已實際運行並累積真實 continuity 資料（本次研究引用的 07-16～07-18 三筆 run 記錄即為產物），符合「真實使用改進模型，API+產品雙輪」的迭代哲學：先讓 8 層記憶治理策略跑在生產環境收集真實資料，再依實測結果（如本次 mem0 文件溯源落後、Graphiti 邊改寫缺口）反覆修正，而非閉門把記憶架構設計到「完美」才上線。

黃仁勳：demand-driven 創新（模型 5）——DDP 沒有整包移植 mem0／Graphiti／Letta 任一套記憶框架，而是「先看 workload 再定義規格」：8 層記憶（message_buffer／continuity／digest_memory／research_registry／adr_registry／research_series／improvement_backlog／state_files／archival_memory）各自對應不同消費者與存取模式，只借用 Graphiti 的雙時態欄位命名（valid_from/valid_until）與 mem0 的三層 scope 概念（作為 memory_scope short_term/long_term 的參考），而非整套採用其淘汰演算法。這正是「不做無用規格，先問 workload 是什麼」的具體實踐，比全盤移植更貼合系統實際負載。

反模式檢查

依 Taleb「拒絕」清單逐條檢視：① Neomania（對新事物病態迷戀）——memory-policy.yaml 多處以「2026-06-05／06-10 REST 觀測」star 數作為設計正當性依據（如「mem0，57,735★」「letta，23,147★」），這是以熱度佐證架構選擇，本次研究證實至少 mem0 的引用內容（ADD/UPDATE/DELETE/NOOP）已與官方現況脫節——星數高不代表引用的具體機制仍是現況，屬於需要提防的 Neomania 傾向徵兆，但程度輕微（僅文件註解落後，非架構誤用）。② 中間地帶（不上不下最危險）——DDP 的 deduplication_policy 選擇明確二元開關（default: false 全關），未採取「部分啟用」的中間態，符合 Taleb 對中間地帶風險的警告，是正面案例非反模式。③ Fragilista（過度最佳化製造脆弱性）——未發現 DDP 記憶治理有強制自動刪除且不可逆的設計；archival_tier 與 rollback 欄位皆保留「設 false 立即停用、git restore 回退」路徑，屬於反脆弱設計而非 Fragilista 干預。

透鏡盲區自陳

Taleb 的核心專業領域是風險／機率／金融不對稱性，套用於「AI Agent 記憶架構」此一工程主題本身已是一次跨域延伸，其「誠實邊界」明確自陳「公開表達 ≠ 真實想法」——本次研究對 mem0／Graphiti／Letta 的認識同樣完全來自公開 README、部落格與論文（含 1 篇 2026-07-18 剛發布的 mem0 官方部落格），無法排除官方文件本身即帶有行銷性質的可能落差（例如 mem0 部落格自陳 LoCoMo/LongMemEval 分數本身有 ±1 分信賴區間）。本簡報已對「mem0 ADD-only 轉向」做二次 WebFetch 原始碼庫驗證以降低此風險，但 Graphiti／Letta 兩項發現僅單一來源交叉比對，建議下次系列階段（optimization）若涉及具體實作決策，應追加官方 GitHub Issue／Discussion 佐證再定案。

建議行動與後續研究

A（低成本，文件正確性覆核）：覆核並視需要修正 config/memory-policy.yaml 第 65-74 行 deduplication_policy 對 mem0 的機制描述註解，標明「mem0 官方已於 2026-04 轉向 single-pass ADD-only（無 UPDATE/DELETE），本機制為 DDP 依 2026-06-10 前觀測自建之邏輯，非現行 mem0 官方實作的直接移植」，避免未來啟用該 kill switch 時誤以為有官方實作可對照除錯。

B（中成本，欄位擴充）：context/continuity/auto-task-*-archive.json 的 archived_summary schema 增加選填欄位 superseded_note（仿 Graphiti 邊改寫精神，1 句話描述「此摘要記錄的問題／發現後續是否已被取代」），供 optimization 階段設計 reconcile 機制時可直接判讀而非僅靠 valid_until 時間戳推斷。

下一階段（optimization，60%→80%）：依系列既有 next_research_hint，量測 retention_runs=3 與 archival_tier 上線後的實際壓縮效果（archive 檔案增長率、max_archived_summaries=10 上限觸及頻率），並評估 K-LRU frequency 因子是否值得補入 archival_memory.retrieval 的 recency_boost 演算法。
