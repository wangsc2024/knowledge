偵察提案：wide-trace/open-higgsfield

專案是什麼

開源版 Higgsfield AI 影像／影片生成工作室，單一 prompt bar 驅動 40 個模型（12 影像 + 28 影片，如 Nano Banana、Kling 3、Veo 3.1、Flux 等）。核心機制是「每個模型自行宣告設定 allow-list」（長寬比、解析度、時長、輸出格式、音訊、批次量、prompt enhancement），studio 只依該模型宣告的欄位動態渲染設定面板，不用單一固定表單套所有模型。專案本身是瀏覽器內執行、免 Node.js 部署，成熟度屬新專案（README 描述為 MVP 級 catalog 整合，具體驗證機制待查證）。

對本系統的借鑑點

已核實 examples/plugins/llm-router/index.mjs 與其共用的 examples/plugins/llm-common.mjs：目前 PROVIDERS（llm-common.mjs:9-33）是單一同構 schema——所有供應商都是 OpenAI 相容 chat/completions，欄位固定為 envPrefix/base/suggestedModel/supportsJsonMode/appendV1/requiresKey/defaultModel，llm-router 的 CAPABILITY_BY_PROVIDER 也只是名稱→capability id 的扁平映射（index.mjs:6-14）。這套設計吃得下「文字對話」這種高度同構的介面，但完全沒有處理「每個供應商參數形狀互異」的情境。

open-higgsfield 的「per-model allow-list、由呼叫端據此動態渲染/驗證」機制，正好補上這個缺口：

  • 若未來要新增影像／影片生成類 provider 插件（目前 specs/ 下無此類插件，art-design-plugin 只做設計代幣、不做媒體生成），可比照此模式讓每個 provider 在 plugin.json 的 capabilities..input 內宣告自己的參數 allow-list（現有 plugin.json 的 input.required 目前只列必填欄位陣列，未涵蓋「允許哪些選填旋鈕」），路由層據此過濾/校驗輸入，而非假設所有 provider 共用同一組欄位。
  • 這與 llm-router 現有「explicit provider 不備援、chain 依序嘗試」的設計哲學相容——allow-list 只是加一層「參數形狀校驗」，不需更動 fallback 邏輯本身。

建議行動

低風險，可先做：在 specs/llm-provider-plugins/ 補一段研究筆記，記錄「若未來新增非文字生成 provider（影像/影片/語音），plugin.json 的 capability schema 需要從『必填欄位陣列』擴充為『per-capability 參數 allow-list』」，作為架構備忘，不動現有程式碼。

需人工決策：是否要真的新增影像/影片生成插件（目前系統無此需求信號，屬全新能力範疇，非現有插件的重構）；若要做，才需要決定 allow-list 校驗要放在路由層（仿 llm-router）還是各 provider 插件自行校驗。在無明確需求前不建議動工，僅留存架構參考。
